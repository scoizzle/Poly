## Summary

PR 62 centralizes inverse collection wiring and subscription registration inside the public static `Type.Create` factory method. Previously, inverse wiring was split across `BindCreate` (Store bind, autoLink `_field.Add` block) and `AddCreateNavMethod` (CreateNav, direct `_field.Add` + `Register*`). Now `Create` calls `peer.Attach*(created)` for each singular nav arg with a unique inverse, and `BindCreate` / `CreateNav` delegate to `Create` without duplicating the work.

**Call graph (primary evidence):**

```
BindCreate (StoreBind.cs:118-125)
  → Target.Create(args)             // public factory — same method simulate runs
      → peer.Attach*(created)       // wires inverse + Register*
  → RewrapObjectResult              // no _field.Add here (removed)

CreateNav (Notify.cs:199-253)
  → Target.Create(args)             // same public factory
  → createWiredThisCollection?      // skip Add/Register if Create already wired
      yes → return Success
      no  → _field.Add + Register* (legacy fallback, same as before)

Simulate (session.Lower → VM)
  → Entity.Create(args)             // same lowered AST body
      → peer.Attach*(created)
```

All three paths share the same `Create` method body. The `Attach*` methods are generated by `AddAttachNavMethod` (Notify.cs:275-305), the same mechanism used by CreateNav before this change. The `BindCreate` autoLink block (which did `_field.Add` outside Create) is removed. No sibling-path drift: `BindCreate` and `CreateNav` both call `Target.Create(...)`, and `Create` is the single point of inverse wiring.

**Test oracle strength:** 4 new/updated tests, including a full Roslyn-compile-and-load integration test (`Export_PublicCreate_CheckIn_SetsRoomOccupied_ViaGeneratedTypes`) that creates entities via reflection, verifies inverse collection membership, transitions a stage, and asserts subscription-driven state change. Ambiguous-inverse fail-closed is also tested. All 2830 tests pass.

### Issue 2 -- Severity: suggestion

- File: `Poly/DomainModeling/Lowering/DomainToCSharpExporter.cs:702`
- Description: The inline comment on line 702 says "same rule as FindInverseCollection." The logic is identical (count collection navs on peer targeting this entity, return if count == 1), but the code is a manual re-implementation of `FindInverseCollection` rather than a call to it. This is not a bug — the inline version operates on `peerEntity` directly from the constructor parameter loop — but the duplication is a maintenance risk if `FindInverseCollection`'s rule ever changes.
- Suggestion: Consider extracting the inner loop into a shared helper (e.g., `FindUniqueInverseCollection(peerEntity, entityName)`) used by both `Create` and `FindInverseCollection`, or at minimum add a comment noting the rule must stay in sync.
- Status: open
