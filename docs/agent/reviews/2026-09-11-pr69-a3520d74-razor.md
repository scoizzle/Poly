## Issues

### Issue 1 -- Severity: suggestion
- File: `Poly/Analysis/Analyzer.cs:39`
- Description: Dropping DistinctBy also dropped `.ToList()`. `AnalysisResult.Diagnostics` now aliases the live `AnalysisContext` `_diagnostics` list (`Diagnostics => _diagnostics`). Metadata is still snapshotted (`new NodeMetadataStore(...)`). Callers that capture `AnalysisContext` via `Analyze(..., setup:)` and call `Report*` after `Analyze` returns would mutate the published result. Normal production paths discard the context; this is residual snapshot asymmetry, not a fail-open.
- Suggestion: Prefer `context.Diagnostics.ToList()` (no DistinctBy) for a frozen report-order snapshot, or document that `Diagnostics` shares the context list for the lifetime of the result.
- Status: open

### Issue 2 -- Severity: suggestion
- File: `Poly/DomainModeling/Queries/DomainQueries.cs:260-275` (representative; also MCP counts / `DomainEvolution` summary counts)
- Description: Downstream **counts** treat `Diagnostics` as a bag of reports. Under the new contract, two identical reports yield ErrorCount 2. That is consistent with tip CORE but can mislead agent/UI copy that reads counts as unique issues. Fail-closed and `HasErrors` remain correct.
- Suggestion: Document multiset semantics at the analysis API boundary; if MCP/UX needs unique-issue counts, dedupe only at the presentation layer (not in `Analyzer`).
- Status: open

### Issue 3 -- Severity: nit
- File: `Poly.Tests/Syntax/Analysis/AnalyzerDiagnosticsTests.cs:5-15`
- Description: Test name claims report **order**, but both reports are identical (`DUP` / same message), so index order is not distinguished. Count=2 proves keep-both; order is only weakly evidenced.
- Suggestion: Optionally report two distinguishable messages (or codes) in sequence and assert `[0]`/`[1]` equality to that sequence.
- Status: open
