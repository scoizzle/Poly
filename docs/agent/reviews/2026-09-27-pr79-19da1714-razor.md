## Summary

The fix replaces the Block-in-expression shape with `LoweredExpression(Statements, Variables, Value)` (`Poly/DomainModeling/Lowering/LoweredExpression.cs:6-31`), and the sinks place the statements before the statement that reads the value. The named F1 shapes now compile and agree with the simulator: action `if (any … where)`, `assign N to count … where`, and a void create initializer. The new tests would have caught the old bug: I copied `QuantifierLoopTests.cs` and `ExportedCSharp.cs` onto `bc3423b6`, and 5 of the 10 tests fail there with CS1525/CS1026 (block in expression position). F2 (fail closed without a store) and F6 (outbound-only collection read) are fixed, and CORE is updated. The new shape still breaks at four sinks the tests do not cover:
- for-each invoke arguments collide on variable names (CS0136, F8);
- a non-void create-return always throws (F9);
- a path-prefix hop containing a quantifier now throws in the simulator, where master handled it (F10);
- a temporal-library child that is a quantifier throws, and the whole export now fails with it (F11).

## F3: source-order judgement (principle zero)

**Judgement: good enough to step through, for the shapes the PR lowers correctly.** What remains is ordering cosmetics inside pure expressions, not changes to what gets evaluated. F10 is the exception: it breaks simulation outright rather than ordering.

- **Short-circuit on the right of `and`/`or`: correct.** The right side's loops run only when the left side requires it (`DomainExpressionLoweringPass.cs:338-346`). A probe domain with `Active or any…`, `not (Active and any…)`, `(any…) and (all…)`, `(Active or any…) and (none…)`, and an action `if (Active or any…)` gave identical simulator and compiled-C# answers for all of them. `ActionShortCircuitAnd_SimulateAndGeneratedCSharp_Agree` asserts that the loop sits inside the `if` then-branch and not in the condition.
- **Left-side quantifier:** its loops run unconditionally before the operator. The source always evaluates the left side, so this is correct.
- **Guarded branches: never hoisted out.** Each nested effect is lowered with `Route(sub)` and placed inside its own then/else block (`EffectLoweringPass.cs:822-848`). Probe `Go2: if (Active) { if (any widgets where Active) {…} }` prints the loop *inside* `if (this.Active)`. For-each invoke argument loops run inside the loop, after the predicate `continue` guard (`:765-767`), so only for matched records.
- **Hoisted ahead, harmless, but not strictly in source order** (pure reads, nothing observable):
  - Comparison and arithmetic operands (`:289-315`, `:353-392`, `Combine`): every operand's loops run before any operand value is read, so stepping shows the right operand's loop before the left member read.
  - Singular invoke (`EffectLoweringPass.cs:666`): argument loops run before the `Rel == null` guard, even when the invoke then fails for a missing link.
  - Create-in probes re-evaluate the condition's loops (probe copy plus body copy, e.g. `any0` and `any1` in an entry). This duplication already existed in the probe design.
- **Traceability to the source snippet:** lowered nodes carry no source spans. That is not new; the pass has never attached spans. The generated names tell you which construct produced each variable: `any{n}`, `all{n}`, `none{n}`, `count{n}`, `item{n}`, `sawItem{n}`. The collection is `Member(subject, PascalCase(rel))`. The short-circuit temporary `t{n}` is the only synthetic without a source-derived name. That is acceptable, but a trace cannot point at a snippet, only at a construct kind. Follow-up only.

## Hand-editability gate: **NO**

Could Scot open these files cold and change them by hand? Mostly yes. `LoweredExpression` is small, `ShortCircuit` and `LowerFilteredQuantifier` read top-down, and the tests read as behavior (simulate, compile, invoke, compare). It still fails the gate on:

- **A naming contract that lives only in callers.** Unique variable names depend on copying `_quantifierSequence` into and out of each new pass (`DomainExpressionLoweringPass.cs:47`, `:519-521`). The one other place that creates a pass (`EffectLoweringPass.cs:753`, for-each args) does not copy it and emits code that does not compile (F8). Anyone who adds a pass by hand will hit this.
- **Two Block shapes with different meanings.** `LoweredExpression.Before` wraps a statement that is itself a `Block` instead of splicing it (`LoweredExpression.cs:17-23`). `CollectNode` flattens only one level (`EffectLoweringPass.cs:851-858`). So "the last node is the value" silently stops being true (F9).
- **Comments that claim more than the code does.** "analysis already rejects this form" (`DomainExpressionLoweringPass.cs:189-191`) is false; analysis accepts it (F10). `EffectAnalyzer.cs:771-772` and `:845-846` say quantifier policies export to a throwing method; that stub was deleted by this PR (F13). `Poly.Mcp/Docs/poly-dsl-guide.md:883-892` says the same (F13).
- **Twin guards that disagree.** The runtime path-prefix path throws on statements (`:188-192`). The export twin (`:196-197`) hoists them silently (F10).
- **A `Try…` method that throws** (`DomainEntityInstance.Runtime.cs:373`), reached from `IDictionary.ContainsKey` (F15).
- No agent paperwork was found in product paths: a grep of the added lines for F#/PR#/Razor/review/agent found nothing.

## New findings

### F8 -- Severity: bug
- File: Poly/DomainModeling/Lowering/EffectLoweringPass.cs:753 (argument statements at :767, locals at :772-774; flattening at :851-858; counter at DomainExpressionLoweringPass.cs:47, :519-521)
- Description: for-each invoke arguments are lowered by a fresh `argPass` whose `_quantifierSequence` starts at 0. Its `any0`/`item0` locals are declared inside the foreach body. The action's other quantifier locals come from `_expressionPass`, which also starts at 0, and `CollectNode` flattens them into the method scope. C# rejects the inner redeclaration. Repro, which passes analysis: `Go: action { if (any widgets where Active) { assign N to 1 }  for widgets as w invoke w.Mark(flag: any widgets where Active) }`. The export has `var any0` at method scope and again inside `foreach (var target0 …)`, and Roslyn reports **CS0136**: "A local or parameter named 'any0' cannot be declared in this scope because that name is used in an enclosing local scope". Pass B concluded "argPass reset does not collide". That is refuted here: its probe lacked a top-level quantifier in the same action.
- Suggestion: build `argPass` from `_expressionPass` so it shares the counter, or move the counter into a shared per-method object on `LoweringContext` so no caller can forget it. Add a compile+invoke test for this exact shape.
- Status: open

### F9 -- Severity: bug (found by Pass B; confirmed)
- File: Poly/DomainModeling/Lowering/LoweredExpression.cs:17-23; Poly/DomainModeling/Lowering/EffectLoweringPass.cs:1152, :851-858; Poly/DomainModeling/Lowering/DomainToCSharpExporter.Actions.cs:292-298
- Description: when a create initializer produces statements, `Before(loweredInitializers, new Block(nodes, locals))` nests the create block as one child. `CollectNode` flattens only one level, so the body's last node is a `Block`, not the create result. Repro: `Spawn: action -> Widget { create in widgets { Active: any widgets where Active } }`. The export's `Spawn()` ends in `throw new NotSupportedException("Action 'Spawn' has return type but its last effect does not produce a value…")`. The simulator fails with `VM compile rejected: no matching constructor for 'NotSupportedException' with 1 argument(s)`. `SpawnPlain: action -> Widget { create in widgets { Active: true } }` succeeds. `CreateInitializer_QuantifierValue_…` (`QuantifierLoopTests.cs:283`) only covers a void action. On master, action quantifiers threw outright, so this is not a regression, but it is a valid domain that neither simulates nor prints.
- Suggestion: have `Before` splice a `Block` statement (prepend the parts to `sb.Nodes`, merge the variables), or make the action-body collector recurse. Add a compile+invoke test for `-> Entity` + `create in … { p: <quantifier> }`.
- Status: open
