## New findings

### F21 -- Severity: bug (found by Pass A; reproduced by me)
- File: Poly/DomainModeling/Runtime/DomainEntityInstance.cs:400-407 (the coercion) and :409-417 (`CoercePolicyBool`); root: Poly/DomainModeling/Analysis/ExpressionTypeAnalyzer.cs (policies are walked, but no Boolean result type is required)
- Description: `CoercePolicyBool` routes policy results through `CoerceBooleanBagValue("Boolean", …)`. With the F19 change, an integer other than 0/1 now reaches the `not a boolean` throw. On master and at eb603731 it was truthy (`l != 0`). Analysis accepts non-Boolean policy bodies. My probe: `Bin: entity { N: Number default(0)  P: policy { N }  Q: policy { N + 1 } }` evolves and analyzes cleanly, and `EvaluatePolicy` with N=2 throws "Policy 'P' produced Int64, not a boolean." (Q the same). Pass A saw the same through MCP with `policy { Qty }`, and reports `policy { count lines }` throws once there are two or more links. The result depends on the value: N=0 and N=1 still answer, N=2 throws. That is a trap in the harness. The export of such a policy already fails to compile (CS0029 `long` to `bool`, reproduced), so no working print is lost. The simulator regression is real on a domain analysis accepts.
- Suggestion: move detection earlier. Have analysis reject a policy whose expression is not Boolean (and add a test), so both simulate and print refuse it the same way. Until then, either keep `CoercePolicyBool`'s own integer handling apart from the bag coercion, or make it throw for every integer result, so the outcome does not depend on the value.
- Status: open

### F22 -- Severity: suggestion (hand-editability gate; found by Pass A; reproduced by me)
- File: Poly/DomainModeling/Analysis/EffectAnalyzer.cs:771-779, :844-849; Poly.Mcp/Docs/poly-dsl-guide.md:554-556
- Description: `ReadsSingularHopOrExists` returns true for every `Exists`/`NotExists`, including a scalar property (`Name exists`) and a collection (`items exists`). The summary says "or `Rel exists`", and the comment and diagnostic give "an unlinked hop simulates false but the export dereferences null" as the reason. The export lowers `exists` to `x != null` or `.Count != 0` (`DomainExpressionLoweringPass.cs:249-266`), with no dereference, so the reason does not apply to those arms. My probe: `Widget { Name: Text  HasName: policy { Name exists } … }` with `for widgets as w where w HasName invoke w.Mark()` is rejected with that exact dereference message and the advice to use "a local policy over the record's own properties". Over-rejecting `exists` predates this PR and is conservative. What's new is the stated reason, which is F18's fix, and it is still wrong for two of the three arms.
- Suggestion: narrow the check to what the reason covers (`RelationshipNavigation`), with a compile+simulate test that `exists` for-predicates agree. Or keep `exists` rejected and give it its own true reason and message. Align the guide.
- Status: open
