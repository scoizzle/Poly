## New findings

### F23 -- Severity: bug (regression vs 52d063a9 and master; found by me and Pass A independently; reproduced by execution)
- File: Poly/DomainModeling/Analysis/EffectAnalyzer.cs:781-791, :855-863 (`TestsPropertyExists(expr, targetEntity)`); Poly.Mcp/Docs/poly-dsl-guide.md:554-561, :892-895
- Description: `TestsPropertyExists` walks the whole predicate policy but compares every `exists` target with the **`for` target entity's** properties. Inside a quantifier body, the target belongs to the **related** entity, so it never matches and the predicate is allowed. Repro, which evolves and analyzes cleanly at 66d728bf:
  ```poly
  domain Yard
  Part: entity { Qty: Number }
  Widget: entity {
    Flag: Boolean default(false)
    parts: many Part
    Pick: policy { any parts where Qty exists }
    Mark: action { assign Flag to true }
  }
  Bin: entity {
    widgets: many Widget
    Go: action { for widgets as w where w Pick invoke w.Mark() }
  }
  ```
  With one widget linked to one part whose Qty is unset, simulate returns `Failure("for widgets.Mark matched zero targets.")` with Flag=False. The compiled export returns `Success` and sets Flag=True. They pick different records, which is exactly what the rule's comment says it prevents. Master rejected this predicate (store-dependent) and so did 52d063a9 (`ReadsSingularHopOrExists` matched any `Exists`), so this is newly accepted. The reverse mismatch is only an over-rejection and is harmless: a `for` target property whose name matches a related entity's property rejects a relationship `exists` it could allow.
- Suggestion: resolve the entity per scope. When walking into `AnyExpr`/`AllExpr`/`NoneExpr`/`CountExpr`, switch to the relationship's target entity (the related entity is already resolved for quantifier validation in `PolicyConstraintAnalyzer`), and do the same for nested hops. Or, more simply, reject any `Exists`/`NotExists` whose target is not a relationship of the entity in scope. Add the repro above as an analysis-rejection test, and qualify the guide until then.
- Status: open

### F24 -- Severity: suggestion (pre-existing; acknowledged by the implementer; non-blocking)

- Description: two simulate/print disagreements outside `for` predicates are now known and written down, but not rejected and not tracked:

Decide what scalar `exists` means (for example "not null and not default") and lower it the same on both paths, or reject scalar `exists` outright. Track both in `docs/plans/` if they are out of P3-A scope.
- Status: open
