## Summary

`TestsPropertyExists(context, domain, expr, entity)` (`EffectAnalyzer.cs:855-882`) now changes scope when it steps into a quantifier. It resolves the relationship with `TryResolveRelationship` and its target with `TryResolveEntity` (`:871-879`), the same helpers the `for` check uses. It then checks the body against that entity. The call site is `:781`. The quantifier records expose only `Body` as a child (`DomainExpression.cs:195/205/215/226`), so no outer-scope expression gets checked against the wrong entity.

When a relationship does not resolve, the walk returns false and trusts the policy analyzer to report it. That holds at depth 1 (`PolicyConstraintAnalyzer.cs:99-114`, `:169-174`). It does not hold for a nested quantifier: the body walker `ValidateRelatedPropertyAccess` (`PolicyConstraintAnalyzer.cs:311-336`) has no quantifier case. It just recurses and checks names against the first-level entity. This is F25 (pre-existing, same on master) and the source of F26.

## New findings

### F25 -- Severity: suggestion (pre-existing, same on master; `PolicyConstraintAnalyzer.cs` is untouched by the PR; reproduced by execution)
- File: Poly/DomainModeling/Analysis/PolicyConstraintAnalyzer.cs:311-336 (`ValidateRelatedPropertyAccess`)
- Description: a quantifier nested inside a quantifier body is never validated. Its relationship name is not resolved, and its body names are checked against the **first-level** related entity. Each of these evolves and analyzes with 0 errors at both c6da0f18 and 66d728bf, with Part `{ Qty, bolt, bolts }` and Bolt `{ Size }`:
  - `any parts where (any nope where Qty > 0)`
  - `any parts where (any widgets where Qty > 0)`
  - `any parts where (any bolts where Qty > 0)`, where Bolt has no Qty

  For each one, simulate fails with "VM compile rejected: Type 'Part' does not contain a member named 'Nope'" (or the matching message for the others), and the export fails with CS1061. A resolvable nested quantifier with valid names works, and simulate and print agree (`any parts where (any bolts where Qty > 0)` with Bolt.Qty: both give ok=False, A=False, B=False). When the inner body uses a name that exists only on the inner entity, it is wrongly rejected (`any parts where (any bolts where Size > 1)` → "Path-prefix body references property 'Size' … on target entity 'Part'").
- Suggestion: in `ValidateRelatedPropertyAccess`, handle `AnyExpr`/`AllExpr`/`NoneExpr`/`CountExpr` by calling `ValidateQuantifierExpression(context, lookup, rel, body, targetEntity)`. The lookup would have to be threaded through. Or reject nested quantifiers outright if they are out of P3-A scope. Either way the claim in F26 becomes true. Track this on the board if it is deferred.
- Status: open

So this is not a silent divergence, and I do not rank it as a bug.
- Suggestion: fix F25, which makes the comment true. Otherwise reword the comment to "a top-level unresolved quantifier is reported by the policy analyzer; nested ones are not validated (F25)" and qualify the guide's "at any depth" to resolvable quantifiers.
