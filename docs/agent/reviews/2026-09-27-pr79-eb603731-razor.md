## Summary

The fix moves local-name numbering into a `LocalNames` object carried on `LoweringContext` (`LocalNames.cs:6-9`, `LoweringContext.cs:85-88`, `:108`). Every pass built from an existing context `with { … }` shares that object, so the for-each argument pass, the nested quantifier-body pass, and the effect pass all number from one counter. `LoweredExpression.Before` now splices a `Block` statement instead of nesting it (`LoweredExpression.cs:20-23`). A runtime path-prefix hop whose target has a quantifier lowers to `t = false; if (ExistsRelated) { loops; t = value }` (`DomainExpressionLoweringPass.cs:190-199`). Library handlers get a route that collects child statements (`:234-247`). The collection read is split into a matcher that never throws and a store read (`DomainEntityInstance.Runtime.cs:372-399`). Every sink named last time now compiles and agrees with the simulator. I confirmed that with the new tests and with my own probes: an entry/exit quantifier, a quantifier in a runtime path-prefix inside `or`/`and`, two temporal children plus a date-add assign, a non-void action mixing assign/if/create, and several quantifier arguments on singular and for-each invokes. What remains is a sink the tests never reach: the method that dispatches one action name across stages (F16).

## Hand-editability gate: **NO**

Could Scot open these files cold and change them by hand? Mostly yes, and this pass is better than the last one. The save/restore of a counter is gone. `LocalNames` is nine lines. The path-prefix and library changes read top-down. The Dictionary split names what each half does. The tests read as behavior (build a domain, simulate, compile, invoke, compare). A grep of added lines for F-numbers, Razor, PR numbers, and "review" finds nothing in product or test paths. It still fails on:

- **A contract that the code claims but does not keep.** `LocalNames` says it is the "Shared source of unique local names for one method's lowering" (`LocalNames.cs:5`, and again at `LoweringContext.cs:85-88`). `AddStageDispatchedActionMethod` builds one C# method out of several separately constructed `EffectLoweringPass`es (`DomainToCSharpExporter.Actions.cs:128`, `:138`, each reaching `LowerActionToMethodBody` → `new LoweringContext` → a new `LocalNames`). So one method gets several generators that all start at 0. It also drops the entity-level body's declarations (`:138-140` `.Nodes`). The result does not compile (F16). Anyone adding a code path that stitches bodies together will repeat this, because the one-per-method rule lives only in a comment.
- **Two name generators in one method.** `EffectLoweringPass` still numbers its own locals (`invoke{n}`, `target{n}`, `matched{n}`, `result{n}`, `assignValue{n}`, `create{n}`, `created{n}`) from `_forEachInvokeSequence`/`_createInProbeSequence` (`EffectLoweringPass.cs:43-44`, `:316`, `:663`, `:680`, `:722`, `:1119`), next to `_context.Names`. The prefixes don't collide today, so this is not a bug. But the "shared source" is not the only source, and a new prefix in the effect pass could silently collide. (Part of F16's suggestion.)
- **A name and a reason that no longer match the code.** `ContainsStoreDependentExpression` (`EffectAnalyzer.cs:848`) now leaves out quantifiers. Quantifiers *are* store-dependent at simulate time: they read `ReadLinkedTargets`, which throws without a store (`DomainEntityInstance.Runtime.cs:390-393`, and `docs/CORE.md:137` says so). The comments at `:772-774` and `:844-847` give "store host reads at simulate time" as the reason that separates path-prefix/exists from quantifiers, and that reason is false (F18).

## New findings

### F16 -- Severity: bug (found by me and Pass A independently; reproduced with Roslyn)
- File: Poly/DomainModeling/Lowering/DomainToCSharpExporter.Actions.cs:137-141 (branches built at :128; each reaches `LowerActionToMethodBody` → `new LoweringContext` at :436 → a fresh `LocalNames`); Poly/DomainModeling/Lowering/LocalNames.cs:5; Poly/DomainModeling/Lowering/EffectLoweringPass.cs:43-44
- Description: when one action name exists at entity level and on a stage, the exporter emits one method: an `if (CurrentStage == X) { branch body }` per stage, then the entity-level body appended with `BuildFullActionBody(...).Nodes`. `.Nodes` drops that Block's `Variables`, so the tail assigns locals that are never declared. And because each branch and the tail come from separate passes with separate `LocalNames`, the names repeat (`any1`/`item0` in every branch and in the tail). Keeping the declarations would then fail with CS0136 instead. Repro, which passes analysis:
  ```poly
  domain Yard
  Widget: entity { Active: Boolean default(false) }
  Bin: entity {
    N: Number default(0)
    widgets: many Widget
    Go: action { if (any widgets where Active) { assign N to 1 } }
    Open: stage { Go: action { if (any widgets where Active) { assign N to 2 } } }
    Closed: stage { }
  }
  ```
  The export's `Go()` ends with `any1 = false; foreach (var item0 in this.Widgets) …` at method scope, and Roslyn reports **CS0103** "The name 'any1' does not exist in the current context". On master `640025f7` the same domain fails earlier with `NotSupportedException` (action quantifiers were not lowered), so this is new surface that does not compile, not a regression. The same drop already breaks `for widgets as w invoke w.Mark()` in this shape on master (CS0103 `matched0`); that is pre-existing, and this PR widens it to every quantifier.
- Suggestion: pass `locals` through at `:138-140` (as `:255-257` already does). Create one `LocalNames` per emitted method in `AddStageDispatchedActionMethod` and hand it to every `BuildFullActionBody` / `LowerActionToMethodBody` call (for example through an optional `LoweringContext.Names` argument). Consider moving the effect pass's `_forEachInvokeSequence`/`_createInProbeSequence` names onto the same `LocalNames` so "one source per method" is true. Add a compile+simulate test for the repro above (quantifier and for-each variants).
- Status: open

### F17 -- Severity: suggestion (Pass A item 2; confirmed by me; the behavior predates this PR)
- File: Poly/DomainModeling/Lowering/DomainExpressionLoweringPass.cs:202-203 (export twin) vs :178-199 (runtime); Poly.Tests/DomainModeling/Lowering/QuantifierLoopTests.cs:454-502; docs/plans/simple-agent-tasks/e2e-2-README.md:6
- Description: for an unlinked hop, the simulator returns `false` (`ExistsRelated` guard) but the exported policy method dereferences `this.Team!` and throws `NullReferenceException`. My probe: `P: team Active == any workers where Active` and `Plain: team Active` on a Dept with no team simulate `False`/`False`, and both print methods throw an NRE. `Plain` shows the gap is older than this PR. The PR's new test builds only linked Depts, and e2e-2 says path-prefix hops with a quantifier "lower to the same foreach in simulate and print", which is true only when linked.
- Suggestion: either make the export's policy hop `this.Team != null && …` to match the runtime guard (one change for plain and quantifier hops), or narrow the e2e-2 sentence to "when the hop is linked" and add an unlinked case that pins the current difference. Track it with P3-B/C if it is out of P3-A scope.
- Status: open

### F18 -- Severity: suggestion (hand-editability gate)
- File: Poly/DomainModeling/Analysis/EffectAnalyzer.cs:772-774, :844-848; Poly.Mcp/Docs/poly-dsl-guide.md:554-556
- Description: `ContainsStoreDependentExpression` no longer means "store-dependent". Quantifiers read the store at simulate time and fail closed without one (`DomainEntityInstance.Runtime.cs:390-393`; `docs/CORE.md:137`), but the method excludes them. The comment's stated reason ("Path-prefix and Rel exists still use store host reads at simulate time") would apply equally to quantifiers, so a reader cannot tell from it why quantifiers are allowed and path-prefix is not. The honest reason is F17: the unlinked-hop export does not match. The MCP guide repeats "store-dependent at simulate time" as the reason.
- Suggestion: rename to what it checks (for example `ReadsSingularHopOrExists`), and state the real reason in one line: an unlinked hop simulates false but the export dereferences null. Align the guide sentence.
- Status: open

### F19 -- Severity: nit
- File: Poly/DomainModeling/Runtime/DomainEntityInstance.cs:399-407 (used at :114, :518)
- Description: `CoerceBooleanBagValue` turns any nonzero integer into `true` for a Boolean property or parameter. The VM only produces 0/1, so this silently accepts `5` from a caller (for example MCP `create_instance`) as `true`, where the typed export would not accept an integer at all. It is consistent with the older `CoercePolicyBool`, so this is not a regression on valid inputs. It is a small fail-open.
- Suggestion: coerce only `0`/`1` and leave other values alone (or reject them), and add a test.
- Status: open

### F20 -- Severity: nit

This PR removed that path; the real reason is the `ExistsRelated` hop guard. The file is untouched by the PR (noted as scope last time), but the comment is now plainly false.
