## Foreman question (a): F2 by analysis rejection

My probes at master and cd6cec02 (simulate, print, analysis):

| Model | master | cd6cec02 |
|-------|--------|----------|
| `OrderStage: enum { Low, High }` + `Order` with stages | analysis OK; simulate runs; **print CS0101** | rejected: "Enum 'OrderStage' collides with the stage enum generated for entity 'Order'. Rename the enum." |
| `OrderStage: enum { Draft, Placed }` (members = the stage names) + `Order` with stages | analysis OK; simulate runs; **print CS0101** | rejected (same message) |
| `OrderStage: enum { Low, High }`, `Order` **without** stages | OK; simulate OK; print compiles | OK; simulate OK; print compiles |
| `OrderStage` enum, no `Order` entity (used by `Invoice`, which has stages) | OK / OK / compiles | OK / OK / compiles |

- **Honest early error, or does it break a valid model?** It is an honest early error. Every model the rule rejects failed to print on master, including the case where the enum's members equal the stage names, so the exporter never adopted a declared enum. No valid model is lost. Only "simulate-only" validity is lost, and that is not a contract Poly offers (principle 2: simulate and print are the same tree).
- **Is the rule scoped correctly?** Yes. It fires only when the entity has stages and the name is exactly `{Entity}Stage`. Nothing else in analysis produces a different stage-enum name: `EntityStructureAnalyzer.cs:61-64` falls back to the same literal. Neither the no-stages case nor an unrelated entity triggers it.
- **Is the diagnostic clear?** Yes. It names the enum and the entity, says why, and says the fix ("Rename the enum.").
- **Would unambiguous runtime resolution be better?** No. It would make simulate accept a model that print cannot compile, which is exactly the divergence P3 is removing. The runtime throw is a sound backstop for unanalyzed domains.
- **Recommendation: keep the rejection.**
- Sibling, not filed as a PR finding: a *value type* named `OrderStage` next to `Order`'s stages is still accepted by analysis and fails print with CS0101 (probed at cd6cec02). The collision is between a declared type and a generated type in general, not just enums. This is pre-existing and outside the PR, and worth a board item: "reject any declared type named `{Entity}Stage` when the entity has stages".

### F8 -- Severity: suggestion (hand-edit gate: dead guard in the new F1 code; verified)
- File: Poly/DomainModeling/Lowering/DomainExpressionLoweringPass.cs:419
- Description: `hops.Contains(hop)` compares freshly built `Member` records. `Node` equality includes a per-instance `NodeId` (`Poly/Ast/Node.cs:15`), so two structurally identical members are never equal: my probe got `Equals` = False and `List.Contains` = False. The check never drops anything. For example, `Age + advisor Age < advisor mentor Age` emits `this.Advisor != null` twice. The result is correct but redundant, and the guard implies de-duplication that does not happen.
- Suggestion: remove the check (duplicate guards are harmless), or de-duplicate by the hop's path string, as the previous name list did.
- Status: open
