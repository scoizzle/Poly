### F201 [suggestion] "Cascade" is counted as "more than one error", which overstates it about twofold
Class comment (lines 11-13): "One edit is one root cause, so any count above 1 is cascade." Body: "Cascade shows up in two kinds only: renaming a property (5 of 11 give more than one) and changing a type (6 of 10)." But the body also defines the cell: "Errors that name the broken element are the direct report; errors for the same break that do not name it are likely cascade". By that definition (cascade = n - m) the table gives: rename a property 15 errors, 11 name the property, so 4 cascade, in **3 of 11** breaks (`simulate-create-create-in` 4 (2), `simulate-create-in` 2 (1), `simulate-create-type` 2 (1); `warehouse` 3 (3) and `mcp-library` 2 (2) are one edit hitting several uses of the name, each a direct report); type change 19 errors, 12 name it, so 7 cascade, in **3 of 10** (`university` 4 (1), `warehouse` 4 (1), `mcp-library` 2 (1)); entity, stage and action 0. Most cascade from one edit is **3**, not 4, and the number of breaks with any cascade is 6 of 49, not 11. The reading changes in the other direction too: `Mentions` only matches the old name, so a message that names the renamed property by its new name ("does not provide required property 'AmountGone'") counts as not naming it, and the body itself says a count by name "undercounts the cascade for type changes". Either way, decision 18 needs a definition it can cite. Fix: drop "any count above 1 is cascade" from the class comment; report cascade as n - m (and say it is a name match) in the body and, ideally, as a column in the per-break table. Also the body sentence "Some errors do not name the broken element (type change: 12 of 19 do)" is inverted: 12 of 19 do name it, 7 do not.

### F202 [suggestion] `ChangeNumberToText` can rewrite the property name instead of the type
`CascadingErrorReportTests.cs:114-119`: the regex finds the first `name: Number` line, then `text.IndexOf("Number", m.Index, ...)` searches from the start of the match, which is the start of the line (`^\s+`). If the property is `PhoneNumber: Number`, the first "Number" is inside the name, the edit becomes `PhoneText: Number`, and the cell reports a harmless rename (victim `PhoneNumber`, probably 0 errors). No sample hits it today (checked all ten victims: `Total`, `Amount`, `NightlyRate`, `MaxCredits`, `Capacity`, `Copies`), so the printed table is right, but one new sample or one renamed property would silently mis-measure. Fix: capture the type word as a group (`^\s+(\w+): (Number)\b`) and edit at `Groups[2].Index`. Mill: found it (as a bug); I confirmed the index logic and checked the samples; kept as suggestion because the current output is unaffected.

### F203 [suggestion] "Mentioned elsewhere" cannot tell a second declaration from a use
`RenameDeclaration` (line 107) and `DeleteAction` (line 126) accept a declaration when its name occurs at least twice in the file, but the declaration itself is one of the occurrences and another entity's declaration of the same name or a string literal counts as the second. Checked against the zero cells: `crm.poly` stage `New` (declared at lines 31 and 233, nothing else), `hotel.poly` action `ReturnToService` (declared at 62 and 108) and property `Name` (declared in many entities), `mcp-library.poly` stage `Active` (the other mentions are the strings `"Active"`). Those are bad picks, not silent holes. The body admits this ("some '0' cells are a bad pick rather than a silent hole. They are kept, not filtered") but then lists "Some breaks produce no Error at all and the domain still loads" among its findings and counts them in the `no Error` column (16 of 49 breaks). A reader of decision 18 cannot tell which zeros are real. Fix: count mentions that are not themselves a declaration of the same shape (for example, skip names declared more than once, and ignore matches inside string literals), regenerate, and keep the "still loads with no Error" examples only if they survive.
