### 3. General or special-case; semantics of dropping Notify
- The condition is unconditional per context kind (every subscription-handler body, every first-stage entry). No probe names, no check on transition presence. Mutation M4 (false only when entity name is "Tr"/"Z") is caught by the in-repo suite: the cascade row goes red (entity `W`), and my V2 rename variant fails with CS1061.
- Simulate-side `Notify` (`DomainEntityInstance.HostAbi.cs:21-33`) only calls `Store.NotifyTransition` and returns immediately while `_isExecutingSubscription`; the cascade to the next subscribers is store-owned (`DomainInstanceStore` recursion on a stage change). So during a handler body the simulator's `Notify` is a no-op; dropping it from the printed code drops nothing simulate fires. The printed class never had a `Notify` member to call, so the old output was simply uncompilable.
- What printed code does lack is the `Notify{Stage}Subscribers(previousStage)` fan-out that an action transition emits (`PostTransitionNotifyStages`); handler contexts do not pass it. That is the real subscriber-cascade gap, pinned (check 4) and independent of `this.Notify`. Verified with the subscriber test: V15 and the pinned cascade row show simulate W to R, printed W stays P; the 1-hop rows (`SubscriberTransitionsToo`, `BothTransition`) agree.
- Decision 12 / simulate == print: holds for the card probe and every 1-hop variant; the two gaps are known, pinned, owned.
