## What changed (PR only, `b480caaa..8787ad8d` minus docs)

Compared with master, the PR is now small:

- **`EffectAnalyzer.ValidateAssign`:** a root `RelationshipNavigation` still gets DMEFF012. The new rule is that any other shape that is not a bare `PropertyAccess` gets DMEFF001: "Assign target is not a property of entity 'X'. An assign writes one of the entity's own properties by name: 'assign <Property> to <value>'." The general walk from `0fc64633` and `IsOwnStateTarget` are both gone. The bare-property rule covers every nested case, so neither is needed.
- **`EnumerateRelationshipNavigations`** is now `internal`, and `SubscriptionAnalyzer` uses it in place of its own copy. `HasNestedRelationship` is deleted and behaves identically: it matched the node itself or any descendant.
- **`SubscriptionAnalyzer`:**
  - `isAssignTarget`, `PeerAsAssignTarget` and the "Peer binder path-prefix cannot be an assign target" report are removed.
  - An assign target is collected only when it is a bare property. Every other target shape is left to `EffectAnalyzer`.
- **Tests:** 9 new cases in `CrossEntityMutationAnalysisTests`:
  - owned over a relationship, in an action, in entry/exit and in a when handler
  - an owned field
  - an owned access named after a relationship, where simulate refuses the domain
  - a computed target
  - a parameter target
  - a peer path, reported once (both bare and under an owned value)

  `SubscriptionEffect_PeerAsAssignTarget_AnalysisError` now expects exactly one error, DMEFF012.

The only producer of `AssignEffect` in the product is `PolyDslParser.cs:685`, and it always builds `Property(name)`. MCP builds none. So the new DMEFF001 rule can only fire on models built through the API, and valid DSL and the goldens are unchanged.

## Findings (all nits, none blocking)

- **F435 (nit, card).** For a peer-binder assign target, DMEFF012 calls the binder a "relationship" and suggests `invoke <binder>.SomeAction`, which Analyze rejects. This is API-only and fails closed. Fix: when the root name is the handler's `PeerBinding`, say "peer binder" and point to "use peer fields on the right-hand side; change the peer through its own `when` or an action". That needs the subscription's peer binding passed into `ValidateEffects` for subscriptions.
- **F436 (nit).** The class summary in `CrossEntityMutationAnalysisTests` says "A mutation that targets another entity is an Analyze Error (DMEFF012)". Both are true for every target that starts with a relationship. Suggested wording: "DMEFF012 when the target starts with a relationship; any other target that is not a bare property is DMEFF001."
