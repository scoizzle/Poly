## F1 — Cross-entity invoke arg that references the caller's action parameter is mangled to the instance handle
- **Signal:** export/runtime divergence
- **Severity:** 🟠
- **Slice:** VM & interpretation (EmitMember unresolved-member passthrough + runtime binding provider)
- **Repro:** `probes/fleet-eval/11-vm/vm-crossinvoke.poly` — `Order.PayWithParam(amount:100)`
  (`invoke invoice.Settle(amount: amount)` + `assign Total to amount`). Runtime: source `Total = 100`
  but linked `Invoice.Amount = 1`. `PayWithLiteral` (`invoke invoice.SettleLiteral(amount: 100)`)
  sets `Amount2 = 100` correctly, isolating the param-reference form.
- **Expected:** target `Invoice.Amount == 100`. The C# export emits `this.Invoice.Settle(amount)`
  which passes 100.
- **Actual:** the arg binding `amount` is lowered to `Member(Order, "amount")` and compiled by
  `EvaluateParameterBindings` (`DomainEntityInstance.cs:537`) with the **entity-only** type provider
  (not the action-scoped provider that the effects loop uses). `amount` is an action parameter, not a
  property, so member resolution fails; `DirectVmAbiEmitter.EmitMember` (DirectVmAbiEmitter.cs:1106-1107)
  falls back to a silent passthrough returning the **instance heap handle** (the bag's handle number),
  and `InterpretResult` (Unknown root) returns the raw long. The target receives `amount = 1`.
- **Proposed patch:** (a) runtime — pass the action-scoped `TypeDefinitionNodeAnalyzer`
  (`BuildActionScopedTypeDefAnalyzer(action)`) into `EvaluateParameterBindings` (and the `for`
  fan-out binding path), mirroring the effects loop; (b) VM defense — `EmitMember` should throw on an
  unresolvable member instead of returning the instance expression.

## F2 — Missing action parameters are not validated: Text params silently store `System.Reflection.Missing`, Number params throw `InvalidCastException`
- **Signal:** silent-gap (export/runtime divergence; guide-drift vs "all params required")
- **Severity:** 🟠
- **Slice:** VM & interpretation (member-read fallback) + runtime arg validation
- **Repro:** `probes/fleet-eval/11-vm/vm-warehouse.poly` — `Bin.Mark` invoked **without** `label`:
  action returns `succeeded=True` and `Note = System.Reflection.Missing (Missing)`.
  `probes/fleet-eval/11-vm/vm-orders.poly` — `Order.ApplyDiscount` invoked without `rate`:
  `InvalidCastException: Unable to cast object of type 'System.Int64' to type 'System.Reflection.Missing'`.
- **Expected:** the runtime fails loud on a missing required parameter (the C# export cannot be called
  without it — `Mark(string label)` is compile-time; the guide §6 invoke: "all params required").
- **Actual:** `DomainEntityInstance.InvokeAction` injects whatever args are given without checking the
  action's declared parameters; the MCP `invoke_action` tool likewise doesn't validate. The VM
  dictionary-backed member read (`AstPropertyDefinition.EmitRead`, TypeDefinitionNodeAnalyzer.cs:310-324)
  returns `Missing.Value` when the key is absent. Text target stores it silently; a Number target
  surfaces a confusing cast error. Behavior is type-dependent — Text silently corrupts, Number throws.
- **Proposed patch:** validate required action parameters in `InvokeAction` (throw before injecting
  args), and/or have the member-read fallback throw for `Missing.Value` on read (fail loud, no sentinel).

## F3 — VM truncates non-long value-type member reads to `long` (double/float/decimal silently mis-evaluate)
- **Signal:** silent-gap / latent divergence (ABI contract violation)
- **Severity:** 🟡
- **Slice:** VM & interpretation (ConvertMemberResult ABI conversion)
- **Repro:** direct VM harness (AST program, `Interpreter.Compile` + `Execute`) with a dictionary-backed
  type def whose property is `double` (`PrimitiveTypeReference(Float64)`), bag value 3.7:
  - `Price > 2.5` → **False** (expected True)
  - `Price == 3.7` → **False** (expected True)
  - `Price * 2` → raw bits `2`, `Int64BitsToDouble` = `1E-323` (expected 7.4)
  - `decimal` 3.70: `== 3.70` → False; `3.70 + 1.30` → raw `3` (expected 5)
- **Expected:** `AbiValueTypes.IsLongRepresentable` (AbiValueTypes.cs:17-25) lists float/double/decimal
  as long-representable, so member reads must preserve them. The comparison/arithmetic double paths
  (DirectVmAbiEmitter.cs:633-636, 757-759, 789-791) reinterpret the ring `long` via
  `Int64BitsToDouble`, but `ConvertMemberResult` (DirectVmAbiEmitter.cs:1155-1170) first truncates
  `(long)(double)value` — the truncated integer re-read as double bits is a denormal near zero.
  Decimal arithmetic runs as raw `long` arithmetic (no decimal rounding).
- **Reachability caveat:** the DSL parser (PolyDslParser.cs:128) and MCP `add(kind: property)` analysis
  reject `Double`/`Float`/`Decimal` type names ("references unknown type"), so this is **not** reachable
  through shipped authoring today — only via programmatic/IR construction. It is a latent correctness
  hole in the VM ABI for types the ABI explicitly claims to support (a future pack would trip it), and
  in the equality case it produced an `IndexOutOfRangeException` (scalar bits dereferenced as a heap
  handle — type-confusion hazard).
- **Proposed patch:** `ConvertMemberResult` must box float/double/decimal members as heap handles
  (like DateTime/DateOnly/Guid) instead of truncating to `long`, and the ring double path must only be
  entered when both operands are known to carry double bit patterns.

## F4 — Fractional literals parse as Text, so the guide's own arithmetic example is rejected and the VM's double path is unreachable from DSL
- **Signal:** guide-drift (blocks shipped arithmetic surface; adjacent to expression-type slice)
- **Severity:** 🟡
- **Slice:** VM & interpretation (arithmetic reachability) — root cause in `Poly/DomainModeling/Parsing/DslExpressionParser.cs`
- **Repro:** any probe policy using a fractional literal — e.g. `HasFraction: policy { Total * 0.5 > 10 }`
  or `FractionCmp: policy { Total > 0.9 }` → analysis error `arithmetic operand is not numeric
  (got 'Number' and 'Text')` / `comparison between incompatible types 'Number' and 'Text'`.
- **Expected:** the guide §8 lists `Number` primaries and ships arithmetic, with the example
  `Total * 0.9` (guide line 834). A fractional literal is a Number.
- **Actual:** `DslExpressionParser.ParsePrimary` (DslExpressionParser.cs:111-116) does
  `long.TryParse("0.5")` → false → `DomainExpression.Literal(numText)` — the literal becomes a
  **string** "0.5". The domain type analyzer then types it Text, so all fractional arithmetic fails
  authoring, and the VM double/float arithmetic paths (F3) are unreachable from the DSL surface.
- **Proposed patch (parser slice):** parse a failed-integer numeric token as a double literal
  (`double.TryParse` → `Literal(double)`); add a regression probe for `Total * 0.9`.
