# Dogfood 2026-11-20 — real systems described in Poly

**Tool:** `poly-local` MCP (`poly_workspace`, `poly_define`, `poly_check`, `poly_simulate`, `poly_export`).
**HEAD:** `bbe2d6bf1`.
**Question:** can Poly describe systems that already exist and run, as opposed to a domain invented to fit the DSL? Each model below is copied from the behaviour of a real system (a compiler pipeline, a CI runner, double-entry bookkeeping, a TTL cache, an IAM directory, a filesystem, an escalation ladder), and then executed.

Every probe in this directory was applied through `poly_define` and exercised through `poly_simulate`. Two are recorded refusals: `*-refused.poly`. The rest apply, check and run.

## What worked

These are not small: they are the core of the platform's claim, and they hold.

| Model | Evidence |
|-------|----------|
| `poly-pipeline.poly` — parse → load → resolve → analyze → lower → produce, with diagnostics as an owned collection | Applies clean. `Clean: policy { count diagnostics where Severity is Error is 0 }` evaluates correctly; `Load: action require Clean` refuses with `Action 'Load' blocked by guards: Clean` when an error diagnostic is linked; the happy path walks every stage. |
| `ledger.poly` — double-entry journal, two-column debit/credit, aggregate invariant | Applies clean. `AddLine` creates postings through an entity-typed parameter; `Balanced: policy { sum postings Debit is sum postings Credit }` evaluates `true` after two lines; `Post` runs under `require Balanced`. An empty journal is balanced. |
| `ci-pipeline.poly` — run/job/step state machines, retry, cancel, skip | Applies and checks clean; transitions are enforced per stage (`Start` is unavailable in `Running`). |
| Requiredness, enum membership, `unique`, rollback of a blocked action | All behave as the guide says; no surprises in these models. |

The rest of this note is what the exercise could not say, in the order it hurt.

## Findings

### F1. A self-referential ownership collection accepts an instance cycle

`filesystem.poly`: `children: many owned Entry`. `poly_check` says `Proven`; then a `link` from an instance to itself succeeds, and `get` reports the node among its own children. `DMDEP002` only covers type-level cycles between different entities, and a self-owning type is legal by design. Nothing establishes that the instances are a tree.

A filesystem, category tree or org chart therefore cannot state its central invariant, and a consumer that walks the collection does not terminate.

→ [#1001](https://github.com/scoizzle/Poly/issues/1001) (new).

### F2. An action named `Add` makes every create fail in the simulator

`filesystem-add-refused.poly` (owned self-collection + `unique` + an action named `Add`): `poly_define` applies clean, then the very first create fails with

```
Failed to create instance: Cannot thread 'Add' through Member in Entry.__Restore.
```

This is #934's shape (`List.Add` mistaken for the threaded action by bare name), but it reaches `poly_simulate`'s create path, not only `polyc build`, and needs no explicit `uses sqlite`. Renaming the action to `Put` makes the same document run.

→ [#934 comment](https://github.com/scoizzle/Poly/issues/934#issuecomment-7052669263).

### F3. No ordered collection, and no ordering operator

`escalation.poly`: `Incident.rungs: many Rung` with `Rung.Level: Number range(1, 5)` applies and checks clean, but nothing can read the lowest rung or the next unacknowledged step. There is no `min`/`max` (#547), no `first`/`last`, no index or position, and quantifiers are order-free. A self-linked list (`next: Step optional`) is writable but not walkable and not acyclic.

→ [#673 comment](https://github.com/scoizzle/Poly/issues/673#issuecomment-7052671026).

### F4. No many-to-many; reciprocal `many` navigations are independent

`access.poly` (`User.roles: many Role`, `Role.users: many User`) applies clean. Link `u1.roles += r1`; then `Role.HasUsers: policy { count users > 0 }` on `r1` is **false**. Declaring `via users` / `via roles` on both sides (`access-paired.poly`) does not change it: `via` only supplies the back-reference at `create in`. The C# export shows the same model as two `List<T>` fields and two `Attach` methods.

The canonical RBAC shape is therefore two disjoint graphs. An author must link both directions and duplicate every policy.

→ [#673 comment](https://github.com/scoizzle/Poly/issues/673#issuecomment-7052671026).

### F5. No derived/computed property

`ExpiresAt` cannot be declared as `CreatedAt + Ttl`; `Account.Balance` cannot be declared as the sum of its postings. Every reader recomputes, and any stored copy can drift. With the per-aggregate invariant limits (#576/#577) there is also no way to state "the stored balance equals the postings".

→ [#673 comment](https://github.com/scoizzle/Poly/issues/673#issuecomment-7052671026).

### F6. Scoped uniqueness is missing, so a hierarchical namespace cannot be modeled

`filesystem.poly`: `Name: Text unique` is global. Two directories cannot each contain `README.md`; the second `Put` fails `Unique constraint violated`. The only authorable model is a globally unique full path maintained by hand, and `key(...)` over a navigation is `DMSTR007`.

→ [#405 comment](https://github.com/scoizzle/Poly/issues/405#issuecomment-7052670116).

### F7. A per-entry TTL is inexpressible

`cache-duration-property-refused.poly`: `assign ExpiresAt to Now + ttl` (a `Duration` parameter) is `DMSEM003` (F-11, #550). `cache-param-count-refused.poly`: `Now + ttlSeconds Seconds` (a `Number` parameter) is `DMSEM006` at define — the parser reads it as a path. Only a literal offset works, so one action per TTL value. Expiry has no end state either: there is no delete effect (#637), so an entry can be marked but never evicted.

→ [#550 comment](https://github.com/scoizzle/Poly/issues/550#issuecomment-7052670414), [#649 comment](https://github.com/scoizzle/Poly/issues/649#issuecomment-7052669561).

### F8. A computed failure cannot fail the action

`poly-pipeline.poly`: with an error diagnostic present, `Lower` transitions to `Failed` and the caller is told

```
Action 'Lower' succeeded. New stage: 'Failed'.
```

There is no effect that fails an action and no postcondition gate; `require` is a precondition, evaluated before the diagnostics exist. A compiler (or a double-booking check) reports success for a refusal, and every caller must sniff the stage afterwards.

→ [#504 comment](https://github.com/scoizzle/Poly/issues/504#issuecomment-7052670715).

### F9. A child in two parents' collections is accepted

`ci-pipeline.poly`: `Job.needs: many Job` is the only way to write a DAG edge, because there is no many-to-many. A diamond links the same job into two parents' `needs`, both links succeed, and nothing reports the aggregate boundary break. Unlike #585's `owned` case this shape is *required* by the domain, so refusing the second owner alone would not be a fix.

→ [#585 comment](https://github.com/scoizzle/Poly/issues/585#issuecomment-7052669829).

## Tooling observations (not filed separately)

- `poly_define(edit:)` reports a parse error in the *spliced document's* coordinates. A three-line snippet whose second line had a comma gave `Parse error: Expected property name, got ',' (line 20, col 41)`. Iterating an edit by line number is hard when the number refers to the whole document.
- `poly_simulate`'s `evaluate` needs `entity` as well as `instanceId` (`Step is missing string 'entity'`), and an `as` alias is not resolved in `invoke` `args` (`Argument 'acct': instance 'cash' of 'Account' not found`). Both are already filed (#609, #500); they cost one round trip each here.
- A create initializer separates properties with whitespace, not commas (`create in postings { account: acct Debit: debit Credit: credit }`). The comma error is positioned and clear; the guide shows no multi-property initializer, which is why it was hit.

## Not covered in this round

Concurrency, the HTTP host's behaviour for these models, and durability are out of scope here; the sim and the printed module were the subject. The models that need those guarantees (ledger, cache) are the ones the existing pack issues (#653, #626, #559) already track.
