## Findings

### F26 — `Now ± N <unit>` mis-evaluates in the policy-eval path: rate limiters never limit on the VM (🔴)
- Signal: silent gap / VM-export divergence. Slice: policy evaluation lowering (RuntimeAnalysisCache/CompileBody) vs action VM.
- Repro: `docs/probes/evolve-2026-10-14/ratelimit.poly`. `ApiKey{ Limit: 3 }` with `OverLimit: policy { count requests where SeenAt > Now - 60 Minutes >= Limit }` and `Allow: action require not OverLimit { create in requests { SeenAt: Now } }`. VM: 5× `Allow` all succeed; `OverLimit` evaluates false. Isolated: bare `Now` folds fine (`SeenAt < Now` → true on a fresh request), `SeenAt > Now + 60 Minutes` → false ✓, but `SeenAt > Now - 60 Minutes` → false ✗ (should be true). Meanwhile `assign WindowStart to Now - 60 Minutes` computes the correct time (10:51 for a 11:51 now) and the exported C# is correct (`item0.SeenAt > DateTime.UtcNow.AddMinutes(-60L)`).
- Expected: `Now ± N Minutes` behaves identically in policies, assign, and export (guide §8: offsets "author, lower, and execute as Add* on that clock value" on the VM).
- Actual: the policy-eval lowering path (used by `evaluate_policy` AND `require` guard evaluation) doesn't fold `DateOperation` correctly — the windowed count is always 0, so `require not OverLimit` never blocks. A rate limiter authored the natural way is a no-op on the VM but works in the exported C#. Also note the previous mission's temporal-policy evals (`Expiry < Today` etc.) were all false-compatible with this bug — worth re-auditing.
- Proposed fix: register the temporal DateOperation lowering in the policy-body compile path (RuntimeAnalysisCache), or share the action-VM lowering config. Add a regression test with a negative offset in a policy body.

### F27 — Subscription handlers fire TWICE for children created via `create in` (regression vs a6203103) (🔴)
- Signal: silent gap / VM regression. Slice: subscription registration in the create-in path.
- Repro: `docs/probes/evolve-2026-10-14/notifications.poly` (and a library-shaped check): one `Reopen` (Snoozed→Unread) → `UnreadBadge +2` and TWO notes from a create-in handler; one `MarkRead` → `SeenCount +2`. Library shape on this master: `CheckOut` (create-in) + one `MarkOverdue` → **2 fines**. The same shape on master `a6203103` (prior mission) produced exactly 1 fine. Children linked via the `link_instances` tool fire once (1 fine).
- Expected: each handler runs once per matching transition (guide §7: "Fires effects for every matching transition (per-element)").
- Actual: create-in children double-register their subscriber, so every subscription handler (assign or create-in body, stage-scoped or entity-level, subscriber with or without stages) executes twice per transition. Badges, counters, fines, and audit-log creates all double. Suspect commits between `a6203103` and `bd416609`: "C8-tc1a: typed by-type create lowering (#162)" / "C8-vm: create-in params (#163)".
- Proposed fix: dedupe subscriber registration in the create-in link path (LinkRelated + registry) or make registries idempotent; add a regression test counting fires per transition for create-in vs tool-linked children.

### F28 — Creating a child INTO a watched stage does not fire subscriptions; only transitions do (🟡)
- Signal: silent gap (documentation absent). Slice: subscription dispatch.
- Repro: `notifications.poly`: `Notify` creates a Notification in its first stage (`Unread`), subscriber has `when notifications Unread { assign UnreadBadge to UnreadBadge + 1 }` → badge stays 0 after any number of `Notify` calls; a later real transition (New→Unread) fires (+2, per F27). Export behaves the same (Create registers subscribers but doesn't dispatch).
- Expected: the guide says subscriptions trigger "when a related entity … enters one of the listed stages"; a create-in lands the child IN that stage, so the unread-badge pattern (the obvious real-app use) expects a fire on creation.
- Actual: creation is not treated as entry; every counter built on "create in watched stage" silently misses the event. Workaround: create in a `New` stage and transition.
- Proposed fix: either dispatch on create-in when the created stage is watched (matching author intuition), or document the transition-only rule explicitly in §7 and add a diagnostic hint when a `when Rel Stage` targets a first stage that children are created into.

### F29 — Entity-level actions bypass stage gating, and stage membership can't guard an action (🟠)
- Signal: modeling trap / silent gap. Slice: action placement semantics.
- Repro: `docs/probes/evolve-2026-10-14/cart.poly`: `AddItem` is entity-level; after `Checkout` moves the cart to `CheckedOut`, `AddItem` still succeeds ("New stage: 'CheckedOut'"). Items can be added to a checked-out cart with no diagnostic, because an entity-level action is available in every stage and there is no `require <stage membership>` expression (stage names are not properties; the previous mission showed `where x in Stage` works only in `for` predicates).
- Expected: the obvious real-app intent — "only while Active" — is expressible, or the trap is visible.
- Actual: the author must move the action into the stage (per-stage copies, which hit F2's duplicate-route shape in the HTTP export) or maintain a mirror Status property. Nothing in analysis flags the always-available action.
- Proposed fix: allow stage-membership predicates in `require` gates (e.g. `require in Active`), or emit an advisory when an entity-level action exists on an entity that has stages.

### F30 — No aggregation (`sum`): derived-field invariants are inexpressible (🟡)
- Signal: surface gap + misleading diagnostics. Slice: expression language.
- Repro: `Cart { Total: Number, lines: many Line }` with `TotalMatches: policy { Total == sum lines Price * Qty }` → rejected: "Relationship name 'sum' is not defined on entity 'Cart'…" + "Policy references property 'Qty' which does not exist on entity 'Cart'." Guide §8 confirms only `any`/`all`/`none`/`count` exist.
- Expected: cart/ledger-style invariants ("Total equals the sum of line prices×qty") need an aggregate; at minimum the rejection should say aggregations aren't supported.
- Actual: every real-app domain with a total, balance, or subtotal must hand-maintain arithmetic bookkeeping that can silently drift (nothing can assert consistency). The error misreads `sum` as a relationship name.
- Proposed fix: ship a `sum Rel [where …] Prop` aggregate (or fold it into `count`-style lowering), and make the parse error say "aggregate not supported".

### F31 — DateTime-typed `Now ± N Minutes` in a create initializer is rejected by the VM (🟠)
- Signal: fail-loud VM rejection / VM-export divergence. Slice: VM compiler type analysis.
- Repro: `docs/probes/evolve-2026-10-14/sessions.poly` v1: `Login: action { create in sessions { Token: Guid ExpiresAt: Now + 30 Minutes } }` → invoke fails: `VM compile rejected: cannot tell whether argument 'DateTime.UtcNow.AddMinutes(30)' is a scalar or a reference.` The export emits `CreateSessions(DateTime.UtcNow.AddMinutes(30L), …)` correctly; `assign ExpiresAt to Now + 30 Minutes` works on the VM (12:07→12:37 ✓), and DateOnly initializers (`Today + 14 Days`, mission 1) work.
- Expected: DateOperation initializers behave like assigns for every temporal family (guide §8 claims offsets "author, lower, and execute").
- Actual: DateTime-family DateOperation in create-initializer position can't be typed by the VM compiler (scalar-vs-reference ambiguity for the CLR DateTime argument); only the initializer position breaks.
- Proposed fix: teach the VM compiler the DateTime argument is a scalar in create initializer bindings (same resolution as the assign path).

### F32 — `create_instance` stores JSON values un-coerced: ISO date strings stay Strings and break typed policy comparisons (🟠)
- Signal: fail-loud-but-sharp / tool-boundary coercion gap. Slice: MCP create_instance → store.
- Repro: `sessions.poly`: `create_instance(Session, {"ExpiresAt":"2026-10-13T10:00:00Z"})` stores `ExpiresAt` as a **string**; `evaluate_policy(IsExpired)` (`ExpiresAt < Now`) then fails: `Cannot compare values of different runtime types: 'String' vs 'DateTime'.` (Mission 1's F15 — 0.25 → 0 truncation — is the Number face of the same gap.)
- Expected: the tool boundary coerces JSON values to the property's declared type (or rejects mismatches), as `invoke_action` args apparently do.
- Actual: raw JSON values land in the store; every typed comparison/effect on those properties blows up later. The export's typed factories don't have this hole (hosts pass CLR values).
- Proposed fix: apply the declared property type coercion in `create_instance` (same path as action-arg coercion), and/or store `DomainEntityInstance` values with runtime-type validation against the catalog type.

### F33 — `add(relationship, ManyToMany)` works but M:N is inexpressible in DSL; `export_dsl` silently degrades it to `many` (🟠)
- Signal: silent gap / round-trip cardinality loss. Slice: dual authoring path (§12) vs DSL printer.
- Repro: `add(kind: relationship, {"name":"OrderItems","source":"Order","target":"Item","cardinality":"ManyToMany"})` succeeds; analysis 0 errors; `link_instances` across the M:N works on the VM. `export_dsl` prints `OrderItems: many Item` — re-applying that text produces a OneToMany. `get_relationships` still reports ManyToMany (session-only truth). The DslCompiler can never see the M:N shape (DSL has no syntax for it).
- Expected: guide §12 offers ManyToMany for "when you need other cardinalities" — the exported DSL should preserve it or refuse to export it.
- Actual: cardinality is silently lost on round-trip; a session-authored M:N becomes N1 with no warning.
- Proposed fix: either print an M:N DSL form (and teach the parser), or fail the export with a "ManyToMany not expressible in DSL" error instead of degrading.

## Weirdness log

- **notifications:** stage-scoped placement semantics verified: fires while subscriber is in the stage, silent while Away, resumes after ComeBack — correct apart from F27's double-fire.
- **notifications:** dispatch pipeline is re-entrant-shaped (`Store.NotifyTransition` → compiled Notify → `DEI.Notify` → `Store.NotifyTransition`), bounded by `MaxNotifyDepth = 16` — worth an audit alongside F27.
- **cart:** `many owned` parses, analyzes, runs, and exports 0/0, but the DbContext gives it no special treatment (plain convention FK) — consistent with the guide's "ownership is a modeling flag" statement. Verified-as-documented.
- **cart:** entity-level `AddItem` ran fine while CheckedOut (see F29); manual `Total`/`ItemCount` bookkeeping worked (100×2+50×1 = 250 ✓) but nothing can assert it against the lines (F30).
- **sessions:** `Token: Guid` in a create initializer generates a real GUID on the VM and `Guid.NewGuid().ToString()` in the export — shipped. `default(Now)` applied at create. Export `Login` is correct while the VM rejects the DateTime initializer (F31).
- **authoring path (§12):** incremental `add` works for entity/property/stage/stage_action/relationship/constraint/policy; unknown kinds fail closed with the full kind list; `remove property` rolls back transactionally when a policy references it (diagnostic printed twice); `remove constraint` is honestly unimplemented (documented). `describe_domain_element` gives plain-English + structured expression. `oracle_expression` works but arithmetic inference misfires (`Total * 2 > 10` with `{"Total":7}` → "arithmetic operand is not numeric (got 'Text' and 'Number')").
