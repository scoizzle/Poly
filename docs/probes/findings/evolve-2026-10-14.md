## Findings

### F26 — `Now ± N <unit>` mis-evaluates in the policy-eval path: rate limiters never limit on the VM (🔴)
- Signal: silent gap / VM-export divergence. Slice: policy evaluation lowering (RuntimeAnalysisCache/CompileBody) vs action VM.
- Repro: `docs/probes/evolve-2026-10-14/ratelimit.poly`. `ApiKey{ Limit: 3 }` with `OverLimit: policy { count requests where SeenAt > Now - 60 Minutes >= Limit }` and `Allow: action require not OverLimit { create in requests { SeenAt: Now } }`. VM: 5× `Allow` all succeed; `OverLimit` evaluates false. Isolated: bare `Now` folds fine (`SeenAt < Now` → true on a fresh request), `SeenAt > Now + 60 Minutes` → false ✓, but `SeenAt > Now - 60 Minutes` → false ✗ (should be true). Meanwhile `assign WindowStart to Now - 60 Minutes` computes the correct time (10:51 for a 11:51 now) and the exported C# is correct (`item0.SeenAt > DateTime.UtcNow.AddMinutes(-60L)`).
- Expected: `Now ± N Minutes` behaves identically in policies, assign, and export (guide §8: offsets "author, lower, and execute as Add* on that clock value" on the VM).
- Actual: the policy-eval lowering path (used by `evaluate_policy` AND `require` guard evaluation) doesn't fold `DateOperation` correctly — the windowed count is always 0, so `require not OverLimit` never blocks. A rate limiter authored the natural way is a no-op on the VM but works in the exported C#. Also note the previous mission's temporal-policy evals (`Expiry < Today` etc.) were all false-compatible with this bug — worth re-auditing.
- Proposed fix: register the temporal DateOperation lowering in the policy-body compile path (RuntimeAnalysisCache), or share the action-VM lowering config. Add a regression test with a negative offset in a policy body.

### F27 — Subscription handlers fire TWICE for children created via `create in` (regression vs a6203103) (🔴)
- Signal: silent gap / VM regression. Slice: subscription registration in the create-in path.
- Repro: `docs/probes/evolve-2026-10-14/notifications.poly` (and a library-shaped check): one `Reopen` (Snoozed→Unread) → `UnreadBadge +2` and TWO notes from a create-in handler; one `MarkRead` → `SeenCount +2`. Library shape on this master: `CheckOut` (create-in) + one `MarkOverdue` → **2 fines**. The same shape on master `a6203103` (prior mission) produced exactly 1 fine. Children linked via the `link_instances` tool fire once (1 fine).
- Expected: each handler runs once per matching transition (guide §7: "Fires effects for every matching transition (per-element)").
- Actual: create-in children double-register their subscriber, so every subscription handler (assign or create-in body, stage-scoped or entity-level, subscriber with or without stages) executes twice per transition. Badges, counters, fines, and audit-log creates all double. Suspect commits between `a6203103` and `bd416609`: "C8-tc1a: typed by-type create lowering (#162)" / "C8-vm: create-in params (#163)".
- Proposed fix: dedupe subscriber registration in the create-in link path (LinkRelated + registry) or make registries idempotent; add a regression test counting fires per transition for create-in vs tool-linked children.

### F28 — Creating a child INTO a watched stage does not fire subscriptions; only transitions do (🟡)
- Signal: silent gap (documentation absent). Slice: subscription dispatch.
- Repro: `notifications.poly`: `Notify` creates a Notification in its first stage (`Unread`), subscriber has `when notifications Unread { assign UnreadBadge to UnreadBadge + 1 }` → badge stays 0 after any number of `Notify` calls; a later real transition (New→Unread) fires (+2, per F27). Export behaves the same (Create registers subscribers but doesn't dispatch).
- Expected: the guide says subscriptions trigger "when a related entity … enters one of the listed stages"; a create-in lands the child IN that stage, so the unread-badge pattern (the obvious real-app use) expects a fire on creation.
- Actual: creation is not treated as entry; every counter built on "create in watched stage" silently misses the event. Workaround: create in a `New` stage and transition.
- Proposed fix: either dispatch on create-in when the created stage is watched (matching author intuition), or document the transition-only rule explicitly in §7 and add a diagnostic hint when a `when Rel Stage` targets a first stage that children are created into.
