## Findings

### F26 — `Now ± N <unit>` mis-evaluates in the policy-eval path: rate limiters never limit on the VM (🔴)
- Signal: silent gap / VM-export divergence. Slice: policy evaluation lowering (RuntimeAnalysisCache/CompileBody) vs action VM.
- Repro: `docs/probes/evolve-2026-10-14/ratelimit.poly`. `ApiKey{ Limit: 3 }` with `OverLimit: policy { count requests where SeenAt > Now - 60 Minutes >= Limit }` and `Allow: action require not OverLimit { create in requests { SeenAt: Now } }`. VM: 5× `Allow` all succeed; `OverLimit` evaluates false. Isolated: bare `Now` folds fine (`SeenAt < Now` → true on a fresh request), `SeenAt > Now + 60 Minutes` → false ✓, but `SeenAt > Now - 60 Minutes` → false ✗ (should be true). Meanwhile `assign WindowStart to Now - 60 Minutes` computes the correct time (10:51 for a 11:51 now) and the exported C# is correct (`item0.SeenAt > DateTime.UtcNow.AddMinutes(-60L)`).
- Expected: `Now ± N Minutes` behaves identically in policies, assign, and export (guide §8: offsets "author, lower, and execute as Add* on that clock value" on the VM).
- Actual: the policy-eval lowering path (used by `evaluate_policy` AND `require` guard evaluation) doesn't fold `DateOperation` correctly — the windowed count is always 0, so `require not OverLimit` never blocks. A rate limiter authored the natural way is a no-op on the VM but works in the exported C#. Also note the previous mission's temporal-policy evals (`Expiry < Today` etc.) were all false-compatible with this bug — worth re-auditing.
- Proposed fix: register the temporal DateOperation lowering in the policy-body compile path (RuntimeAnalysisCache), or share the action-VM lowering config. Add a regression test with a negative offset in a policy body.
