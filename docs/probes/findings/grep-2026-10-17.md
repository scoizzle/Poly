# Findings — grep domain probe 2026-10-17

Baseline: `origin/master` `b40e694b` (`docs(board): record async/await slices A1 and A2 merged (#207)`).

**Method:** author `docs/probes/grep-2026-10-17/grep.poly` → `apply_dsl` → `get_domain_analysis`
→ VM walk (`create_instance` / `invoke_action`; three queries — exact match, zero match, inverted —
over one three-line and two two-line sources) → `export_dsl` round-trip → `scripts/run-probe.sh`
(`--mode all --dbms sqlite --http`) → emitted-host build. Then ~35 single-spelling probes on
scratch MCP sessions to map the expression surface grep's kernel needs, plus a comparison of the
candidate shapes for the scan loop.

**Question:** model a real, complex, well-understood tool (grep) and measure how far the domain
model compilation is from a working version of that tool.

**Status:** ✅ the domain compiles, runs on the interpreter, and emits a host that builds 0/0.
It implements `grep -F -x` and `-v`, and it reports "no matches" instead of failing. It cannot
implement grep, because it cannot test a line for *containing* a pattern — and a `for` over an
*empty* set still fails, so an empty file or an empty query has no valid run.

Severity: 🔴 blocks the deliverable (a working grep) or is a real defect · 🟠 significant ·
🟡 gap, trap or DX · 🟢 cosmetic · (note) information, not a defect.

---

## 1. The answer in one paragraph

The compilation gives you the whole **shell** of a grep-like tool — the record shapes (query,
source, line, hit), the lifecycle (`Prepared → Scanned → Reported`), the option surface, per-file
and whole-query counts, stage-gated action endpoints, constraint-checked create factories,
subscription wiring, a database schema, and 1029 lines of emitted C#/SQL/host across 8 files that
build clean — and **none of the text semantics**. The shipped model decides `Content is needle`
(whole-value equality, with the needle threaded from the query down to the line as an action
parameter), and that is `grep -F -x`. Three things are missing from the language, and only the
first is about grep as such:

1. **a text predicate** — no `contains`/`startsWith`/`endsWith`, no regex, no case fold, no length,
   no extraction. The guide itself concedes this ("Grep-style read-time matching against stored text
   is not expressible", §8), so the model can be a schema for a grep-like tool but not grep.
2. **a scalar result** — no exit status; the outcome exists only as a stage.
3. **an input door** — no argv/file/stdin; the caller (or the host) creates every source and every
   line.

Plus **one semantics limitation, fixed while this pass was reviewed**: a `for` over an **empty** set
used to fail, so an empty file (or a query with no sources) had no successful run. That is G3; it is
fixed on branch `fix/for-empty-set` (`a965d287`) — zero records is a no-op, and the analysis warning
(DMREL002) stays as the modelling-side signal.

So the honest distance is small in *shape* and absolute in *kernel*: the model is a bookkeeping
layer, the matcher is the host's job, and of the five gaps my first pass reported, two turned out to
be my modelling, not the language's (§5, G2/G3).

## 4. The distance, in gaps

Three gaps, in descending value:

1. **A text predicate** (G1) — `contains`/`startsWith`/`endsWith` plus a case fold turn this model
   from "a schema for grep" into "grep". Everything else about the probe's shape already works.
2. **A scalar result** (G4) — an exit status (or a matched span). Today the outcome is a stage and
   the caller maps stage → process code. Diagnosed: the *print* path already supports it, the
   analyzer rejects it and the interpreter has no value slot (§5, G4).
3. **An input door** (G5) — argv/files/stdin, or the host supplying lines. Today every line is
   created by hand.

Two things that *looked* like gaps and were not:

- a predicate-filtered `for` failing when nothing matched, and a `for` over an empty collection —
  both were the same zero-target check; **fixed** 2026-10-17 as G3;
- the pattern having to be copied onto every line — a consequence of my first draft's choice to
  filter in the `for` predicate rather than guard in the callee (G2).

## 5. Findings

### G1 🔴 — There is no text predicate in any spelling
- **Repro:** `Test: policy { <expr> }` with `Haystack: Text`, `Needle: Text`. Every spelling of
  "does Haystack contain Needle" is rejected: `contains`/`startsWith`/`matches`/`like` →
  `Relationship name 'Haystack' is not defined on entity 'Line'. Declare a navigation property…`;
  `matches(Haystack, Needle)` / `lower(Haystack)` / `substring(Haystack, 0, 2)` → `Parse error:
  Expected RBrace, got '(' (LParen)`; `Haystack.ToLower()` → `Expected RBrace, got '.' (Dot)`;
  `length(Haystack)` → `Expected expression, got 'length'`; `Haystack in Needle` → `Expected
  RBrace, got 'in' (In)`.
- **Actual:** the expression surface for `Text` is `is` / `is not` / `==` / `!=` (whole value),
  `+` (concatenation, G10), and `>`/`<` (G7). `pattern(regex)` is a write-time constraint on a
  stored value (guide §8), not a read-time filter, so it cannot select lines.
- **Impact:** the shipped probe's only predicate is whole-value equality, so `grep alpha` misses
  `alpha beta` — the walk shows exactly that (1 hit from 3 lines, and the substring line is the one
  that is missed). The guide says so itself: "Grep-style read-time matching against stored text is
  not expressible."

### G2 🟡 — A `for` predicate cannot read a relationship (the first draft's denormalization was avoidable)
- **Failing shape:** `Matches: policy { query PatternText is Content }` on `Line`, used as
  `for lines as line where line Matches invoke line.Mark` →
  `Evolution rolled back: ForEachInvoke predicate policy 'Matches' reads a path-prefix hop; an
  unlinked hop simulates false but the export dereferences null. Use a local policy over the
  record's own properties.` (Without the back-reference on `Line` it also reports `Path-prefix
  expressions must be on the source entity of the relationship.`)
- **My first draft** therefore stored `PatternText: Text required` on **every `Line`** and made the
  caller copy the query's pattern into each `LoadLine` — a join the analyser has to guess at, which
  is the behaviour guide §0.1 warns against in the related case of an identifier standing in for a
  navigation (`BookIsbn: Text`). That shape compiles, runs, and counts correctly; I shipped it
  before checking the alternative.
- **Working shape (what the probe ships):** the pattern travels as an action parameter and the
  decision moves into the callee:
  `Query.Scan: for sources as src invoke src.Scan(needle: PatternText)` →
  `Source.Scan: for lines as line invoke line.Check(needle: needle)` →
  `Line.Check: if (Content is needle) { transition to Marked }`. No denormalization, no hop read in
  a predicate. Verified end to end.
- **Residual (fair to keep as a 🟡):** a *predicate* still cannot read a hop, so any filtering done
  in the `for` (rather than in the callee's `if`) must be over the record's own properties, and the
  error text an author meets first says "reads a path-prefix hop" without naming the parameterized
  alternative.

### G3 ✅ — Zero records is a no-op (fixed 2026-10-17)
- **What it was.** One check, two symptoms, both from `EffectLoweringPass.ForEachInvoke`: the loop
  body set a `matched` flag and a zero-check failed the whole action with
  `for {rel}.{action} matched zero targets.` whenever the body ran zero times — whether the
  collection was **empty** (a source with 0 lines, a query with 0 sources) or a **predicate matched
  nothing** (`for lines as line where line Matches invoke …`). The action failed, the enclosing
  `for` failed by fail-fast propagation, and the caller could not distinguish "nothing to do" from
  "failed". `grep x empty.txt` is an ordinary no-match in real grep; here it was unrecoverable.
- **Decision (Scot, 2026-10-17):** both cases become a no-op — the body runs per matching record, and
  no matching records is not an error.
- **Fix:** branch `fix/for-empty-set` off `master` (`a965d287` plus its review-fix follow-ups):
  `ForEachInvoke` emits only the fail-fast loop. The first failing record still fails the whole `for`
  and returns the caller's result. Guide §6 and `docs/interpretation/domain-execution-model.md`
  updated in the same change.
  DMREL002 — the analysis warning for a collection nothing writes — is untouched, so the *modelling*
  error is still reported; the runtime just no longer turns it into a failure.
- **Evidence:** `ForEachInvoke_ZeroTargets_Throws` (which pinned the old failure) is **replaced** by
  two interpreter tests — empty collection, and a predicate that matches nothing — each asserting the
  action succeeds **and** the effect after the loop runs; the exporter tests pin the absence of the
  failure return; four goldens regenerated; and the university dogfood walk (`DropAllRegistered` /
  `CompletePassing` with nothing to do) flipped to success. Suite green: 3942 tests on clean
  `master` → 3943 (one test removed, two added).
- **Left over (recorded, not fixed):** a *failure return* inside a `when` body — `for` **and**
  plain `invoke` — is accepted by analysis and emits `return DomainResult.Failure(...)` into a `void`
  handler → **CS0127**; see
  [`2026-10-17-failure-return-in-void-subscription-handler.md`](../../plans/poly-eng/research/2026-10-17-failure-return-in-void-subscription-handler.md).
  Pre-existing on `master`; the empty-set slice removes one of its four `for` returns, not the hazard.

### G4 🟠 — No scalar return: not a broken check, an unfinished narrowing (diagnosed 2026-10-17)
- **Repro:** `Cmp: action (other: Text) -> Boolean { … }` → `Evolution rolled back: Action 'Cmp'
  declares return type 'Boolean', but only entity returns produced by create / create-in are
  supported on the product path.` Same for `Number` and `Text`.
- **Where the restriction lives:** `EffectAnalyzer.ValidateActionReturnProducer` reports it whenever
  the declared result type is a known type that is not an `Entity` (DMEFF009).
- **What a spike showed** (relax that one check, then run a domain through the pipeline; the spike was
  reverted):
  - the **print path already works** — `Compute: action -> Number { assign Discount to Total * 2 }`
    emits `public DomainResult<long> Compute() { … return DomainResult<long>.Success(this.Discount); }`
    and the whole export **compiles 0 errors / 0 warnings** (same for `-> Text` →
    `DomainResult<string>`). The emitter is type-generic (`MapDomainTypeRef`) and already implements
    last-effect-as-return, including `Assignment` → `Success(destination)` and a `NotSupportedException`
    fallback whose message tells the author to "use an 'assign' statement as the final effect";
  - the **interpreter is instance-only** — the same action *runs* (`Discount` = 42) but the result is
    projected as a **failure**: `ok=False … "declared return type 'Number' but no create/create-in
    produced an instance of that type during this invoke"`, because `DomainEntityInstance` finds the
    result among `_createdChildren` of the declared type. The MCP surface derives from that
    (`returnInstanceId`), so it would report failure and no value.
- **Verdict:** the *check* is the only obstacle on the print path, and its message is factually wrong
  there — so "sounds like a bug" is right in spirit; but it is not a one-line deletion. The remaining
  slice is: extend DMEFF010 (final statement must produce the value) past its non-entity early-return
  so a scalar return requires a final `assign` of the right type; give the interpreter's result a
  value slot (the last assigned value) and project it in the MCP result; update guide §6, which
  currently says primitive returns are "not product". Recorded for the CLI/exit-status scope note
  ([`2026-10-17-cli-host-library-scope.md`](../../plans/poly-eng/research/2026-10-17-cli-host-library-scope.md), D2).

### G5 🟠 — No input door: the caller creates every source and every line
- **Observed:** seven calls per query to build and run it (`create_instance`, `AddSource`,
  3 × `LoadLine`, `Scan`, `Report`) plus reads. The emitted HTTP host is the same shape: `POST
  /api/queries/{id}/sources/{sourceId}/loadline` per line.
- **Impact:** there is no argv, no file/stdin read, and no bulk load, so the "grep" is a data-entry
  API. The host must read the files and post the lines — which is also why the matcher ends up in
  the host (G1, G11).

### G6 🔴 — A property named like a primitive type (`Text`, `Number`, `Boolean`) is declared but can never be read
- **Repro A (policy):**
  `Thing: entity { Number: Number required  Big: policy { Number > 3 } }` (two members on one line
  for brevity) → `Parse error: Expected expression, got 'Number'`. Identical for `Text` and
  `Boolean`, and for a comparison against another property (`Number is Other`).
- **Repro B (peer read):** `assign Count to kid Number` → `Parse error: Expected effect
  (transition, assign, create, invoke, for, if), got 'Number'`.
- **Repro C (create initializer):** in the probe's first draft (`Line.Number`,
  `Hit.LineNumber: (l Number) …`) the parse succeeded with parentheses and the failure moved to
  analysis as `'l' is not a property, parameter, or enum member` — an error naming the **binder**,
  not the property. Without the parentheses it was `Parse error: Expected Colon, got 'Content'`,
  also not naming the cause.
- **Expected:** either reject the declaration ("a property may not be named after a primitive
  type") or resolve it. The declaration is accepted by analysis, so the model looks healthy until
  something reads it.
- **Impact for grep:** `Line.Number` is the natural name for `-n`; the probe uses `LineNo`. Same
  family as the 2026-10-14 finding S10 (`policy`/`stage`/`when` as member names).

### G7 🔴 — A `Text > Text` comparison is accepted, runs on the VM, and prints C# that does not compile
- **Repro:** `Greater: policy { Haystack > Needle }`, then `scripts/run-probe.sh`.
- **Actual:** analysis accepts it (0 errors); the VM evaluates it (`Policy failed (false)` for
  `"a" > "b"`); the printed C# is `public bool Greater() => this.Haystack > this.Needle;` →
  `error CS0019: Operator '>' cannot be applied to operands of type 'string' and 'string'`. The
  emitted host does not build.
- **Expected:** the guide (§8) says "Expressions are type-checked at analysis. Wrong-typed
  comparisons … are rejected at authoring time". `<`/`<=`/`>`/`>=` on two `Text` properties is the
  counterexample; `==`/`!=` on `Text` is correct, so the check is operator-specific.
- **Bonus:** a VM-vs-print divergence — the class of bug the frozen-core rule says to fix in Lower.

### G8 🟠 — A plain `many` collection declares no composition, and nothing says so
- **Repro (control):** `Root: entity { kids: many Kid }` + `Kid: entity { … }` →
  `roots=[Root, Kid]`, `aggregates Root:[] Kid:[]`.
- **Repro (fixed):** the same domain with `kids: many owned Kid` (or with `Kid.root: Root`) →
  `roots=[Root]`, `aggregates Root:[Kid]`.
- **Impact:** the first grep draft used plain `many` navs, so all four entities became roots and the
  emitted API flattened to sibling top-level routes, with **0 errors / 0 warnings** and no hint that
  ownership was missing. (The probe's `owned` navs give the nested form the report quotes in §2.)
- **The 2026-10-14 recommendation omits the load-bearing part.** That pass's note lists the good
  shape as "each child owned by exactly one root through a collection; the root has **no** singular
  nav". Re-applied on `b40e694b`, roastery reports the facts the note recorded
  (`roots=[Bean, Order]`, `Bean:[Batch] Order:[Line]`, 0 errors) — but roastery's children carry
  singular back-references (`Batch.bean: Bean`, `Line.order: Order`), which is what the control
  above shows to be the actual ownership trigger. The recommendation as written describes the shape
  that yields all-roots.
- **Also:** `owned` is a *prefix* modifier (`kids: many owned Kid`); `kids: many Kid owned` is a
  parse error with no hint (`Expected property, stage, action, or policy, got 'owned'`).

### G9 🟡 — An unsupported infix operator is diagnosed as a missing navigation property
- `Haystack contains Needle` → `Relationship name 'Haystack' is not defined on entity 'Line'.
  Declare a navigation property (e.g. 'Haystack: TargetEntity') on this entity first.`
- The parser reads the unknown word as a path-prefix read (`Rel Prop`), so a missing *string
  operator* is reported as a missing *relationship*. `startsWith`, `matches` and `like` behave the
  same. This is the message an author meets first when they write the obvious thing, and it points
  at the model instead of at the language.

### G10 🟡 — `Text + Text` is string concatenation on both paths, and the guide does not say so
- `Plus: policy { Haystack + Needle is "ab" }` → VM `Policy passed (true)`, printed
  `this.Haystack + this.Needle == "ab"`.
- The guide's shipped list says "Arithmetic (`+`, `-`, `*`, `/`) in expressions" with no type
  qualifier. So the language has exactly one string operation: text *construction*, with no text
  *inspection*.

### G11 🟡 — The contract seam is fail-closed and not extensible, and it conveys only success/failure
- **Probed:** a `contract external` + `bind` domain emits
  `public static DomainResult Match(MatchRequest request) => DomainResult.Failure("Contract endpoint
  'Regex.Match' has no in-process adapter.");` inside a `RegexAdapters` class that is **static, with
  a private constructor and no partial or registration seam** — `git grep` for a registration API
  finds none. The bound action receives only `adapterResult.IsSuccess`, so an endpoint cannot hand a
  *value* (a verdict, a span) back into the model; the body can only proceed or fail closed.
- **Consequence for the escape hatch:** "put the matcher behind a contract" is not available — the
  matcher cannot be injected, and even if it could, the model could not receive its answer. So a
  real grep has to live in the host and drive the model. (Guide §2 and the 2026-10-14 S15 finding
  agree on the fail-closed part; the *extensibility* part is what this probe adds.)

### G12 🟢 — Two spelling traps
- `not Haystack is Needle` → `Parse error: Expected RBrace, got 'is' (Is)`; the working spelling is
  `Haystack is not Needle` (accepted; the probe's `Skew` uses it).
- `pattern` is a reserved word in a parameter position: `LoadLine: action (…, pattern: Text)` →
  `Parse error: Expected parameter name, got 'pattern'` (the `pattern(...)` constraint keyword).

### G13 (note) — The VM analyzer reports 7 errors on a domain that analyses clean, runs, and builds
- Every one of the 7 is `no matching member 'Success' on 'DomainResult' for invoke with 1
  argument(s)`: the lowered VM trees call the generic `DomainResult.Success(value)` while the VM's
  `DomainResult` type-def declares only the parameterless overload. Emit stays fail-open
  (`ThrowIfVmHasErrors` has no product call site), so the export and the host are unaffected.
- Recorded because it bounds what "the pipeline is green" means. The other 22 pre-existing samples
  all report VM Errors too (their messages were not inspected in this pass), and
  `VmAnalyzerReportTests` enshrines **zero VM-clean samples** — a parked nit (board `#128`). A
  VM-clean result is not reachable here, so the VM analyzer is not a correctness signal for a new
  domain: the probe is one of the errors in a canary that asserts every sample has one.

## 6. Positives (exercised)

- **The full path works for a domain of this shape:** `apply_dsl` → 0-error analysis → the three VM
  walks → clean `export_dsl` round-trip → `--mode all --dbms sqlite --http` export → host build 0/0
  in ~2s.
- **The pattern threads from the query to the line without denormalization:**
  `for sources as src invoke src.Scan(needle: PatternText)` → `for lines as line invoke
  line.Check(needle: needle)` → `if (Content is needle)`. No line-level copy of the pattern.
- **A guard in the callee makes a no-match run an ordinary result:** the no-match query ran `Scan`
  and `Report` to completion with `TotalHits=0`. **A `for` over zero records is now a no-op**
  (`a965d287`), so the probe's two empty-set cases (a source with 0 lines, a query with 0 sources)
  are covered by that fix's tests — the same shape the walk measured as a failure.
- **An option can drive the model:** `Query.Scan` branches on `Invert is true` and dispatches to
  `Source.ScanInverted`; the `Invert=true` walk found the one non-matching line. So the option
  surface is not decorative — it is readable and usable.
- **`sum Rel Prop` works end to end:** `TotalHits` = `sum sources HitCount` = 1, and the per-source
  `HitCount` agreed with the walk (1, 0, 1 across the queries that ran).
- **Stage gating is real:** after `Report` the query is `Reported` and `AddSource` reports
  `Action 'AddSource' exists on entity 'Query' but is only available in stage 'Prepared'.`
- **Peer-binder subscriptions and `owned` compose:** `when lines Marked as found { create in hits
  { LineNumber: (found LineNo) Content: (found Content) } … }` produced exactly one `Hit` from
  three lines, and `roots=[Query]` / `Query:[Hit,Line,Source]` is correct.
- **The option surface is a local-property policy away:** `Content is PatternText and IgnoreCase is
  false and MaxCount > 0` was probed on a scratch entity that carries all four, and applies cleanly
  — a future text operator could read the flags. In the shipped probe the flags live on `Query`,
  which the line cannot read, so `IgnoreCase`, `MaxCount` and `MatchMode` are declared and read by
  nothing (placeholders for the missing operators).

## 7. Repo/test-contract notes (for whoever lands this as a probe)

- Adding a `.poly` under `docs/probes/` enrolls it in tests that auto-enumerate the tree
  (`VmAnalyzerReportTests`, `ParityTests`, and the report-only `CascadingErrorReportTests`,
  `DiagnosticElementGapTests`, `EveryConceptHasTreeTests`). Two explicit pins matter:
  `VmAnalyzerReportTests` holds **exact-set** lists — `VmErrorSamples` for a probe whose VM analysis
  has Errors, `DomainErrorSamples` for one the domain analyzer rejects — and it requires every
  sample to be in one of them (no VM-clean sample); and any probe named in a test's `InvalidProbes`
  is matched by **file name only**, in three tests (`VmAnalyzerReportTests:26`,
  `EveryConceptHasTreeTests:16`, `ParityTests:1042`). The grep probe has **VM Errors** (7), clean
  domain analysis, and printable C#, so it took a `VmErrorSamples` row and nothing else.
- `restaurant.poly` moved because it now fails **domain** analysis (T5 / `#205`, DMSTR006), which is
  what put it into `DomainErrorSamples` (its `InvalidProbes` entry is the display label). That is why
  the pre-existing "23" comment read as 22 samples until this row made it 23 again.
- The probe `uses http`, so `scripts/run-probe.sh` takes its full host-build branch.
- **One emitter observation** (not chased): with `owned` navs the root nests its children
