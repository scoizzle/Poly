## S1 — `get_domain_analysis` never returns on the canonical parent/child back-reference shape (🔴)

- Signal: tool hang (the harness aborts the call; no error from the server). Slice: MCP
  facts walk + ownership-aggregate pass.
- Repro: `apply_dsl` the gym domain (any domain with `A.children: many B` + `B.a: A`),
  then call `get_domain_analysis`. The call spins and is aborted. `export_dsl`,
  `create_instance`, `invoke_action`, `evaluate_policy` all still work. The CLI
  (`Poly.DslCompiler --mode all --http --dbms sqlite gym.poly`) completes, so
  **analyze itself is fine** — only the MCP facts walk spins.
- Root cause: `Poly.Mcp/Tools/DomainTools.cs:332-338` walks the aggregate parent chain
  with no visited set:
  `cursor = aggregateByName.GetValueOrDefault(cursor.AggregateParentName)`.
  `OwnershipAggregatePass.ResolveChild` (`Poly/DomainModeling/Analysis/OwnershipAggregatePass.cs:143-151`)
  makes an entity's aggregate parent the **source of an inbound singular nav**. For
  `Member.bookings: many Booking` + `Booking.member: Member`, the collection edge gives
  `Booking.parent = Member` while the singular fallback gives `Member.parent = Booking`
  → a two-node cycle (`Trainer ⇄ ClassSession` likewise). The walk then never reaches
  any root and loops forever.
- Introduced by the mission merge (#173/#176): the walk is new in that range, so every
  probe domain from the last round would hang the tool today.
- Proposed fix: visited-set guard in the walk (and cycle detection where the aggregate is
  built, or make the singular fallback not point "up" into a collection owner).

## S5 — a peer-side subscription/quantifier silently misses a child created under another owner (🔴)

- Signal: silent wrong behavior (no diagnostic). Slice: runtime linking / `create in` semantics.
- Repro: one Member, one ClassSession, then `Reserve(who: member)` which runs
  `create in bookings { member: who }`. Then have the Booking `Attend`:
  - `ClassSession` subscription fires → `AttendedCount = 1` ✅
  - `Member` subscription (`when bookings Attended { assign Visits to Visits + 1 }`) does

    `for bookings.Drop matched zero targets.` even though a `Booked` Booking exists ⛔

  ClassSession) silently loses one parent's whole subscription/quantifier surface.

## S10 — a member named for a DSL keyword is unparseable, with no reserved-word hint (🟡)

- Repro: `Claim: entity { … policy: Policy … }` — the most natural name in an insurance domain —
  is rejected:
  `Compilation failed: Parse error: Expected property, stage, action, or policy, got 'policy' (line 54, col 9)`.
- The *entity* named `Policy` is fine (capitalized); only a lowercase member name collides, because
  `DslTokenReader.WordToKind` maps `policy`/`stage`/`entity`/`action`/`when`/`require`/`assign`/`to`/… to
  keyword token kinds.
- Expected: the message says the word is reserved (F18/F19 already treat `Text`/C# keywords
  specially), or the DSL offers an escape.
- Workaround used: renamed the nav to `cover: Policy`.

## S11 — a collection nav whose PascalCase name equals its target entity name shadows the type (🔴)

- Repro: `Claim: entity { evidence: many Evidence  Attach: action (kind: Text) -> Evidence { create in evidence { Kind: kind } } }`.
- Generated `Claim.cs` declares the collection property `Evidence` and then, inside the same class:
  `var evidenceResult = Evidence.Create(kind, this);` — which binds to the **property**
  (`IReadOnlyList<Evidence>`) instead of the entity type `Evidence`.
- Errors: entities gate → `CS1061: 'IReadOnlyList<Evidence>' does not contain a definition for 'Create'`;

- Expected: the factory references the target type unambiguously (qualified name or local alias).
- Workaround used: entity renamed to `Document`, nav `documents`.

## S12 — a second collection nav to the same child is silently empty (🟠)

## S14 — a subscription does not fire when the child is *created into* the watched stage (🟠)

- Isolated probe: `Parent { Ticks: Number default(0)  kids: many Kid  Add: action (name: Text) -> Kid { create in kids { Name: name } }  when kids Fresh { assign Ticks to Ticks + 1 }  when kids Moved { assign Ticks to Ticks + 10 } }`

- Observed: `Add` → `Ticks = 0` (no firing); then `Kid.Move` → `Moved` → `Ticks = 10` ✅.

  documented contract, and it is silent (no diagnostic; the effects simply do not run).

## S15 — a bound action renders its target stage (and its subscriptions) unreachable in the VM (🟡)

# Cycle 5 — banking

## S20 — a singular nav before a collection breaks the generated create endpoint and seed (🔴)

- `Account` has `parent: Account` (singular) + `txns: many Transaction` (collection). The factory is
  `Create(string currency, string number, Account? parent = null, IEnumerable<Transaction>? txns = null, long balance = 0L, long flags = 0L, AccountKind kind = …)`.
- The generated `Program.cs` calls it **positionally with the collection in the singular slot**:
  - line 32 (create endpoint): `Account.Create(dto.Currency, dto.Number, Enumerable.Empty<Transaction>());`
  - line 251 (seed): `Account.Create("Sample", "XXXXXXXX", Enumerable.Empty<Transaction>());`
  → `error CS1503: Argument 3: cannot convert from 'IEnumerable<Transaction>' to 'Account?'` (twice), so the
  emitted host does not build at all. The http gate caught it.
- Expected: the emitter must order arguments to match the factory (or pass `txns:` by name).
- Why it only shows now: an entity with a singular nav *and* a collection needs a create endpoint; logistics'
  `Customer` (owned `address` + `orders`) had no create endpoint because of S18 — so the two defects mask
  each other in different domains.
- Control (invoicing sub-probe): `Invoice { Reference, customer: Customer, lines: many Line }` builds fine
  and has **no** `Invoice.Create(` call site at all — because the bidirectional back-reference makes Invoice
  a child per the aggregate, so S18 removes its endpoint and the mis-ordering never surfaces. S20 is
  therefore coupled to the aggregate: it hits entities the aggregate keeps as roots (the self-referential
  `parent` is the clean trigger, since it cannot make the entity someone else's child).

## S21 (note, not a defect) — `any` fires on each transition

- `when any txns Flagged { assign Flags to Flags + 1 }`: flagging txn A → `Flags=1`; flagging txn B →
  `Flags=2`. Guide §7 says `any` "fires once when at least one linked related entity is in a matching
  stage" — read literally that would be once *ever*. Two separate transitions each fired once, so "once"
  means once per transition event (not per matching peer). Distinguishing `any` from `Each` needs one event
  that moves several peers at once (a `for … invoke` fan-out); deferred.

# Cycle 8 — fleet

Domain: `docs/probes/scratch-2026-10-14/fleet.poly` (a single fan-out action that moves three
children at once, three subscriptions with different quantifiers, arithmetic policy, `entry`/`exit`).

## S25 🟡 — `any` is indistinguishable from the default `Each`

- Three subscriptions on the same relationship/stage with separate counters:
  `when jobs Done { DoneCount + 1 }`, `when any jobs Done { AnyCount + 1 }`, `when all jobs Done { AllCount + 1 }`.
- One `CompleteAll` action (a `for jobs as t where t in Todo invoke t.Complete` fan-out) moved **all three**
  jobs `Todo → Done` in a single invocation. Result: **`DoneCount=3`, `AnyCount=3`, `AllCount=1`**.
- So `each` and `any` fire once per peer transition; only `all` behaves differently (once, when the whole set
  matches). The guide's table says `any` "fires **once** when at least one linked related entity is in a
  matching stage", which would be 1 here — the documented "any" and "Each" cannot be told apart in practice.
- This also resolves the S21/S23 ambiguity: "once" in the guide means once per transition *event* for `all`;
  `any` is not "once ever" in any observable case.

## S26 🔴 — an entity named `Task` shadows `System.Threading.Tasks.Task` in the emitted host

- The http gate failed with 5 errors in the generated `Program.cs`:
  `CS1983: The return type of an async method must be void, Task, Task<T>, …` (line 348),
  `CS1061: 'Task' does not contain a definition for 'GetAwaiter'` (line 24) and two `CS0126`s.
- Cause: the domain's `Task` entity shadows `System.Threading.Tasks.Task`, so the emitter's
  `async Task SeedAsync(FleetDbContext db)` / `await …` resolve to the domain type.
- Same family as F11 (`Program` entity) and F19 (C# keywords), but this is a **BCL type** collision, and
  `Task` is a very plausible domain name for a work item. It only appears on the http/storage path (the
  entity-only export has no async methods).
- Workaround used: renamed the entity to `Job`.

## S26 refined — only a *type* named `Task` breaks the async host

- Any domain **type** named `Task` (entity or enum) shadows `System.Threading.Tasks.Task` in the emitted
  http host (`async Task SeedAsync(…)`), so the host does not compile. A *property* named `Task` is fine
  (member names do not shadow a type in a type position), and every other BCL-ish name tested is fine —
  including `Program` (F11 holds).

## S11 refined — the shadow needs a create-in

- `child: many Child` alone builds; adding `AddChild: action … -> Child { create in child { … } }` makes the
  emitted factory `Child.Create(label, this)` bind to the `Child` property → the confusing
  `FileSystemAclExtensions.Create` overload error. The trigger is the emitted per-nav factory, not the
  property.

## S10 extended — reserved words as member names

- `policy`, `stage`, `when` (and the rest of `DslTokenReader.WordToKind`) are rejected as property names with
  `Expected property, stage, action, or policy, got '<word>'` — no hint that the word is reserved.

## S28 🔴 — an enum property's column type is the enum's own name, on every pack

- `Kind: Kind` emits `b.Property(x => x.Kind).HasColumnName("kind").HasColumnType("Kind")` for **both** sqlite and
  sqlserver; the resulting DDL is `"kind" Kind NOT NULL`.
- SQLite accepts it (loose typing, NUMERIC affinity), so it passes the gate and the host runs. SQL Server
  would reject the DDL (unknown data type) — the pack's own string type (`nvarchar(...)`) is what every other
  text property gets.
- Expected: the pack's column type for the enum's storage representation.

## S29 🟡 — `default(...)` is the only thing that makes a create parameter optional (undocumented)

- Printed factory:
  `Create(string code, string currency, string name, string sku, TimeOnly slot, DateTime stampedAt, string title, string todo, bool active = true, Kind kind = Kind.Alpha, DateOnly? made = null, long score = 0L)`.
- Every property **without** `default(...)` is a required parameter (even `Todo: Text`, `slot: Time`,
  `stampedAt: DateTime` — none of them `required`), and the only optional ones are those with `default(...)`
  (`active`, `kind`, `made`, `score`).
- This explains S2 (an enum without a default blocks create), S8 (a value-type property's param has no
  default) and S24 (defaulted properties are absent from the create DTO, so a client cannot set them).
  The guide's §3 property table does not state the rule; `required` governs value *validation*, not
  creatability.

## S27 🟡 — a plausible property type that is not a primitive is reported as a bad navigation

- `Ref: Guid` → `Parse error: Navigation property 'Ref' references unknown entity 'Guid'. No entity with that
  name was found in the domain.`
- `Guid` is authorable as a `default(...)`/expression value (guide §11: "`Now`/`Today`/`Guid` are authorable in
  `default(...)`, assign RHS, and policy bodies"), so `Ref: Guid` is a natural mistake. The message blames a
  navigation and never lists the valid primitives (`Text`, `Number`, `Boolean`, `Date`, `Time`, `DateTime`,
  `Duration`).

- Pack typings are right for every primitive tested (`date`/`datetime2`/`time`/`bit`/`bigint`).
- `pattern` and `equals` are code-enforced (consistent with F12's documented projection).
