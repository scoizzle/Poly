# Collapse thirty tools into seven decisions

Poly's MCP 2.0 surface should shrink from **30 tools to seven** — `poly_guide`, `poly_open`, `poly_define`, `poly_check`, `poly_inspect`, `poly_export`, `poly_simulate` — with an **explicit workspace handle**, one `.poly` document as the only authoring path, and capped, deduplicated results. The measured fixed cost of today's catalog is **18,218 characters, about 4.6k–5.5k tokens**, not the 50k–134k that motivates most MCP diet advice; a seven-tool list saves roughly **2.3k–2.8k tokens once per conversation**, less under prompt caching. The defensible case is **selection and turns**, not the catalog: eight tools answer "what is in my model?" in incompatible shapes, two authoring paths are both declared best, five tools are never advertised by any response, and two tools disagree on the same entity's action count. The larger token win is per-call — a ten-entity `get_domain_analysis` result is **~30–32k chars, 92.9% of it the same 60 hints encoded three times**, costing more than the entire catalog. Ship the author–prove–export slice first, measure wrong-tool rate and turns against a frozen 30-tool baseline, and delete v1 only after non-inferiority.

## The catalog costs 4.6k tokens; one analysis call costs more

Two independent stdio measurements of the built server (`initialize` → `tools/list` against `Poly.Mcp/bin/Debug/net10.0/Poly.Mcp.dll`) both returned **16,464 characters** for the 30-tool catalog: **6,705–6,730 characters of description text** and **7,867 of input schemas**; the 25-character description difference is between the two notes' counts of the same text, not a disagreement about the catalog. Add the **1,754-char** server instruction and the fixed surface is **18,218 chars, 4.6k–5.5k tokens** at the labelled 3.3–4.0 chars/token band. The contract note estimated 7–12k tokens for the same catalog by extrapolating schema cost; the stdio measurement refutes that, and both audits independently landed on the same 16,464. Quote the measured number.

The vendor numbers that drive most MCP diet advice describe a different regime. Anthropic's **58-tool, five-server fleet at ~55k tokens** and **134k-token** worst case (vendor self-report), and the 94-tool GitHub server at **~17.6k tokens** (vendor figure, reported second-hand by Atlassian), are **3× to nearly 30×** Poly's catalog ([Anthropic](https://www.anthropic.com/research/advanced-tool-use); [Atlassian, vendor](https://www.atlassian.com/blog/development/mcp-compression-preventing-tool-bloat-in-ai-agents)). Poly's 30 tools average ~549 chars each, **~137–166 tokens per tool**, below GitHub's ~187, because its descriptions are lean (mean 224 chars; max 732 for `link_instances`, min 35 for `list_sessions`). Speakeasy's vendor ladder — 107 tools hallucinated, 40 tools 3/4 correct, 20 tools 19/20, 10 tools zero errors, small n and not peer-reviewed — and the secondary claim that 30 tools is where descriptions begin to overlap put Poly at the edge of the risk zone, not in the 100-tool failure zone ([Speakeasy, vendor](https://www.speakeasy.com/mcp/tool-design/less-is-more); [Breunig, secondary](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html)). The count is a symptom to fix, not a 50k-token fire.

The first useful model is where the tokens go. Measured as the arithmetic sum of the pieces, it costs **74,366 chars ≈ 18.6k–22.5k tokens** before an instance exists: catalog 16,464 (22%), instructions 1,754 (2%), guide default 9,111 (12%), the guide sections a normal domain needs (§3–§8) cost 43,377 (**58%**), `validate_dsl` 2,873, `apply_dsl` 787. The guide, not the catalog, dominates the cold start. Per call, a ten-entity analysis is ~30–32k chars, `validate_dsl` 21,170, C# export 51,484; on four entities analysis is 5,280 and C# 12,796. **One analysis call at ten entities is 8.0k–9.7k tokens, roughly twice the whole catalog.** Worse, 92.9% of the analysis envelope (28,023 of 30,178 chars) is the same 60 findings written three times, and `validate_dsl` is 98.3% duplicated; the 60 hints are `DMCS001` firing once per length-constrained property on a model whose own summary says "0 errors" (`Poly/DomainModeling/Queries/DomainQueries.cs:293-302`, `Poly.Mcp/Tools/DomainTools.cs:434-465`).

So fixed-surface reduction is a hygiene gate, not the headline. The gate should be **≤9k chars, ≤0.5× baseline**; the headline metrics are **`tool_result_tokens` p90 and calls per task**. Dedupe findings to one array, cap at 20, default `poly_inspect` to brief, replace the 9,111-char guide default with a ~700-char quickstart, and offload artifacts over 4k chars to a file. That is where a 2.0 pays for itself; the tool list is where it stops confusing the agent.

## Thirty tools, eight answers to one question

The 30 split into 2 session, 10 inspect/read, 6 authoring/DSL, 5 export, and 7 runtime tools. Eight of them answer "what is in my model?" with incompatible shapes: overview counts, entity detail, analysis diagnostics, a Markdown report, relationships, constraints, DSL export, and `describe_domain_element`; `get_domain_suggestions` filters the same diagnostics. The cheapest complete read is `export_dsl` (**834 chars for 2 entities, 3,880 for 10**); reading ten entities individually costs ~9,940 chars, 1.3× the whole-domain report and 2.6× the DSL. The surface contradicts itself on the same model: `get_entity_detail` reports "3 stage actions" for `Account` while `describe_domain_element(entity)` reports "0 actions", because only the first got the stage-action fix; `get_policy_expression` returns 311 chars that are a strict subset of `describe_domain_element(policy)` at 745 ([`DomainTools.cs`](https://github.com/scoizzle/Poly/blob/master/Poly.Mcp/Tools/DomainTools.cs), [`OracleTool.cs`](https://github.com/scoizzle/Poly/blob/master/Poly.Mcp/Tools/OracleTool.cs)).

Two authoring paths are both declared best. [`Poly.Mcp/README.md`](https://github.com/scoizzle/Poly/blob/master/Poly.Mcp/README.md) line 156 tells an AI agent to use incremental `add`/`remove`; the server instructions, the shipped skill, and the guide's golden workflow all prescribe one document → validate → apply (`.agents/skills/poly/SKILL.md:12-15`, `PolyMcpInstructions.cs:21-26`, `Poly.Mcp/Docs/poly-dsl-guide.md:1287`). The surface biases the wrong way at first use: `create_domain_session` advertises only `["add","get_domain_overview"]`, `add`'s own description says bulk belongs to `apply_dsl`, and every successful `add` advertises `apply_dsl`. The asymmetry is **13 add kinds to 7 remove kinds**; removing a constraint returns a **510-char** explanation of `ReferenceEquals` internals, and the documented workaround is to replace the whole domain and lose every instance. `add` can create `ManyToMany`, which `export_dsl` refuses, and four contract kinds that no read tool sees. The README's claim that both paths "produce identical models" is false in current code.

Five tools are never named by any affordance — `describe_domain_element`, `oracle_expression`, `get_constraints`, `export_domain_to_shacl`, `export_domain_to_html` — and `get_domain_suggestions` only when hints exist. The affordance graph is inverted: `get_entity_detail` is suggested 51 times, `apply_dsl` 43, `get_dsl_guide` **3**, although `apply_dsl` makes the guide mandatory. `apply_dsl` advertises itself among its eight success affordances, and a re-apply clears instances. The catalog also carries **0 output schemas, 0 annotations, 0 pagination parameters, 5 free-form JSON-string parameters** (`add.payload`, `remove.payload`, `create_instance.propertiesJson`, `invoke_action.argsJson`, `oracle_expression.propertiesJson`), and a `success` field that means "the call ran" for `evaluate_policy` — a false policy returns `success: true` while the test suite pins that behavior.

The repo's own probes record the same failure families repeatedly. `invoke_action` reports the actor's stage instead of the returned instance's stage (`S4`, five recurrences, reproduced 2026-11-06: a `Kid` in `Fresh` reported "New stage: Idle"). DMAS001 hints are invisible through analysis in both dogfood reports. Entity-level policies gate all actions without the description saying so. The repo's own [`docs/reference/mcp-guiding-principles.md`](https://github.com/scoizzle/Poly/blob/master/docs/reference/mcp-guiding-principles.md) already asks for ~10–25 tools, "when not to use", no free-form bags, pagination, annotations, and `revision` on every response; the 30-tool surface misses all of it. Confusion here is surface-shaped, not engine-shaped, which is why the same defects survived multiple runtime rewrites (`docs/probes/findings/scratch-2026-10-14.md`).

## Six or seven? Three choices hide inside the count

The contract note's six tools and the evaluation note's seven both sit inside the evidence-backed band: **5–15 tools per server** ([Phil Schmid](https://www.philschmid.de/mcp-best-practices)), **8–12 for a domain server** (synthesis), and an adaptive shortlist of **~7 tools** that matches showing 50 on BFCL, 90.3% versus 90.8% coverage, while a fixed shortlist of 5 finds none of the hard queries ([arXiv 2605.24660](https://arxiv.org/abs/2605.24660)). The count is not the discriminator. The 6-versus-7 dispute is really three independent choices, and the final number falls out of the rulings.

| Choice | Six-tool contract | Seven-tool variant | Ruling |
|---|---|---|---|
| Separate prover | `poly_check` is its own tool | Folded into `poly_inspect(focus:"analysis")` | **Keep separate.** It is the only tool that would expose `ActionStageInvariant`, `EffectInvariantMetadata`, `ConstraintQualityAnalyzer`, and the disjoint-versus-overlap test — facts no MCP tool reads today. "May I ship?" is a different decision from "what is true?", with a different failure response. |
| Separate reporter | `poly_export(format: markdown/html)` | `poly_report(audience)` | **Fold.** Markdown and HTML are the same facts rendered two ways; the audit measured 1,434/7,824 and 7,480/39,281 chars. `audience: review/operate` is unbuilt capability. A wrong format is a visible enum choice, and an unknown one errors with the valid list — not a tool-selection error. |
| Workspace identity | Implicit connection workspace; no session tools | `poly_open` + required handle | **Explicit.** MCP 2026-07-28 states there is no protocol-level session and servers needing cross-call state should return an explicit opaque handle ([MCP spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). Explicit also fixes a repo-specific hazard: the skill says the server is shared and has no ownership check, so implicit state can silently merge two agents' models. |

The final surface is the six-tool contract plus `poly_open` (with `poly_describe` renamed `poly_define`); it drops the evaluation variant's `poly_report` and keeps the contract's separate `poly_check`. The implicit-state case deserves a fair hearing: the server is stdio and process-local, `sessionId` is pure bookkeeping on 26 of 30 tools, `list_sessions` returns opaque ids with no name or revision, there is no delete or rename, and the skill warns there is no ownership check. That is a **bad handle**, not proof that handles are bad. A short handle returned by `poly_open`, plus `state` in every envelope carrying the model name, revision, and counts, converts the worst failure — a reconnect that silently yields an empty model — into `WORKSPACE_REQUIRED` or `WORKSPACE_EXPIRED` with `poly_open` as the next call. It also preserves two models in one process for the isolation test and for two subagents sharing a server; implicit state can silently merge them. The spec's handle rules — a handle is a name, not a capability; document its lifetime; return a specific expiry error; keep `tools/list` stable per credential — are satisfiable without ceremony. The cost is one call and one parameter.

| Tool | Decision it serves | Writes | Description hook |
|---|---|---|---|
| `poly_guide` | "I don't know this language." | no | Learn the `.poly` surface: minimal document, workflow, denylist, section index. |
| `poly_open` | "Which model is mine?" | workspace | Create or list a workspace; returns the handle every stateful call needs. |
| `poly_define` | "Make this document true." | model | Validate and apply a whole `.poly` document; a rejected document changes nothing. |
| `poly_check` | "May I ship / is this action legal?" | no | Prove the model or one action, argument set, property or expression: proven, violated, unknown. |
| `poly_inspect` | "What is true here?" | no | Read one element with the solver's constraints; brief by default. |
| `poly_export` | "Produce the artifact." | no | Emit dsl, json-schema, csharp, markdown, html, json-ld or shacl. |
| `poly_simulate` | "Try it and observe." | instances | Run create/link/invoke/evaluate steps; one trace entry per step. |

Name the authoring tool `poly_define`, not `poly_describe`: "describe" reads as a read tool, the exact ambiguity the audit found in `describe_domain_element`. Keep the `poly_` prefix because clients flatten every server's tools into one list and `check`/`export` collide; the prefix costs five characters.

Non-goals in v1: incremental `add`/`remove`, a separate report tool, MCP resources, and code mode. The guide tool is the only discovery path that works on every MCP host; deferred loading and code execution are host-specific.

## The envelope, not the count, makes seven tools honest

Every response is `{ok, summary, findings[], data?, next[], state{workspace, model, revision, entities, instances}}`. `ok` means the requested job reached an answer the caller can act on — for `check`, no error-severity finding; for `simulate`, the scenario ran to a trace even if a step failed; a guard block is a failed step, not a failed call. `summary` always states the outcome and the state change, and starts `INVALID:` when the model has errors. `findings` is one array, never null, capped at 20 with `truncated` and `omitted`; each finding carries code, severity, dot path, message, hint, and an advisory fix. `next` is zero to three **call sketches with arguments** — `poly_check(select:"Order.Submit", args:{amount:5000})` — not bare names. Today's affordances force the agent to re-derive arguments from the schema, and a bare `apply_dsl` invites a re-apply that clears instances.

Inputs stay flat: `poly_open(op?: create/list, name?)`, `poly_guide(topic?)`, `poly_define(poly, apply?)`, `poly_check(select?, stage?, args?, expression?, bindings?, severity?)`, `poly_inspect(select?, detail?)`, `poly_export(format, inline?)`, `poly_simulate(steps, reset?, stopOnError?)`. Every stateful call also takes the `workspace` handle returned by `poly_open`.

The single findings array is the biggest measured saving: the ten-entity analysis envelope drops from ~30k chars to ~2.2k before the 20-item cap, because 28,023 chars were the same findings in three encodings. Budgets belong in the contract. `poly_inspect` defaults to brief. `poly_check` findings cap at 2,000 chars. `poly_guide` returns a ~700-char quickstart, defaults to ≤1,500, serves sections on demand, and never defaults to `all` (today's default is 9,111 and `all` is 78,766). `poly_export` inlines up to 4k chars, then returns `{path, bytes, sha256}`. `poly_simulate` caps trace entries and returns `failedAt`. Every cap returns `total`/`truncated` and a narrower `next` sketch. Fix the guide's missing §1 while sectioning it; headings currently run 0, 2, 3 … 13.

`poly_check` is the reason to do this at all, and its honesty is the design. The verdict is **`proven | violated | unknown`**, because the abstract interpreter returns `AbstractValue.Unknown` for division, non-numeric operators, unmodelled modules, and unbound symbols, and today that unknown is silently absorbed into published metadata (`Poly/DomainModeling/Analysis/EffectInvariantAnalyzer.cs:216-266`). `unknown` must name the unmodelled part, and the summary should report the share — "2 of 9 facts unmodelled" — because a `proven` that hides an unknown teaches the agent to distrust the tool. The witness is an interval boundary, not a counterexample search; for strings, patterns, enums, and equality, return the conflicting constraint pair and `witness: null`. State the scope in the description: no uniqueness, no cross-entity reasoning beyond the documented call-chain, no arithmetic inversion. `poly_check()` with no selector returns the cached whole-model verdict in ~200 chars; `poly_check(select:)` does targeted questions. This is where preconditions, narrowed ranges, postconditions, and merged constraints become visible for the first time; no MCP tool consumes them today.

Descriptions follow six beats — outcome, use when, do not use / does not return, inputs, returns, next — in **60–120 words**. The contract's 1–3-sentence drafts sit at or below Anthropic's three-to-four-sentence floor, but long schemas and grammar belong in the guide ([Anthropic](https://platform.claude.com/docs/en/agents-and-tools/tool-use/implement-tool-use)). Every required parameter must be named in prose, which alone catches the `polyText`/`document` class that a blind client hit. Use enums for closed sets, objects instead of JSON-string bags, and one risk level per tool. The exemplar:

> **poly_check** — Proves a fact about the current model: the whole-model verdict, or one action, argument set, property or expression. Returns `proven`, `violated` or `unknown` with the admissible range and a witness when one exists. `unknown` means the analyzer's abstract model cannot decide; bind the input or simulate. Does not re-analyze the document — use `poly_define` for that.

The hooks in the seven-tool table are the opening line of each description; expand each to the six beats and stop.

Annotations and schemas are part of the surface, not polish: `readOnlyHint` on guide/check/inspect/export, `destructiveHint` on define and simulate, `poly_open` additive with `destructiveHint: false`, `outputSchema` plus `structuredContent` with a text fallback, deterministic `tools/list`, and a checked-in golden hash ([MCP annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)). Server instructions stay under ~300 tokens and name the loop: `guide → open → define → check → fix → export or simulate`.

`poly_simulate` takes steps as data — `create`, `link`, `unlink`, `invoke`, `evaluate`, `get` — and returns one trace entry per step with `ok`, stage from/to, `failedGuards`, and `failedAt`. Each step is atomic: a guard-blocked invoke leaves the instance unchanged, and earlier steps stay committed; `reset: true` starts clean. If transcripts later show agents misreading a half-run scenario, add `commit: false` as a dry-run; do not make transactionality the default. `SetProperty` stays off the surface, because a mid-run write lets a scenario repair data the model forbids. No `runId`; one run per workspace. This is also where `S4` gets fixed: report the stage of the returned instance, not the actor.

## Measure wrong-tool rate and turns; ship author–prove–export first

Build the seven tools above, delete the 30 below, and hold the result to nine gates; the first slice is the five-tool author–prove–export vertical.

The A/B is the only credible evidence, and it must be pre-registered before the descriptions are written. Freeze the baseline tree — the working tree has a modified `Program.cs` and an untracked `PolyMcpInstructions.cs`, so `HEAD` is not what the owner runs — and record the `tools/list` and instruction hashes. Run both surfaces from one binary behind `POLY_MCP_SURFACE`. Start with the evaluation note's 12 scored tasks, one negative task (Poly should not be used), and one two-workspace isolation task, then add tasks mined from the two dogfood reports and the probe `S`-list to reach **16–20 scored tasks**, because those are recorded real failures and the 12-task core is below Anthropic's 20–50 starting range ([Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)). Write three held-out tasks after descriptions freeze. N=3 pilot, N=5 main, two model families, fresh process and conversation per trial, paired per task, code graders validated by replaying every reference transcript to 100% before spending tokens. Grade outcomes, not paths: `required` is "at least one model-producing call and one artifact call", everything else `allowed`.

| Metric | Gate |
|---|---|
| `pass@1` | ≥ baseline and ≥ 0.80 |
| `pass^5` | ≥ baseline + 0.10, and ≥ 0.60 |
| `wrong_tool_rate` | ≤ 5% and ≤ baseline |
| Calls per successful task (median) | ≤ 0.7× baseline |
| First valid model calls (median) | ≤ 0.8× baseline |
| Total tokens per successful task (median) | ≤ 0.8× baseline |
| Fixed surface tokens | ≤ 0.5× baseline (≤ 9k chars) |
| Zero-tool rate on the negative task | ≥ 0.9 |
| Recovery after one seeded error | ≥ 0.80; ≤ 2 recovery cycles |

Token accounting separates cached from uncached input and reports fixed surface as a one-time cost, because provider caching means the invoice, not the catalog, decides. That suite is still directional; require the direction on two models or two independent runs. If the A/B is null, 2.0 keeps a maintainability case — seven tools, one authoring path, one envelope — but argue it as such, not as an eval win.

| New tool | Absorbs and deletes |
|---|---|
| `poly_guide` | `get_dsl_guide` |
| `poly_open` | `create_domain_session`, `list_sessions` |
| `poly_define` | `validate_dsl`, `apply_dsl`, `add`, `remove` |
| `poly_check` | `get_domain_analysis`, `get_domain_suggestions`, `oracle_expression` |
| `poly_inspect` | `get_domain_overview`, `get_entity_detail`, `get_constraints`, `get_relationships`, `get_policy_expression`, `describe_domain_element` |
| `poly_export` | `export_dsl`, `get_domain_report`, `export_domain_to_json_schema`, `export_domain_to_csharp`, `export_domain_to_html`, `export_domain_to_json_ld`, `export_domain_to_shacl` |
| `poly_simulate` | `create_instance`, `get_instance`, `list_instances`, `link_instances`, `unlink_instances`, `invoke_action`, `evaluate_policy` |

Before deleting, settle two things. Confirm that `.poly` text can author the contract and value-type shapes that `add` can create today — the audit proves `export_dsl` prints contracts, not that the parser accepts them. Record that `ManyToMany` becomes unexpressible: it was already unpersistable, so deleting `add` removes a trap rather than a capability. Port every surface test; `ValidateDslTests` is only 103 lines and 6 call sites, but the engine and session tests stay.

The first slice is the **author–prove–export vertical**: `poly_guide`, `poly_open`, `poly_define`, `poly_check` (whole-model plus one targeted action), and `poly_export` (dsl and json-schema), behind the flag, with a black-box stdio client, eight contract tests, and annotations plus output schemas for its five tools. Its gate is concrete: exact names and a `tools/list` hash; every required parameter named in the description; unknown arguments rejected with the valid names; `WORKSPACE_REQUIRED`, not a crash; a failed define leaves revision unchanged; no empty artifact; dsl and json-schema byte-identical to v1 on four fixtures; fixed surface ≤9k chars, guide default ≤1,500, define findings ≤2,000 on four entities, check verdict ≤800. This proves the seam — one document in, one verdict out, one artifact out — with the least new code. Slice 2 adds `poly_inspect` selectors, the remaining formats, and the rest of the schemas. Slice 3 adds `poly_simulate`, the task corpus, replay, the pilot, then the main A/B and v1 deletion.

## Conclusion

The count was never the decision. Thirty tools are a symptom of authoring and reading by accretion; seven is what falls out of three rulings — keep the prover, fold the reporter, make the workspace explicit. The number to watch is not 30 or 7 but the size of one result and the turns to a valid model; a surface that ships seven tools but still returns 30k-char analyses has solved the wrong problem.

The real risk is coverage: deleting a tool the agent needed. The mitigations are the quickstart guide, argument-bearing `next` sketches, the finding-path-as-selector identity, and pre-registered fallbacks — an eighth `poly_report`, a split `poly_inspect`/`poly_analyze`, or a `mode: patch` on `poly_define` if document replacement proves too expensive. The failure mode to avoid is shipping seven tools, declaring victory from a 2.5k-token delta, and leaving the result payloads untouched.
