# Ship scoped uniqueness as a scalar key

Yes, Poly should add a scoped uniqueness constraint, and it should ship it as a required scalar scope property — not as `unique_within(navigation)`. The scoped-uniqueness gap is real: Poly's `unique` is one global key per property, so **two rooms in different hotels cannot both be numbered 101**, and no existing construct fixes that. But the two design notes that recommend a navigation scope and the feasibility note that rejects it are not disagreeing about taste; they are describing two different features. A navigation scope needs the parent's *identity* at the guard, and the lowered module has no identity to read — the create guard is a **static** factory method, the entity type carries **no id member at all** ([Source](../Poly.Tests/DomainModeling/Compile/EmitGolden/crm/Opportunity.cs.golden#L41)), and the only key in the system is an EF **shadow** property the module can never see ([Source](../src/Poly.Packs.Product/DbContextGenerator.cs#L277)). A scalar scope is enforceable today through the seams that already exist. Two latent bugs must be fixed first: the `ConstraintMerge` false contradiction, and the three-way null-path divergence. The honest slice is **five green commits**, with the DSL spelling landing last, and navigation scope waits behind three named preconditions.

## The gap is real, and prior art splits it into three different constraints

The formal content of "unique within a parent" is a **functional dependency whose determinant includes the parent**: `{parent} ∪ key` is a candidate key of the child relation. That is the ER model's **weak entity with a partial key**, specified for forty years — a dependent is identified by its first name *plus* the employee it belongs to, and the mapping rule makes the child's primary key "the combination of the primary key(s) of the owner(s) and the partial key of the weak entity type" ([Source](https://www.cs.purdue.edu/homes/bb/cs448_Fall2016/lecture-files/pdf/ch07-Relational%20Database%20Design%20by%20ER-%20and%20EERR-to-Relational%20Mapping.pdf)). Treat the "≡ functional dependency" step as inference, not quotation: the notes flag that no primary source for Armstrong's axioms was fetched. The ER framing matters anyway, because it supplies the lifecycle answer the SQL layer leaves implicit — a weak entity's existence depends on its owner, so the scope disappears with the rows.

Every surveyed system separates **three** constraints that Poly currently conflates into one keyword, and the split is the single most reusable finding in the notes.

| Constraint shape | What it says | Prior-art spelling | Poly today |
|---|---|---|---|
| Per-subject at-most-one | one value per instance | OWL `FunctionalProperty`, SHACL `sh:maxCount 1` | not offered |
| Per-population at-most-one for a value | one instance per value, globally | SQL `UNIQUE(value)`, OWL `InverseFunctionalObjectProperty`, DASH `uniqueValueForClass` | `unique` |
| Per-parent at-most-one | one instance per value *per parent* | SQL `UNIQUE(parent_id, value)`, LinkML container-scoped `unique_keys`, XML Schema `xs:unique`, ER partial key | **the gap** |

SQL has no distinct scoped construct at all: a multi-column unique constraint merely says "the combination of values in the indicated columns is unique across the whole table" ([Source](https://www.postgresql.org/docs/current/ddl-constraints.html)), so scope is *data*, not a declaration. LinkML is the only mainstream schema language with a first-class scoped key, and its scope is structural — "the uniqueness scope is that of the container (the multi-valued slot) that contains instances of the identified class" ([Source](https://linkml.io/linkml/schemas/constraints.html)). XML Schema derives scope from where the declaration sits: "the root element for the constraint is the element in which the constraint is defined" ([Source](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html)). Three mechanisms, one shape: **an implicit scope plus an explicit key**. Only LinkML also keeps a separate global variant (`identifier: true`), and only XML Schema keeps presence separate from uniqueness (`xs:key` requires the fields; `xs:unique` ignores keyless nodes) ([Source](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html)). Both distinctions belong in Poly's design even if it ships one keyword.

Two pieces of prior art must be rejected outright. OWL 2 `HasKey` is scoped to a **class expression**, not a parent, and it is an **entailment axiom**: named individuals that agree on every key property are concluded to be *the same individual* ([Source](https://www.w3.org/TR/owl2-direct-semantics/)). A domain author writing a scoped uniqueness rule means "reject this data", never "merge these records" — inheriting OWL's reading would silently coalesce two business objects, which the notes correctly call a hard no. UML's `{unique}` is a second false friend: it is set-versus-bag semantics on a collection, constraining values within one multivalued feature, never a population ([Source](https://stackoverflow.com/questions/44671936/what-is-unique-eclipse-uml-stand-for)). The architectural lesson from the "no" cases is the one that predicts Poly's own difficulty: JSON Schema validates one instance location at a time and its spec says validators "do not need to maintain state across the document-wide validation process" ([Source](https://json-schema.org/draft/2019-09/json-schema-validation)); SHACL Core has no unique-key component at all and every workaround is a self-join in `sh:sparql` ([Source](https://book.validatingrdf.com/bookHtml013.html)). Scoped uniqueness is inherently a **population-level** check, and per-node validators cannot express it.

## Poly's unique path already has the seam — and is missing one key dimension

The existing implementation is smaller and better layered than the feature's absence suggests. `UniqueConstraint` is an empty marker record ([Source](../Poly/DomainModeling/Ontology/Constraints/UniqueConstraint.cs#L3)), and its entire meaning lives downstream: analysis refuses to prove it ("cannot validate statically; requires instance set", [Source](../Poly/DomainModeling/Analysis/ConstraintValidation.cs#L19)), the storage library compiles it into **one static helper and one guard placed before the first `new`** plus a post-construction record ([Source](../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L40)), and assignment is rewritten post hoc from an `EnsureUnique`-then-assign shape into inline `Exists`/`Release`/`Record` calls. The runtime key is the string triple **`entity \u001f property \u001f value`** ([Source](../Poly/DomainModeling/Runtime/ModuleStoragePort.cs#L40)), and the port is a deliberately tiny three-method interface whose docstring promises "no other writes and no `SaveChanges`" ([Source](../Poly.Runtime/IStoragePort.cs#L3)). Because the guard is already an ordinary `Invoke` on the port, adding a scope argument changes **no VM semantics** — the seam is real.

What is missing is one dimension, and a set of unguarded assumptions around it. Uniqueness scope today is the entity type across the whole session and database, because the entity name is baked into the key: two `Room`s under different `Hotel`s genuinely cannot both be `101`. Enforcement runs at exactly **two** module sites (create and assign) plus **two** host sites (the direct `SetProperty` write and the create-in coercion path). Link and unlink "mutate only the relationship field" and never touch the port ([Source](../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Links.cs#L22)), and there is **no delete operation anywhere** on the executor surface. Emission is per column: EF gets one `HasIndex(x => x.Col).IsUnique()` for every unique column over a synthetic `int` shadow key ([Source](../src/Poly.Packs.Product/DbContextGenerator.cs#L296)), and JSON Schema and SHACL both drop to a boolean `x-poly-unique` because neither can express cross-document uniqueness. Roughly **45 tests** across eight areas pin this behaviour, and they all assume one global key.

The trap is that `unique` does double duty. The first property carrying it becomes the entity's **natural key**, which drives the HTTP route key, GET-by-key and the `Created` URI ([Source](../Poly/DomainModeling/Analysis/StorageAnalyzer.cs#L183)). A scoped property must never inherit that role: `/api/users/{email}` is simply wrong for a per-tenant email. That single fact, plus the **27 references and roughly ten `is UniqueConstraint` / `OfType<UniqueConstraint>` test sites** that all silently mean *global*, decides the modelling question. The scoped constraint must be a **sibling record** (`ScopedUniqueConstraint(string ScopeProperty)`), never a field on `UniqueConstraint`, so that every un-audited site defaults to the correct answer — scoped is not global — and the sites that must know are explicit.

## A navigation scope has no readable identity in the lowered module

This is the conflict the notes disagree about, and the feasibility finding wins. The create guard is contributed to the entity's **static** `Create` factory and placed before the first `new`: the emitted shape is `public static DomainResult<Customer> Create(string email, ..., IStoragePort db)` with `if (Customer.ExistsWithEmail(db, email)) return Failure(...)` ([Source](../Poly.Tests/DomainModeling/Compile/EmitGolden/orders/Customer.cs.golden#L63)). Inside a static method there is no `this`, so the parent exists only as a **navigation parameter** — and `Create{Nav}` does pass `this` as that argument ([Source](../Poly/DomainModeling/Lowering/DomainToCSharpExporter.Notify.cs#L206)). So the parent *object* is in reach. Its **surrogate identity is not**, and four independent facts say so: the entity type is built only from domain properties, navigations and `CurrentStage`, so `Opportunity` has `Amount`, `Title`, `Account` and no `Id` ([Source](../Poly.Tests/DomainModeling/Compile/EmitGolden/crm/Opportunity.cs.golden#L41)); the only `Id` is an EF shadow int configured by string name and `HasKey` ([Source](../src/Poly.Packs.Product/DbContextGenerator.cs#L277)); the interpreter mints a GUID **after** `Create` returns and stores it only in the executor's maps, running the factory with `self: null` ([Source](../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.cs#L393)); and a repo-wide search for `HasOne`, `WithMany`, `HasForeignKey` and `HasPrincipalKey` returns **zero hits** in `Poly/` and `src/`, so EF supplies the foreign key by convention as a column the module can never read. `StorageForeignKey` exists as a record but has **no production consumer** and is built only for ownership-aggregate children.

That yields three variants, and they must be priced separately rather than treated as one feature.

| Scope form | Create guard | Assign guard | Link/unlink/reparent | Engine change | Verdict |
|---|---|---|---|---|---|
| **Scalar property** (`unique(TenantId)`) | yes — it is a ctor param | yes — `this.TenantId` | key is invariant, nothing to do | none | **ship now** |
| **Nav → parent natural key** (`unique_within(tenant)`) | yes — read `tenant.TenantId` | yes — `this.Tenant.TenantId` | **no** — needs check/release hooks | none, but two semantic preconditions | later |
| **Nav → parent surrogate id** | **no** | **no** | **no** | yes — module-visible identity, or a host token threaded through every entry point | reject for now |

So the semantics/design notes are right about the *model* and the feasibility note is right about the *machine*. A navigation scope keyed on the parent's **surrogate identity** is not enforceable end to end: it needs a new module-visible identity member on every entity — printed member, bag key, EF mapping, route and key consumers — or a host-resolved scope token threaded as an implied parameter into `Create` and every caller, which changes the module signature and every top-level host entry point. That is the engine change the project's tenets tell us not to buy for an unshipped feature. A navigation scope keyed on the parent's **natural key** is cheaper than the notes imply — the module *can* read `tenant.TenantId`, because a parent's domain scalars are readable at both guards — but it carries two preconditions that must be declared, not discovered: the parent must have a `unique` natural key, and that key must be treated as immutable. It also still leaves **link and unlink unprotected**, because those are host-side bag mutations with no module body: the key would have to be re-recorded on link and **released on unlink**, and today nothing releases a key except an assignment that replaces the value. A stale record makes a later create under that parent falsely fail.

The scalar form is not free either. It buys enforcement at the cost of a **second source of truth**: `tenantId` and `tenant` are two declarations of the same fact, and nothing in create, link, unlink or the emitters keeps them in agreement. A child whose navigation is set but whose scalar is null falls outside every scope and the constraint is **silently vacuous**; a stale scalar puts the child in the wrong scope. That is a real semantic downgrade and it should be stated in the guide in those words, not softened. The counterweight is decisive: the scalar is the only form whose key is **invariant under link, unlink and reparent**, which is exactly why it is the only form enforceable at every mutation site today. Ship it with the hazard named, and add an analysis hint when a scope property and a singular navigation describe the same parent (`tenantId` alongside `tenant: Tenant`): "nothing keeps these in sync."

## Adopt ordinal, at-most-one, scope-must-be-present — after fixing two bugs

The semantics to adopt fit in one sentence: **same scope instance, same value, at most one row; no scope or no value, no rule.** Formally, a state violates the constraint only when two distinct instances are both scoped, both keyed, share the same scope instance and share the same value; a violation witness names that pair. Presence is separate from uniqueness — the constraint never asserts a row exists, and "exactly one per parent" is a different, unshipped constraint. Comparison is **ordinal and typed**: `"Sam"` and `"sam"` are different keys, precomposed and decomposed `é` are different keys, and `""` is an ordinary value that collides with another `""`. That matches the simulator today, which compares with `StringComparer.Ordinal` ([Source](../Poly/DomainModeling/Runtime/ModuleStoragePort.cs#L12)), and it deliberately rejects the vendor default: MySQL's `utf8mb4_0900_ai_ci` makes `'james'` and `'James'` equal in its own index examples ([Source](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)), PostgreSQL lets a nondeterministic collation equate case, accents and normalisation forms ([Source](https://www.postgresql.org/docs/current/collation.html)), and PostgreSQL's own docs warn that the NULL default is "implementation-defined according to the SQL standard". A constraint whose meaning depends on deployment is not a constraint.

For the first slice, take the strictest honest admission rule: the **scope is a required, immutable, `Text` scalar property on the same entity, and the value is required too**. That removes the null question from the new surface entirely — SQL Server allows at most one NULL in a composite unique key while PostgreSQL allows many, a three-vendor disagreement with one wrong meaning ([Source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-unique-indexes)) — and immutability is provable from metadata that already exists, since `EntityStructureMetadata.AssignOnlyPropertyNames` walks every action, stage and subscription assign. The `Text`-only narrowing is the most likely complaint, because Poly's own natural keys can be `Int`; the blocker is real (the generated `Exists` compares a stringified column, which does not translate reliably for enums and is provider-dependent for ints), so narrow now and widen with a typed port overload later rather than shipping an unproven translation. Two rules are hints, not errors: a scope that is itself globally `unique`, and a value that carries both `unique` and a scoped form (global implies scoped).

Now the two bugs, both of which the new feature walks straight into.

**The `ConstraintMerge` false contradiction.** `ConstraintQualityAnalyzer` groups a property's constraints **by CLR type** and merges each group, reporting "contradictory … unsatisfiable" whenever `Merge` returns null ([Source](../Poly/DomainModeling/Analysis/ConstraintQualityAnalyzer.cs#L91)). `ConstraintMerge` has arms for range, length, required, optional, equality and pattern, and its fallthrough is `_ => null` ([Source](../Poly/DomainModeling/Ontology/Constraints/ConstraintMerge.cs#L25)). So **two `unique` constraints on one property today report the property as unsatisfiable**, and any new constraint record reproduces the bug the moment an author writes two scoped constraints with different scopes — a perfectly sound conjunction. Fix it in the merge layer, not by dodging it in the new type: either give the identity-shaped constraints an idempotent arm, or exclude non-mergeable kinds explicitly the way `EqualityConstraint` is already excluded. The current dodge — silently not modelling the second constraint — is the failure mode that makes a *correct* declaration an error.

**The null-path divergence.** Three code paths treat a null value three different ways. The lowered assign path skips both `Exists` and `Record` when the new value is null. The host `SetProperty` does not: it converts null to `""` and records that empty key ([Source](../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.cs#L287)). The create arm has **no null guard at all** — the guard and record are emitted unconditionally — and its `IsString` test recognises `ClrTypeReference`, `PrimitiveTypeReference` and a `NamedTypeReference` named `Text`, but **not `OptionalTypeReference`** ([Source](../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L363)). An optional `Text` property's constructor parameter *is* an `OptionalTypeReference`, because optional properties are emitted as such ([Source](../Poly/DomainModeling/Lowering/DomainToCSharpExporter.cs#L283)), so the create guard emits `.ToString()` on a possibly-null parameter — a null-reference throw — and where a null does reach the port it stringifies into the same empty segment as `""`. The result is that two null creates can throw or collide, two null assigns do neither, and a host write treats null as a real value. No red test exists for this; it is a code-level inconsistency, not yet a validated bug, and the report should say so. The fix is one rule — **null never participates** — applied to all three paths, with `OptionalTypeReference` unwrapped in `IsString` and `ToString()` never allowed to conflate null with `""`. For the scoped slice, requiring the value sidesteps it; for global `unique`, which ships today, only the fix does.

Two smaller traps complete the pre-work. A scope that is not a constructor parameter must **fail loudly**: `BuildCreateConstraintChecks` silently `continue`s when no signature parameter matches ([Source](../Poly/DomainModeling/Lowering/DomainToCSharpExporter.Notify.cs#L521)), and the contributed compiler falls back to `new Parameter(parameterName, text)` when `ParameterOn("Create")` is null — a dangling reference. The scoped compiler must throw a positioned error instead. And the immutable scope must be enforced, not assumed: without it, mutating the scope is a key mutation with **no re-index path**, which silently corrupts the key space.

## Five commits, four gates, and the honest price of navigation

Land the slice additively, with the parser arm **last**, so nothing is authorable before it is enforced.

| Commit | Content | Proof it is green |
|---|---|---|
| 1 | `ScopedUniqueConstraint` record; `IsSatisfiedBy`/`Describe`; coverage-table row; merge-audit fix; rules R1–R6 diagnostics and R7–R8 hints | analysis tests built programmatically — nothing authorable yet |
| 2 | `StorageColumn` scope field; `StorageAnalyzer` sets it, `IsUnique` stays **false**; composite `HasIndex(scope, value).IsUnique()`; scoped `Exists` predicate | EF IR tests + a real SQLite duplicate test |
| 3 | `IScopedStoragePort` (additive, so existing implementers still compile); journaled 4-part key; `ScopedUniqueConstraintCompiler` with the guard, assign obligations and rewrite; `SetProperty`/coercion arms | simulate tests + print/simulate parity on byte-identical messages |
| 4 | JSON Schema and SHACL `"x-poly-unique": { "scope": ... }`; `DomainPresentation`; `poly_check` hint and coverage owner; guide rows | exporter + MCP surface tests |
| 5 | the `unique(Scope)` parse and print arms | round-trip, `unique()` error, one dogfood example |

The spelling follows the semantics that ships, and the two notes' spellings encode their two different features. Since the scalar form means "unique per *value*", `unique(TenantId)` is the right slice: it adds **zero vocabulary**, reads as a modifier argument exactly like `range(0, 150)`, and keeps every existing `.poly` file parsing and printing identically. Reserve `unique_within(nav)` for the navigation form if it ever ships — a distinct spelling for a distinct meaning is a feature, not a naming inconsistency, and it prevents a silent semantic change to an already-published keyword. Reject `unique()` outright: an empty scope is either redundant with global `unique` or vacuous. Reject collection scopes, a scope equal to the key, dotted scope paths, entity-level composite keys and partial/filtered indexes in this slice. Do not emit `owl:hasKey`: it is faithful for a `Text` scope and wrong for the product, because it invites a reasoner to merge the duplicates the constraint exists to reject.

Four gates decide when the feature is done, and they are measurable rather than rhetorical. **Correctness:** the sibling-under-a-different-parent case must pass in both engines, the natural key must not be hijacked (`HasNaturalKey == false`, route key still `id`), a failed action must release its pending key, and the global and scoped key spaces must not alias — prefix the scoped key with `\u001e` so the two namespaces are provably disjoint. **Parity:** simulate and printed C# must agree on success, failure and the **byte-identical message**, because the scope becomes a new value on the one boundary the existing parity test asserts is the only boundary. **Performance:** 10k `Create` calls for global versus scoped, expecting **under 5%** difference from one extra string segment; and `EXPLAIN QUERY PLAN` on the generated SQLite database must show the composite index in use, asserted by name rather than by eye. **Operability:** state in the PR body and the guide that adding a scoped constraint to a populated table fails at index creation until the data satisfies it — there is no migration engine, and failing closed is the correct outcome.

What must be true before the navigation form ships is narrower than the feasibility note's worst case, and that is the report's main reframing. Navigation scope by **natural key** does not need an engine change: the module can already read `parent.Key` at create and `this.Nav.Key` at assign. It needs three things instead. A **lifecycle hook set** — `Link` must check and record, `Unlink` must release, and reparent (necessarily unlink→link, since a to-one source refuses a second link) must release the old scope and check the new one in the same transaction. A **declared precondition pair** — the parent carries a `unique` natural key and that key is immutable — which is a stronger demand on a meta-model whose parents typically have no natural key at all. And a **decided semantic** — whether scope means the parent's identity or the parent's key value, because the two diverge the moment a parent is renamed, and only identity survives that. If the answer is identity, the gate becomes the engine change: a module-visible identity member, or a host-resolved token threaded through every entry point, plus removing the shadow-only key. Until all three hold, `unique_within(navigation)` would be a keyword that parses, prints and does not enforce — the one outcome the project's tenets forbid.

## Conclusion

The decision is not "scalar versus navigation" but "which guarantee can be made at every mutation site, today". A scalar scope guarantees the invariant and weakens the model; a navigation scope strengthens the model and guarantees nothing at link time — and at create time only if the parent happens to carry an immutable natural key, which is a precondition the author cannot see in the declaration. Naming that asymmetry in the guide is worth more than closing it prematurely. The precedent worth carrying forward is LinkML's, not SQL's: keep the tri-partition of global identifier, scoped key and scoped compound key as three distinct rules with three distinct error messages, and keep presence separate from uniqueness as XML Schema does, even while shipping one keyword with one argument.

The subtler takeaway is that Poly's biggest risk here is not the missing dimension but the **silent** failure modes around it. A natural-key hijack turns a business rule into a wrong REST identity; a dropped guard turns enforcement off without a compiler error; a scoped key that becomes its own route key admits `/api/users/{email}` for an email that is only unique per tenant; and a null that stringifies to `""` makes the constraint both stricter and weaker than declared, depending on which of three code paths ran. Every one of those is quiet. That is why the two bug fixes precede the feature rather than travelling with it, and why the admission rules are written as compile-time rejections. A constraint that cannot be described, printed or enforced end to end is not part of the language — and the cheapest way to keep that promise is to reject more than feels comfortable in v1.
