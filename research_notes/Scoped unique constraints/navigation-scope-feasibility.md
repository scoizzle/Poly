# Navigation-scoped unique constraints: enforcement feasibility in the lowered module and the EF model

**Scope.** Answer one design question: can `unique_within(parent)` — a `unique` whose scope is a **singular navigation on the child** — be enforced by Poly's lowered module and its EF model, or must the scope be a **scalar property**? Read-only; the repository at `/Users/scoizzle/.t3/worktrees/Poly/t3-4cc2823d` was not modified. Line numbers are from the tree at `aa142413` (2026-11-06).

**Method.** Traced the full path: ontology (`UniqueConstraint`, `Relationship`, `Entity`, `Property`) → analysis (`EntityStructureMetadata`, `StorageModel`/`StorageColumn`/`StorageForeignKey`, `OwnershipAggregateMetadata`) → grammar (`DomainResolver`, `DomainDslPrinter`) → lowering (`EffectLoweringPass`, `DomainToCSharpExporter`, `ConstraintCheckWriter`) → the constraint seam (`ConstraintCompiler`, `ConstraintCompilation`, `ContributedMethods`) → the storage library (`UniqueConstraintCompiler`) → runtime (`IStoragePort`, `ModuleStoragePort`, `ModuleInstanceExecutor` + `.Links` + `.Coercion` + `SetProperty`) → emission (`DbContextGenerator`, `MinimalApiGenerator`, `DbContextArtifactContributor`, the storage packs) → goldens and tests. Several paths named in the brief no longer exist and are called out as such.

**State of the shipped feature in one paragraph.** `unique` is a payload-free property-constraint marker. The storage library compiles it into one static helper `ExistsWith{Property}` and one guard placed in the entity's **static** `Create` factory, plus a record of the key after construction. The port key is the string triple `(entity, property, value)`. Assign is rewritten post-hoc from an `EnsureUnique`-then-assign shape into inline `db.Exists`/`db.Release`/`db.Record` calls. There is no scope, no FK column in emitted C#, and no entity identity scalar in the module.

## Q1. At the create guard and the assign guard, is the parent instance id available — is `Create{Nav}`'s `this` the parent, and is its id readable in the module?

### Takeaway
`Create{Nav}`'s `this` **is** the parent instance, but the unique guard does not run there: it runs inside the child's **static** `Create` factory, where the parent exists only as the navigation **parameter**. No identity scalar exists on a lowered entity at all — neither in printed C# nor as a bag key in the simulator — so "the parent's id" is not a value the module can read at either guard.

### Inferences
- At the create guard the parent **object** is available, and any of its **domain scalar** properties (including a natural key such as `Email`/`Name`) can be read in the guard. Its **surrogate identity** cannot: it is not a member of the type in either execution mode.
- `DomainInstanceStore` no longer exists; the interpreter host is `ModuleInstanceExecutor` with dictionary instances, and the docs that still name `DomainInstanceStore`/`HostAbi` as store jobs describe removed machinery ([First principles, store-job caveat](../../docs/domain-modeling/first-principles.md#L195)). There is no production `HostAbi` type left; the name survives only in test class names.
- The distinction that decides everything downstream: the *scope value* must be constructible by the module body (printed and simulated identically). A parent scalar is; a parent surrogate id is not.

### Gaps
- Whether any real corpus declares an identity scalar (e.g. `Id: Text unique = guid`) on scope parents was not surveyed; I did not run a corpus-wide grep of `.poly` sources.
- `guid` defaults are lowered to `Guid.NewGuid()` / `Guid.NewGuid().ToString()` — [EffectLoweringPass.cs:1203-1229](../../Poly/DomainModeling/Lowering/EffectLoweringPass.cs#L1203-L1229) — so a `Text` identity scalar is *expressible*, but I did not find a test that exercises `Id: Text = guid` end to end.

## Q2. Does a plain singular navigation produce an FK column/field in the printed entity and in the EF model? What is the minimal addition?

### Takeaway
No. In C# the navigation is a nullable reference property with a private setter and nothing else. In the storage model an FK record exists but only for ownership-aggregate children, and **no code emits it**. The DbContext emits no relationship configuration at all, so EF derives a shadow foreign key by convention — a database column the module can never read.

- `Exists` compares one column by name to one string, with the pending-key set as the in-session ledger — [DbContextGenerator.cs:155-201](../../src/Poly.Packs.Product/DbContextGenerator.cs#L155-L201); `Record`/`Release` key on `entity \u001f property \u001f value` — [DbContextGenerator.cs:203-238](../../src/Poly.Packs.Product/DbContextGenerator.cs#L203-L238).

### Inferences
Minimal additions, in increasing cost:

1. **For nav scope → EF needs a real, mapped scope column.** By convention (unverified here) EF creates a *shadow* FK named `{Nav}Id` for `Opportunity.Account`, typed as the parent's PK (the synthetic `int`). A shadow property cannot be read in a typed lambda, so `HasIndex(x => new { x.Number, x.AccountId })` will not compile against it; you would need the string overload `HasIndex("Number", "AccountId")` plus `EF.Property<int>(e, "AccountId")` inside `Exists`. That is still "no engine change" but it is two new emission shapes and an AST capability the writer does not currently have.
2. **Scalar-AST cost that both forms share:** the generated index is single-column by construction (`HasIndex(x => x.Col).IsUnique()`, [DbContextGenerator.cs:296-302](../../src/Poly.Packs.Product/DbContextGenerator.cs#L296-L302)), and the Syntax AST has no anonymous-object expression to build a composite key: `New` is constructor-only — [New.cs:15](../../Poly/Ast/Nodes/New.cs#L15) — and there is no member-initializer/anonymous-type node in `Poly/Ast/Nodes`. So **any** scoped unique (scalar or nav) needs a composite-index representation (new node kind, or a string-lambda/`HasIndex(params string[])` emitter path).
3. **For nav scope → the module still needs a readable value.** The cheapest correct minimal addition is not an FK at all: require the **parent** to expose a unique natural key and read `parent.{Key}`. That needs zero new columns and zero new AST nodes for the read, but it changes the semantics from "identity of the parent instance" to "value of the parent's natural key" (see Q5/Q6).

### Gaps
- EF Core's convention FK for a nav with no `HasOne` is standard EF behaviour, but this repo never materialises a model, so I could not verify the shadow-property name, CLR type, or whether the FK is created for a nullable nav with the parent's *shadow* key. Treat the shadow-FK statement as an inference.
- Whether the generated `DbContext` would accept a composite string-based `HasIndex` together with a shadow PK-only FK is unverified without running EF.

## Q3. Can the scope key be computed at create, assign, link, unlink and reparent? Which sites need host/interpreter support beyond the storage port?

### Takeaway
Create and assign can compute a scope from the child's navigation **only if the scope reduces to a parent scalar**; link, unlink and reparent cannot, because they are host-side bag mutations with no module body and no port interaction. A navigation scope therefore needs work outside the storage port: the key must be re-recorded on link and released on unlink, and today neither happens.

### Cited Findings
- Create guard: static helper call with `(db, value)` only — [UniqueConstraintCompiler.cs:40-70](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L40-L70); the value is stringified with `ToString()` — [UniqueConstraintCompiler.cs:37-38](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L37-L38).
- Assign: `EnsureUnique` is emitted on the child as `this.EnsureUnique(propertyName, value)` — [EffectLoweringPass.cs:392-402](../../Poly/DomainModeling/Lowering/EffectLoweringPass.cs#L392-L402) — and rewritten into inline port calls. The matcher requires **exactly two** arguments — [UniqueConstraintCompiler.cs:248-280](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L248-L280), in particular `arguments.Length != 2` — [UniqueConstraintCompiler.cs:260](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L260) — and the replacement emits `Exists(value)`, capture `previous`, assign, `Release(previous)`, `Record(value)` — [UniqueConstraintCompiler.cs:287-322](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L287-L322) — with the call shape `new Member(_db, name)`, `(entityName, property, argument.ToString())` — [UniqueConstraintCompiler.cs:316-321](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L316-L321). The rewritten method must already carry the `db` parameter or it fails closed — [UniqueConstraintCompiler.cs:138-141](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L138-L141); `db` is installed as an implied parameter on every method containing that assign — [UniqueConstraintCompiler.cs:82-101](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L82-L101).
- The assign guard runs on the instance, so `this.{Nav}` is reachable (nav is a CLR property, [DomainToCSharpExporter.cs:453-458](../../Poly/DomainModeling/Lowering/DomainToCSharpExporter.cs#L453-L458)) but is **nullable** — the ctor default is `null` ([DomainToCSharpExporter.cs:468-497](../../Poly/DomainModeling/Lowering/DomainToCSharpExporter.cs#L468-L497)).
- Link is host-only: `Link` sets `source.Bag[SingularField(contract)] = target.Bag` and, for a second to-one link, refuses with `Relationship.LinkViolationMessage`; it never touches the port — [ModuleInstanceExecutor.Links.cs:22-51](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Links.cs#L22-L51). `Unlink` nulls the field (or removes the item) and never touches the port — [ModuleInstanceExecutor.Links.cs:57-85](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Links.cs#L57-L85).
- There is **no DSL link/unlink effect**, so "reparent" exists only through the host API: effects are `Create…`, assign, transition, invoke, and the like; no `link` token is resolved in `Poly/DomainModeling/Language`.
- Two further **host-side** unique enforcement sites exist beyond create/assign: `SetProperty` checks `_port.Exists`, releases the old value and records the new — [ModuleInstanceExecutor.cs:276-310](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.cs#L276-L310); and the create coercion path pre-checks `_port.Exists` while resolving an unregistered nested bag — [ModuleInstanceExecutor.Coercion.cs:115-133](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Coercion.cs#L115-L133).
- The port has no scope and no instance notion: `Exists/Record/Release(entity, property, value)` — [IStoragePort.cs:10-19](../../Poly/DomainModeling/Runtime/IStoragePort.cs#L10-L19); the session key is `entity \u001f property \u001f value` — [ModuleStoragePort.cs:40-41](../../Poly/DomainModeling/Runtime/ModuleStoragePort.cs#L40-L41).
- The create guard records only after construction (`AfterStatements` → `db.Record(...)` before the return) — [UniqueConstraintCompiler.cs:66-79](../../Poly/DomainModeling/Libraries/Storage/UniqueConstraintCompiler.cs#L66-L79), visible in the golden as `db.Record("Customer", "Email", email);` immediately before `Success` — [orders/Customer.cs.golden:86-88](../../Poly.Tests/DomainModeling/Compile/EmitGolden/orders/Customer.cs.golden#L86-L88).

### Inferences
- **create:** computable iff the scope reduces to a value the module can read — a parent scalar (natural key). No host support needed: `Create{Nav}` already passes `this`, so the callee's guard can read `parent.{Key}` without any new threading.
- **assign:** computable the same way, but the guard must handle a null nav (scope absent). That is a *semantic* decision, and it interacts with unlink: a child whose nav was nulled retains its recorded key under the old scope unless something releases it.
- **link:** not computable by the module. The host knows `source`/`target` and can resolve `_byBag` to an id, but the module would key by the parent's natural key; two enforcement sites would then use two token conventions. Also, on a successful link the constraint must be **checked and recorded**, which is new host behaviour.
- **unlink:** worse than a missing check — the recorded key must be **released**, otherwise a later child scoped to that parent with the same value falsely fails. Nothing releases it today.
- **reparent** = unlink + link; it needs both of the above plus the old scope captured before mutation. `Link` refuses a second to-one link ([ModuleInstanceExecutor.Links.cs:42-44](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Links.cs#L42-L44)), so reparent is necessarily unlink→link.
- A **scalar** scope sidesteps all of this: link/unlink/reparent change the navigation, not the scalar, so the key is invariant and the existing create/assign/set sites cover it.
- Parity consequence: `UniqueSimulatePrintAgreeTests` asserts that the same lowered module gives the same message on both sides and that "the port is the only boundary value" — [UniqueSimulatePrintAgreeTests.cs:17-21](../../Poly.Tests/DomainModeling/Compile/UniqueSimulatePrintAgreeTests.cs#L17-L21), [UniqueSimulatePrintAgreeTests.cs:59-70](../../Poly.Tests/DomainModeling/Compile/UniqueSimulatePrintAgreeTests.cs#L59-L70). A nav scope adds the scope to that boundary; if the sim used `ModuleInstance.Id` while print used the parent's natural key, the two sides would disagree.

### Gaps
- I did not verify how large the real corpus's link/reparent usage is; if reparenting is never exercised outside the host API, the missing link guard is a latent rather than an observed failure.
- Whether `Unlink`-then-`Link` is reachable from any MCP tool surface (beyond `ModuleInstanceExecutor`) was not traced.

## Q4. Is there an existing seam (`ConstraintAnchor.Create`, `ContributedMethods`, `HostAbi`, `IStoragePort`) that can carry a `scope` without changing analysis/VM semantics?

### Takeaway
Yes for the **module tree**: the anchor, placement, and parameter-threading machinery carry a scope with no AST or VM change, and a declared scalar scope needs no threading at all. `IStoragePort` is the one contract that must grow a scope argument. `HostAbi` and `DomainInstanceStore` no longer exist, so they are not seams.

### Cited Findings
- `ConstraintAnchor.Create` / `Named` resolve semantically (any method with that name), so the create and assign sites need no anchor change — [ConstraintCompiler.cs:12-30](../../Poly/DomainModeling/Compile/ConstraintCompiler.cs#L12-L30), [ConstraintCompilation.cs:167-190](../../Poly/DomainModeling/Compile/ConstraintCompilation.cs#L167-L190).
- `ConstraintContribution` already carries `BeforeStatements`, `AfterStatements`, `ImpliedParameters`, `SupportingMethods` — [ConstraintCompiler.cs:128-146](../../Poly/DomainModeling/Compile/ConstraintCompiler.cs#L128-L146) — and `ImpliedParameter(name, type, ThreadToCallers)` — [ConstraintCompiler.cs:148-153](../../Poly/DomainModeling/Compile/ConstraintCompiler.cs#L148-L153). That is how `db` reaches `Create` and is threaded into callers — [ContributedMethods.cs:124-134](../../Poly/DomainModeling/Compile/ContributedMethods.cs#L124-L134), [ContributedMethods.cs:258-289](../../Poly/DomainModeling/Compile/ContributedMethods.cs#L258-L289), with missing arguments detected by parameter index and bound only when the argument is already a same-named parameter/variable — [ContributedMethods.cs:337-410](../../Poly/DomainModeling/Compile/ContributedMethods.cs#L337-L410).

- `IStoragePort` is the declared storage surface with exactly three methods and a docstring saying "There are no other writes" — [IStoragePort.cs:3-19](../../Poly/DomainModeling/Runtime/IStoragePort.cs#L3-L19). - The host wires the port only when a lowered method actually declares an `IStoragePort` parameter — [CatalogIndex.cs:69-93](../../Poly/DomainModeling/Compile/CatalogIndex.cs#L69-L93) — and registers the context as `IStoragePort` in the minimal API — [MinimalApiGenerator.cs:296-310](../../src/Poly.Packs.Product/MinimalApiGenerator.cs#L296-L310).
- `HostAbi` has no production type (only test class names such as `StageTransitionHostAbiTests`); `DomainInstanceStore` is gone from the tree. The docs still describe both — e.g. [pipeline-convergence-plan.md:242](../../docs/reference/2026-10-03-pipeline-convergence-decisions.md#L242).

### Inferences
- A **scalar** scope needs **no** `ImpliedParameters` entry: the scope property is already a constructor parameter of `Create` and already a parameter of every assign that changes the constrained property is not — but the scope's own value is a field of `this`, readable by the assign guard. The module tree therefore only gains one more argument in existing `Invoke` nodes.
- A **host-resolved token** (needed for surrogate identity) can be carried mechanically by `ImpliedParameter(ThreadToCallers: true)` — the machinery will add it to `Create` and every caller, including `Create{Nav}`. But then every *caller of the caller* must supply it, and the top-level host APIs (`ModuleInstanceExecutor.Create`, `Invoke`, the minimal-API create route, the parity harness) get a new required argument. That is a module-signature change, not an analysis/VM-semantics change.
- The VM needs no change to *call* a 4-argument `Exists`: the call is an ordinary `Invoke` on a `Member` whose value is the port parameter, and the interface method resolves at run time.
- `StorageForeignKey` is a model fact with no consumer, so extending it does not by itself put anything in the EF model or in C#.

### Gaps
- I did not verify that the VM's method resolution accepts an *overload* on `IStoragePort` (as opposed to changing the arity of all three methods); the safe route is to change arity, which is a smaller surface for the resolver but a larger break for test ports.
- Whether `RequiresStoragePort` would still detect the port under an overloaded name is untested.

## Q5. If navigation scope is not feasible, what exactly does a scalar scope (`unique(TenantId)`) lose for the meta-model case (`ModelProperty.Name` unique within `ModelEntity`), and can a back-reference scalar be required instead?

### Takeaway
A scalar scope loses one thing: the scope becomes a second source of truth for "which parent" and can silently diverge from the navigation. Everything else — the at-most-one invariant, create/assign enforcement, EF projection, and the port key — is *easier* with a scalar, because the key is invariant under link/unlink/reparent. Requiring a back-reference scalar is therefore not a semantic downgrade that needs an engine change; it is an authoring obligation with a divergence hazard, and Poly has no machinery that maintains such a scalar today.

### Cited Findings
- No automatic FK scalar exists to require: `StorageForeignKey` names a derived column (`BorrowerId`) but is never emitted, and entity-typed properties are excluded from columns — [StorageAnalyzer.cs:275-276](../../Poly/DomainModeling/Analysis/StorageAnalyzer.cs#L275-L276), [StorageAnalyzer.cs:415-421](../../Poly/DomainModeling/Analysis/StorageAnalyzer.cs#L415-L421), [StorageModel.cs:198-203](../../Poly/DomainModeling/Analysis/StorageModel.cs#L198-L203).

### Inferences
For the meta-model case, `unique_within(ModelEntity)` vs `unique(ModelEntityId)`:

- **What the scalar loses.** (a) One declaration site becomes two (`ModelEntity` nav + `ModelEntityId` scalar) and they can disagree: a child whose nav is set but whose scalar is null falls **outside** every scope, so the constraint is silently vacuous; a stale scalar puts the child in the wrong scope. Nothing in create, `Link`, `Unlink`, or the emitters maintains the pair. (b) `ModelEntityId` must become a required `Create` slot (or be derived), which changes every create-in call site and the HTTP DTO. (c) The model no longer says "within the parent" — it says "within this value", which is a weaker, more error-prone contract.
- **What the scalar does not lose.** The guarantee itself, once maintained; and it is the only form that is enforceable at *every* mutation site, because link/unlink/reparent change the nav but not the scalar.
- **Can a back-reference scalar be required?** Syntactically yes, and it costs the fewest engine changes. But "required" is only a create-time requiredness fact; `Link` can still attach a child to a *different* parent than its scalar, so requiring the scalar does not by itself restore the nav semantics — it moves the trust boundary to the author. To make it sound you would also need either (i) an analysis rule rejecting a nav assignment that disagrees with the scalar, or (ii) a derived scalar maintained by the create/link paths (which is the same host work a nav scope needs).
- **For the specific invariant `ModelProperty.Name` unique within `ModelEntity`:** with a scalar it becomes `unique(ModelEntityId)` on `Name` — a two-column unique `(ModelEntityId, Name)`. That is exactly the SQL shape of a composite unique index and maps to an EF composite index without needing an FK at all. The nav-scoped version is the same SQL shape but requires the FK value to be readable, which is Q1's blocker.
- The natural-key preconditions for a nav scope (`ModelEntity` must declare a `unique` scalar and never reassign it) are a *stronger* constraint on the meta-model than a scalar FK: a meta-model's `ModelEntity` typically has no natural key of its own, in which case nav-scoped-by-identity is the only faithful reading and it is unavailable.

### Gaps
- The meta-model itself is not in this repository; I could not inspect `ModelEntity`/`ModelProperty` to see whether `ModelEntity` already has a `unique` scalar. The whole "nav scope is available for this case" branch depends on that fact.
- Whether the project's design intends the child to carry an explicit FK scalar for aggregate children was not established from a decision record; the code merely derives a name and drops it.

## Q6. Verdict

### Takeaway
**Navigation-scoped uniqueness is not enforceable end to end without an engine change, and it is not even expressible in the module unless the scope reduces to a parent scalar.** Scalar scope is feasible now with a bounded, listable set of changes and is the only form whose key is invariant under link/unlink/reparent. Navigation scope by the parent's **surrogate identity** is the one variant that requires an engine-level change; navigation scope by the parent's **natural key** is feasible with the scalar scope's changes plus a semantic precondition (parent has a `unique` natural key, treated immutable) and still leaves link/unlink unprotected.

**Navigation scope adds, on top of 1–5:**
6. A readable scope value at the guard: either (a) a parent natural key — no new machinery, but a semantic precondition and an immutability obligation; or (b) a surrogate identity — requires a new module-visible identity member on every entity (printed member + bag key + EF mapping + route/key consumers) **or** a host-resolved scope token threaded as an implied parameter into `Create` and every caller, which changes the module signature and all top-level host entry points. 7. Reparent soundness: `Link` must check-and-record, `Unlink` must release, and reparent must release the old scope. None of that exists; it is new host behaviour in [ModuleInstanceExecutor.Links.cs](../../Poly/DomainModeling/Runtime/ModuleInstanceExecutor.Links.cs).

**Verdict in one line:** navigation-scoped is **feasible with 6–7 specific changes if (and only if) the scope reduces to a parent natural key**; navigation-scoped by **surrogate identity is not feasible without an engine change** (module-visible identity); **scalar scope is feasible now with 5 changes** and is the form the current design can actually guarantee.
