# Scoped unique constraints (`unique_within(parent)`) — prior art and semantics

Research cut-off: 2026-11-06. Normative spec language is marked as such; vendor behaviour is marked as vendor.
The recurring finding: **almost nobody has a first-class "unique within this relationship" constraint.** Every system either (a) flattens scope into a composite key tuple, (b) derives scope implicitly from document/container structure, or (c) has no way to say it at all and pushes it into SPARQL, application code, or a bespoke index.

---

## SQL: composite `UNIQUE (parent_id, name)`, NULLs, collation, partial indexes, updates

### Takeaway
SQL's only scoped-uniqueness mechanism is to *include the scope column in the key tuple*: `UNIQUE (parent_id, name)` makes the key unique per parent because the parent id is part of the compared tuple. This is semantically exact and mechanically simple, but it drags in two defaults a domain DSL should not inherit: NULLs are distinct (so "no name" children are all exempt) and equality follows the column collation (so case/accent folding changes what "duplicate" means). Restricting uniqueness to a subset of rows, or mutating keys in bulk, requires separate machinery (partial unique index, `DEFERRABLE`).

### Cited Findings
- Normative/vendor: a multi-column unique constraint "specifies that the combination of values in the indicated columns is unique across the whole table, though any one of the columns need not be (and ordinarily isn't) unique" — [PostgreSQL 18, 5.5.3 Unique Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Adding a unique constraint automatically creates a unique B-tree index on the listed columns; a table may have any number of unique constraints but at most one primary key — [PostgreSQL 5.5.3–5.5.4](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: uniqueness is violated when "more than one row in the table where the values of all of the columns included in the constraint are equal"; by default "two null values are not considered equal", so duplicate rows with a NULL in any constrained column are storable — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Normative: the default NULL treatment in unique constraints "is implementation-defined according to the SQL standard, and other implementations have a different behavior. So be careful when developing applications that are intended to be portable" — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: PostgreSQL supports `UNIQUE NULLS NOT DISTINCT` (and explicit `NULLS DISTINCT`), which makes two NULLs compare equal for uniqueness — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: MySQL's `UNIQUE` index "permits multiple `NULL` values for columns that can contain `NULL`" — [MySQL 8.4 Reference Manual, CREATE INDEX, "Unique Indexes"](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
- Vendor (opposite default): "A `UNIQUE` constraint treats `NULL` as a value. If a column is nullable and a `UNIQUE` constraint exists on the column, at most one row with a `NULL` is allowed." — [Microsoft Learn, CREATE INDEX (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql)
- Vendor: "You cannot create a unique index on a single column if that column contains NULL in more than one row. Similarly, you cannot create a unique index on multiple columns if the combination of columns contains NULL in more than one row. These are treated as duplicate values for indexing purposes." — [Microsoft Learn, Create unique indexes](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-unique-indexes)
- Vendor: SQL Server has no significant difference between a `UNIQUE` constraint and a unique index; both validate identically and the optimizer treats them the same — [Microsoft Learn, Create unique indexes](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-unique-indexes)
- Contradicted source (flagged): a 2026 blog asserts SQL Server "lets you insert multiple `NULL`s" in a unique index and that "PostgreSQL and Oracle follow the same standard" — [powershelldba, "Unique Indexes on Nullable Columns"](https://www.powershelldba.de/blog/articles/unique-indexes-nullable-columns.html). This contradicts Microsoft's own documentation above; the blog appears to describe the *filtered-index* result while claiming it is the plain-index result. Treat as unreliable.
- Workaround for SQL Server's NULL treatment: a filtered unique index `WHERE ProductNumber IS NOT NULL` skips NULL rows entirely, so unlimited NULLs are allowed while non-NULL values stay unique — [Redgate Simple-Talk, "How to get NULLs horribly wrong in SQL Server"](https://www.red-gate.com/simple-talk/databases/sql-server/t-sql-programming-sql-server/how-to-get-nulls-horribly-wrong-in-sql-server/); same technique recommended in [DBA.SE "Why does a UNIQUE constraint allow only one NULL in SQL Server?"](https://dba.stackexchange.com/questions/80514/why-does-a-unique-constraint-allow-only-one-null-in-sql-server)
- Vendor: restricting uniqueness to a subset of rows cannot be written as a unique constraint in PostgreSQL, "but it is possible to enforce such a restriction by creating a unique partial index" — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: a partial index is built over a predicate-selected subset; "The index contains entries only for those table rows that satisfy the predicate", and a unique partial index "enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not" — [PostgreSQL 11.8 Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html)
- Vendor: partial-index example — only one "successful" entry per (subject, target), any number of "unsuccessful": `CREATE UNIQUE INDEX tests_success_constraint ON tests (subject, target) WHERE success;` — [PostgreSQL 11.8, Example 11.3](https://www.postgresql.org/docs/current/indexes-partial.html)
- Vendor: "It is also possible to allow only one null in a column by creating a unique partial index with an `IS NULL` restriction" — [PostgreSQL 11.8](https://www.postgresql.org/docs/current/indexes-partial.html)
- Vendor: column order in a composite index affects query planning, not uniqueness ("Put the category column first, for the reasons described in Section 11.3") — [PostgreSQL 11.8](https://www.postgresql.org/docs/current/indexes-partial.html)
- Vendor: foreign keys must reference columns that "either are a primary key or form a unique constraint, or are columns from a non-partial unique index" — i.e. a *partial* unique index cannot be an FK target — [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: collation determines equality, not just ordering — a nondeterministic collation "may determine strings to be equal even if they consist of different bytes. Typical situations include case-insensitive comparison, accent-insensitive comparison, as well as comparison of strings in different Unicode normal forms"; the docs define such collations with `CREATE COLLATION case_insensitive (provider = icu, locale = 'und-u-ks-level2', deterministic = false)` — [PostgreSQL 23.2.2.4 Nondeterministic Collations](https://www.postgresql.org/docs/current/collation.html)
- Vendor: MySQL string equality/ordering is collation-driven; the docs demonstrate that `utf8mb4_0900_ai_ci` (accent- and case-insensitive) makes `'james'` and `'James'` compare equal, while `utf8mb4_bin` does not — [MySQL 8.4 CREATE INDEX, Functional Key Parts](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
- Vendor: `ON DELETE` actions are `NO ACTION` (default), `RESTRICT`, `CASCADE`, `SET NULL`, `SET DEFAULT`; `SET NULL`/`SET DEFAULT` "do not excuse you from observing any constraints", and a column list can restrict which FK columns are nulled so a key column is preserved — [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Vendor: `ON UPDATE` mirrors `ON DELETE`; `ON UPDATE RESTRICT` "will prevent the update to run even if the state after the update would still satisfy the constraint… This prevents updating a referenced row to a value that is distinct but compares as equal (for example, a character string with a different case variant, if a character string type with a case-insensitive collation is used)" — [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Normative/vendor: unique and primary-key constraints in PostgreSQL are checked per row by default, so bulk key shifts fail even when the end state is valid; `UNIQUE (number) DEFERRABLE INITIALLY DEFERRED` defers the check to commit — [Christian Emmer, "Deferrable Constraints in PostgreSQL"](https://emmer.dev/blog/deferrable-constraints-in-postgresql/); reproducible `UPDATE numbers SET number = number + 1` failure and fix in [Curiosum, "PostgreSQL deferred uniqueness constraints"](https://curiosum.com/blog/using-postgresql-deferred-uniqueness-constraints)
- Vendor limitation: a deferrable unique constraint cannot be an FK target ("The referenced columns must be the columns of a non-deferrable unique or primary key constraint in the referenced table") — quoted in [DBA.SE "Avoid unique violation in atomic transaction"](https://dba.stackexchange.com/questions/104987/avoid-unique-violation-in-atomic-transaction)
- `NOT NULL` and `CHECK` cannot be deferred in PostgreSQL (a documented deviation from the SQL standard), while `PRIMARY KEY`, `UNIQUE`, `REFERENCES` and `EXCLUDE` can — [Emmer](https://emmer.dev/blog/deferrable-constraints-in-postgresql/)
- Oracle supports `DEFERRABLE`/`SET CONSTRAINT … DEFERRED` for unique constraints; SQL Server has no deferrable constraints and needs a staging-table or temp-table two-phase update — [Stack Overflow, "Swap unique indexed column values in database"](https://stackoverflow.com/questions/644/swap-unique-indexed-column-values-in-database)

### Inferences
- `unique_within(parent)` in SQL is exactly `UNIQUE (parent_id, key…)`. There is no distinct construct; scope is *data*, not a declaration. This is the strongest argument that a DSL should model scope as a first-class named reference and only *lower* it to a composite tuple.
- Because PG's default treats NULLs as distinct, `UNIQUE (parent_id, name)` silently degrades to "unique among children that have a name". Reparenting or renaming is not special: they are key mutations and are checked identically (immediately, unless deferred).
- Equality is collation-defined (PG 23.2.1: ordering and character classification use the input expression's collation), so a case-insensitive collation makes `Unique`/`unique` collide in a unique index. MySQL's `_ai_ci` default makes this the *default* behaviour on that platform, which means "the same key" is platform-dependent unless the DSL pins comparison.
- `SET NULL` on a scope column is a silent uniqueness-weakening event: nulling `parent_id` moves the row out of every scope and, under PG semantics, into an exempt class. This is a design trap worth naming explicitly.
- SQL Server's "NULL = NULL for uniqueness only" is a third distinct semantics (neither SQL-standard-implementation-defined nor PG's), which is why portability advice in the PG docs is unusually blunt.

### Gaps
- I did not fetch the SQL:2016/2023 standard text for `<unique constraint definition>`; the "implementation-defined" NULL statement is sourced from PostgreSQL's summary of the standard, not the standard itself.
- No primary source fetched for MySQL's exact behaviour when *part* of a composite unique key is NULL (MySQL's docs state multiple NULLs are allowed; whether that is per-column or per-tuple was not verified).
- No source fetched for Oracle's partial/function-based unique index behaviour beyond the `DEFERRABLE` mention.

## Schema languages: LinkML, JSON Schema, XML Schema, UML, TypeSpec

### Takeaway
LinkML is the only mainstream schema language with a first-class, explicitly *scoped* uniqueness construct, and its scope is the **container** (the multi-valued slot holding the instances) — which is the closest existing spelling of `unique_within(parent)`. XML Schema has real scoped identity constraints but derives scope implicitly from element nesting. JSON Schema has no cross-object uniqueness at all. UML `{unique}` is not a key constraint at all — it is set-vs-bag semantics on a multi-valued feature. TypeSpec only mirrors JSON Schema's `uniqueItems`.

### Cited Findings

**LinkML** (normative for the language)
- "A class can have 'unique keys', which uniquely identify instances of that class within a certain scope." — [LinkML, "Adding constraints and rules"](https://linkml.io/linkml/schemas/constraints.html)
- "Unless specified otherwise below, the uniqueness scope is that of the container (the multi-valued slot) that contains instances of the identified class. That is, when a multi-valued slot has a range set to a class that has one or more 'unique keys', there cannot be two instances with the same values for the keys throughout the entire list." — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Unique keys are inherited: "if a class defines a unique key, the unique key's constraints automatically apply to all the subclasses" — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Compound keys use `unique_keys: {name: {unique_key_slots: [...]}}`; a compound key of one slot is still a compound key and is not the same construct as a singular key — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Singular keys (`key: true`) are limited to one per class and are "automatically *required*, even if the slot holding them is not explicitly marked as such"; `required: false` on such a slot "would be ignored" — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Identifiers (`identifier: true`) are the global-scope variant: "their value must be *globally* unique (there cannot be two instances with the same identifier anywhere). In other words, their uniqueness scope is global, instead of being limited to an enclosing container." — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- A class can have either a singular unique key or an identifier, not both; combining `key: true` and `identifier: true` in one class is an error — [LinkML](https://linkml.io/linkml/schemas/constraints.html)

**JSON Schema** (normative)
- `uniqueItems` applies to arrays only, is boolean, and "An instance validates if and only if all of its elements are unique"; omitting it is equivalent to `false` — [JSON Schema Validation (2019-09), §6.4.3](https://json-schema.org/draft/2019-09/json-schema-validation)
- "Elements in an array value are said to be unique if no two elements of this array are equal" — equality is whole-value equality, so two objects differing in any member are distinct — [JSON Schema Validation, §6.4.3](https://json-schema.org/draft/2019-09/json-schema-validation)
- "While the official vocabularies do not offer a way to ensure uniqueness of array items based a given key, the json-everything project defines a third-party Extended Validation of Arrays vocabulary that introduces a `uniqueKeys` keyword for this purpose. However, keep in mind that third-party vocabularies are often not widely supported." — [learnjsonschema.com, uniqueItems (2019-09)](https://www.learnjsonschema.com/2019-09/validation/uniqueitems/)
- "`uniqueItems` compares whole array items. It does not mean 'unique by id'; two objects with different names but the same `id` are still different objects unless every property matches." — [Jsonic, "JSON Schema Array of Objects"](https://jsonic.io/guides/json-schema-array-of-objects)
- A proposal to allow `uniqueItems` to take a subschema (key-based uniqueness) was opened 2024-10-18 and the response was that the next release is "just looking to publish existing features… No new features for now" — [json-schema-spec issue #1546](https://github.com/json-schema-org/json-schema-spec/issues/1546)
- Cross-field/cross-object uniqueness is out of scope: "you can't do this with JSON Schema. You can check for unique items in an array, but not the object values" — [Stack Overflow, "Can JSON schemas specify cross-field constraints?"](https://stackoverflow.com/questions/47869172/can-json-schemas-specify-cross-field-constraints)

**XML Schema** (normative)
- Identity-constraint definitions "use XPath expressions to pick out sets of information items relative to particular target element information items which are unique, or a key, or a ·valid· reference, within a specified scope" — [XSD 1.1 Part 1: Structures, §2.2.4](https://www.w3.org/TR/xmlschema11-1/structures.html) (XSD 1.0 2E §2.2.4 identical — [W3C](https://www.w3.org/TR/xmlschema-1/))
- Three varieties: `xs:unique` (values unique), `xs:key` (values unique *and required*), `xs:keyref` (references a key or unique) — [XSD 1.1 §3.11](https://www.w3.org/TR/xmlschema11-1/structures.html); contrasted in [O'Reilly, "xs:unique"](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html)
- `xs:unique` requires exactly one `xs:selector` (XPath selecting the nodes across which values must be unique) and one or more `xs:field` (XPath selecting the identifying value); "If there is more than one field element, the combination of the field elements must be unique" — [Microsoft Learn, xsd:unique Element](https://learn.microsoft.com/en-us/previous-versions/dotnet/netframework-4.0/ms256146(v=vs.100))
- Normative: "The root element for the constraint is the element in which the constraint is defined… Defining a root element that has multiple occurrences within a document leaves the possibility of defining local constraints that are unique only in the scope of each occurrence of a document. When a constraint is global to a document, defining it using the document element as a root…" — [O'Reilly, xs:unique](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html)
- Difference between `unique` and `key`: "`xs:unique` keys may be undefined in any of the elements in the selection list, while `xs:key` identifiers must be defined for all the elements in the selection list" — [O'Reilly, xs:unique](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html); same in [Datypic, "Definitive XML Schema" ch.17](http://www.datypic.com/books/defxmlschema/chapter17.html)
- "A unique condition doesn't impose that the node used as an identifier (the field) is required. Selectors whose field is not available are just ignored. To define the same check when the field is required, a 'key' should be defined instead of 'unique.'" — [O'Reilly, "XPath-Based Identity Checks"](https://docstore.mik.ua/orelly/xml/schema/ch09_02.htm)
- `xs:keyref` may refer to either `xs:key` or `xs:unique`, but only to a constraint declared on the same element or an ancestor, because "the 'identity-constraint tables' where the keys and references are stored are local to an element and its ancestors" — [O'Reilly](https://docstore.mik.ua/orelly/xml/schema/ch09_02.htm)
- Composite example: `<xs:unique name="dateAndProdNumKey"><xs:selector xpath="department/product"/><xs:field xpath="number"/><xs:field xpath="@effDate"/></xs:unique>` — [Datypic, Example 17-4](http://www.datypic.com/books/defxmlschema/chapter17.html)
- Field XPath in `xs:field` is restricted (no `../`, no predicates, no functions, no absolute paths) to keep streaming processors feasible — [O'Reilly](https://docstore.mik.ua/orelly/xml/schema/ch09_02.htm)
- Disputed subtlety: whether an `xs:unique` selector node that matches *some but not all* fields is legal. The W3C tableau requires, for each target node, every field to evaluate to "either an empty node-set or a node-set with exactly one member", so partial matching is an error even for `unique`; a commenter argued this reading is wrong — [www-xml-schema-comments, Dec 2005](https://lists.w3.org/Archives/Public/www-xml-schema-comments/2005OctDec/0148.html)

**UML** (normative)
- "For a multivalued multiplicity, this attribute specifies whether the values in an instantiation of this element are unique. Default is true." — `MultiplicityElement::isUnique`, quoted at [No Magic Javadoc, MultiplicityElement](https://jdocs.nomagic.com/2024x/com/nomagic/uml2/ext/magicdraw/classes/mdkernel/MultiplicityElement.html)
- "If the MultiplicityElement is specified as unique… then the collection of values in an instantiation of this Element must be unique. That is, no two values in the collection may be equal, where equality of objects (instances of Classes) is based on object identity while equality of data values… is based on value… If a MultiplicityElement is not multivalued, then the value for isUnique has no semantic effect." — UML 2.x spec, quoted in [Stack Overflow, "What does 'is unique' Eclipse UML stand for?"](https://stackoverflow.com/questions/44671936/what-does-is-unique-eclipse-uml-stand-for)
- `{unique}` composes with `{ordered}` into the four collection types: bag (neither), sequence (ordered only), set (unique only), ordered set (both) — [uml-diagrams.org, "UML Multiplicity and Collections"](https://www.uml-diagrams.org/multiplicity.html)
- Evidence that UML lacks scoped keys and vendors bolt them on: ONF TR-514 defines a non-standard `uniqueSet` property — "defines if the attribute is part of a set of attributes which together (i.e., their values) have to be unique among all instances within a defined context. No value means no uniqueness constraint. An integer value identifies the uniqueness set." — [ONF TR-514 UML Modeling Guidelines v1.3](https://opennetworking.org/wp-content/uploads/2018/08/TR-514_UML_Modeling_Guidelines_v1.3-1-1.pdf)

**TypeSpec** (vendor)
- `@uniqueItems` — "Specify that every item in the array must be unique", applies to `unknown[] | ModelProperty`, and is a JSON Schema emitter decorator (`@TypeSpec.JsonSchema.uniqueItems`) — [TypeSpec, JSON Schema decorators](https://typespec.io/docs/emitters/json-schema/reference/decorators/)
- The emitter maps it onto JSON Schema's `uniqueItems: true` — [TypeSpec, data validation](https://typespec.io/data-validation/)
- Design discussion for that decorator explicitly considers `@key` a separate concept from uniqueness: the resolution included "Add a warning if the decorated item type contains `@key` properties", i.e. `@key` does not by itself imply or enforce value uniqueness — [microsoft/typespec issue #7995](https://github.com/microsoft/typespec/issues/7995)

### Inferences
- LinkML's container scope is a *structural* scope (who owns the list), not a *value* scope. That is the same thing as `unique_within(parent)` when the parent owns a list of children, but it cannot express "unique within a relationship that is itself an entity" (e.g. a join table with an owner column) without reifying a container. This is a real expressiveness boundary worth naming.
- LinkML's orthogonal split — compound key (container-scoped, optional slots), singular key (container-scoped, implicitly required, only one), identifier (global) — is the cleanest published taxonomy of the three things a DSL usually conflates. A DSL should keep all three distinctions even if it has one keyword.
- XML Schema's scope is derived from *where the declaration sits* in the schema/instance tree. That is convenient for documents and hostile to a data model where scope is a reference, not a nesting: you cannot say "unique within `parent_id`" when children are stored flat.
- XML `unique` vs `key` is exactly the at-most-one/exactly-one distinction applied to the *key slots*, not to the entity. It is the single most reused idea across all the surveyed systems (SQL PK vs UNIQUE, LinkML singular key vs compound key).
- UML `{unique}` is a false friend. Reading it as "unique key" is a category error: it constrains a value *collection* (no duplicates in the set), never a *population* (no two instances share a key). It says nothing about scoping and must be rejected as prior art for `unique_within`.
- TypeSpec and JSON Schema are the "no" case, and their limits are structural: both validate one instance location at a time, and the spec says so — JSON Schema validators "do not need to maintain state across the document-wide validation process" — [JSON Schema Validation, §1](https://json-schema.org/draft/2019-09/json-schema-validation). Population-level constraints are outside the model, not merely unimplemented.

### Gaps
- No source fetched on LinkML *runtime enforcement* (whether all validators actually enforce `unique_keys`, and what the error looks like). The docs describe semantics, not conformance testing.
- No source fetched on `xs:unique` interaction with `xs:document` nesting vs `xs:keyref` resolution across `xs:import`/`xs:include` boundaries.
- No fetched treatment of TypeSpec `@key` beyond the issue comment; whether `@key` affects any emitter's uniqueness output was not verified.

## Ontology / RDF: OWL 2 `owl:hasKey`, SHACL, and RDF's non-stance

### Takeaway
OWL 2 `HasKey` is scoped to a **class expression**, not to a parent or relationship, and — critically — it is an *entailment axiom* (coinciding keys imply the two individuals are the same), not a validation constraint (coinciding keys are an error). It also applies only to *named* individuals, and it does not require the key properties to be present, functional, or total. SHACL has no general unique-key constraint in Core (only `sh:uniqueLang`), and SHACL 1.2 does not add one; the community emulates scoped keys with `sh:sparql` or DASH's `dash:uniqueValueForClass`. RDF itself has no uniqueness at all.

### Cited Findings
- Normative: "A key axiom `HasKey( CE ( OPE1 ... OPEm ) ( DPE1 ... DPEn ) )` states that each (named) instance of the class expression CE is uniquely identified by the object property expressions OPEi and/or the data property expressions DPEj — that is, no two distinct (named) instances of CE can coincide on the values of all object property expressions OPEi and all data property expressions DPEj. In each such axiom… m or n (or both) MUST be larger than zero." — [OWL 2 Structural Specification §9.5, via the KGDN mirror of the W3C text](https://kgdev.net/specifications/owl2-syntax/Axioms/); canonical: [W3C OWL 2 Syntax](https://www.w3.org/TR/owl2-syntax/#Keys)
- Normative: "The semantics of key axioms is specific in that these axioms apply only to individuals explicitly introduced in the ontology by name, and not to unnamed individuals… This makes key axioms equivalent to a variant of DL-safe rules." — [OWL 2 Structural Specification §9.5](https://kgdev.net/specifications/owl2-syntax/Axioms/)
- Normative: the direct-semantics condition requires `x ∈ NAMED` and `y ∈ NAMED` (and, for object-property keys, `zi ∈ NAMED`) before concluding `x = y` — [OWL 2 Direct Semantics, Table 9 (§2.3.5)](https://www.w3.org/TR/owl2-direct-semantics/)
- Normative: RDF-based semantics gives the same "if x and y agree on every key property then x = y" condition, and notes "keys are not functional by default under the OWL 2 RDF-Based Semantics" — [OWL 2 RDF-Based Semantics, §5.14, Table 5.14](https://www.w3.org/TR/owl-rdf-based-semantics/)
- Normative/informative: "while in OWL 2 key properties are not required to be functional or total properties, it is always possible to separately state that a key property is functional, if desired" — [OWL 2 New Features and Rationale, F9: Keys](https://www.w3.org/TR/owl2-new-features/)
- Normative/informative: "A key axiom of the form `HasKey( owl:Thing ( OPE ) () )` is similar to the axiom `InverseFunctionalObjectProperty( OPE )`, the main differences being that the former axiom is applicable only to individuals that are explicitly named in an ontology, while the latter axiom is also applicable to anonymous individuals and individuals whose existence is implied by existential quantification." — [OWL 2 New Features, F9](https://www.w3.org/TR/owl2-new-features/)
- Informative: "It does not state that each registered patient has at least or at most one value of `:hasWaitingListN`. The inference that each patient who has a `:hasWaitingListN` belongs to the class `:RegisteredPatient` cannot be drawn." — [OWL 2 New Features, F9](https://www.w3.org/TR/owl2-new-features/)
- Informative: "key axioms will typically not affect class-based inferences such as the computation of the subsumption hierarchy, but they will play a role in answering queries about individuals" — [OWL 2 Structural Specification §9.5](https://kgdev.net/specifications/owl2-syntax/Axioms/)
- Normative (SHACL Core): the only uniqueness-flavoured component is `sh:uniqueLang` — "no pair of value nodes may use the same language tag" — [SHACL, §4.4.5](https://www.w3.org/TR/shacl/#UniqueLangConstraintComponent)
- Provenance: `sh:uniqueLang` was added by resolving ISSUE-82, explicitly scoped to the language-tag case ("A very common pattern e.g. for `skos:prefLabel` is that all values of a property must have a distinct language tag") — [RDF Data Shapes WG ISSUE-82](https://www.w3.org/2014/data-shapes/track/issues/82)
- Secondary but authoritative (book by the ShEx/SHACL spec editors): "One constraint often required is the ability to declare unique keys… Neither SHACL nor ShEx 2.0 support unique keys in general, although they are supported by OWL 2. SHACL Core offers the `sh:uniqueLang` constraint… Other constraints can be defined using SHACL-SPARQL. In the case of ShEx, there is a proposal to add a `UNIQUE` keyword to the language, with the scope and the list of predicates that must be unique as parameters." — [Validating RDF Data, ch.7 "Comparing ShEx and SHACL"](https://book.validatingrdf.com/bookHtml013.html)
- Community emulation 1 (DASH, third-party): `dash:uniqueValueForClass ex:Person` on a property shape — [DASH constraint components, `UniqueValueForClassConstraintComponent`](https://datashapes.org/constraints.html#UniqueValueForClassConstraintComponent), usage shown in [Stack Overflow, "How to impose the uniqueness of data property values via SHACL"](https://stackoverflow.com/questions/76363045/how-to-impose-the-uniqueness-of-data-property-values-via-shacl)
- Community emulation 2 (portable): a `sh:sparql` SELECT that self-joins on the value and filters `?other != $this` — same Stack Overflow answer
- Community emulation 3 (sibling comparison via inverse path): `sh:path ( ex:address [ sh:inversePath ex:address ] ) ; sh:maxCount 1` to detect a value reused across instances — worked through, with the caveat that the naive form is wrong, in [RDFLib/pySHACL issue #182](https://github.com/RDFLib/pySHACL/issues/182)
- Current status (2026): SHACL 1.2 work explicitly preserves Core behaviour — "In SHACL 1.0 it does not handle `xsd:string` - the current WG charter says, about SHACL Core, 'A goal is maximum backwards compatibility'" — and the suggested workaround remains `sh:qualifiedValueShape [ sh:datatype xsd:string ] ; sh:qualifiedMaxCount 1` — [w3c/data-shapes issue #843, comment 2026-04-06](https://github.com/w3c/data-shapes/issues/843)
- RDF layer separation: SHACL exists to "validate RDF graphs against a set of conditions… provided as shapes and other constructs expressed in the form of an RDF graph" — constraints are a separate graph, not part of RDF — [SHACL, Abstract](https://www.w3.org/TR/shacl/)

### Inferences
- OWL's scope axis is **class membership**, and that is the wrong axis for `unique_within(parent)`. To express "name unique among a parent's children" in OWL you must include the parent in the key: `HasKey(Child (hasParent) (name))` — which is precisely SQL's composite trick, not a scoped constraint. OWL has no notion of "within".
- OWL `HasKey` and a uniqueness *constraint* are semantically different operations on the same data: given two children with the same (parent, name), `HasKey` concludes *they are one entity* (merging/identity), whereas `unique_within` concludes *the data is invalid*. A domain DSL must pick one and say so; silently inheriting OWL's reading would make duplicate keys silently coalesce records, which is almost never what a domain author means.
- OWL's "named individuals only" restriction is a real modelling wart (DL-safety), not a design principle to copy.
- SHACL's gap is architectural, not accidental: SHACL Core constraints are evaluated per focus node and per value node, so "no two *other* focus nodes share this value" needs a query with a self-join — which is exactly what every workaround does. This is strong evidence that scoped uniqueness needs a *population-level* (whole-relation) evaluation, which is a different execution model from per-node validation.
- `sh:maxCount 1` on an inverse path is the closest Core-only encoding of "at most one X per Y", and it is exactly the cardinality-vs-uniqueness confusion: it enforces one value per subject, not one subject per value. Reusing it for sibling-uniqueness is a common bug (see the pySHACL thread).

### Gaps
- No fetched normative statement that SHACL 1.2 Core still has no general unique-key component; the evidence is the 1.2 issue comment plus the backwards-compatibility charter goal. A SHACL 1.2 Core spec read would settle it.
- No source fetched for ShEx's `UNIQUE` proposal status (the book calls it a proposal; whether ShEx 2.1/3.0 adopted it was not verified).
- No source fetched on whether any production OWL reasoner *enforces* `hasKey` as an integrity constraint (most treat it as entailment only); the spec text strongly implies entailment.
- No primary RDF 1.1 Concepts citation fetched for "RDF has no constraints"; the claim rests on the SHACL/ShEx layer separation.

## Graph / relational theory: functional dependencies, candidate keys, weak entities, cardinality vs uniqueness

### Takeaway
The formal content of `unique_within(parent)` is a **functional dependency whose determinant includes the parent**: `parent, key → child`, i.e. `{parent} ∪ key` is a candidate key of the child relation. The ER-model name for exactly this pattern is a **weak entity with a partial key**: the child has no key of its own, is identified by an identifying relationship to an owner, and its primary key is `owner PK ∪ partial key`. That is a 40-year-old, precisely specified construct, and it is the correct theoretical backing for the feature.

### Cited Findings
- Textbook (Elmasri/Navathe, via the authors' own slides): "A weak entity must participate in an identifying relationship type with an owner or identifying entity type. Entities are identified by the combination of: a partial key of the weak entity type; the particular entity they are related to in the identifying entity type." Example: "A DEPENDENT entity is identified by the dependent's first name and the specific EMPLOYEE with whom the dependent is related. Name of DEPENDENT is the partial key… EMPLOYEE is its identifying entity type via the identifying relationship type DEPENDENT_OF." — [Elmasri/Navathe, Ch.3 Data Modeling Using the ER Model (Purdue CS448 slides)](https://www.cs.purdue.edu/homes/bb/cs448_Fall2017/lecture-files/pdf/ch03-Data%20Modeling%20Using%20the%20Entity-Relationship%20(ER)%20Model.pdf)
- Textbook, mapping algorithm Step 2: "For each weak entity type W… include as foreign key attributes of R the primary key attribute(s) of the relation(s) that correspond to the owner entity type(s). The primary key of R is the combination of the primary key(s) of the owner(s) and the partial key of the weak entity type W, if any." Worked example: `DEPENDENT` gets PK `{ESSN, DEPENDENT_NAME}` — [Elmasri/Navathe, Ch.7 ER-to-Relational Mapping (Purdue CS448 slides)](https://www.cs.purdue.edu/homes/bb/cs448_Fall2016/lecture-files/pdf/ch07-Relational%20Database%20Design%20by%20ER-%20and%20EERR-to-Relational%20Mapping.pdf)
- Textbook, multivalued attributes (Step 6): a multivalued attribute becomes its own relation whose PK is "the combination of A and K", e.g. `DEPT_LOCATIONS` with PK `{DNUMBER, DLOCATION}` — i.e. the same scope-plus-value shape — [Elmasri/Navathe, Ch.7](https://www.cs.purdue.edu/homes/bb/cs448_Fall2016/lecture-files/pdf/ch07-Relational%20Database%20Design%20by%20ER-%20and%20EERR-to-Relational%20Mapping.pdf)
- Textbook: an identifying relationship "Always has a total participation constraint" on the weak side, and weak entities "Do not have key attributes of their own" — [Elmasri 6e Ch.7 (CSU Ohio)](https://cis.csuohio.edu/~sschung/cis430/Elmasri_6e_Ch07.pdf)
- Course source stating the scope semantics directly: "Dependent identifier is unique only within owner context, so its fully qualified key here is (ssn, dname)" — [UC Irvine CS122A Lecture 3, Conceptual DB Design](https://grape.ics.uci.edu/wiki/asterix/raw-attachment/wiki/cs122a-2015-winter/CS122aLecture3.pdf)
- Course source: "Weak entities are identified by composite keys, where one part is a foreign key of the parent entity, and the second part is a partial key" — worked example `PAR-290-6-6313` (campus / building / floor / room: each level unique only within its parent) — [University of Melbourne, Logical Database Design](https://tomkom.pages.gitlab.unimelb.edu.au/spatialdatamanagement/13_logical_model.html)
- Course source on the constraint taxonomy: "key constraint: the primary key attributes must uniquely identify a row… entity integrity constraint: no primary key can be NULL… referential integrity constraint: FK values must be from the set of existing PK values" — [University of Melbourne](https://tomkom.pages.gitlab.unimelb.edu.au/spatialdatamanagement/13_logical_model.html)
- Textbook: an entity type may have more than one key, e.g. `CAR` with `VIN` and `VehicleTagNumber(Number, State)` — the "many candidate keys, one chosen primary" distinction — [Elmasri/Navathe, Ch.3](https://www.cs.purdue.edu/homes/bb/cs448_Fall2017/lecture-files/pdf/ch03-Data%20Modeling%20Using%20the%20Entity-Relationship%20(ER)%20Model.pdf)
- Practical confirmation that the composite is only as strong as its parts: SQL Server `UNIQUE` treats a composite containing NULL as duplicate — so the "weak entity" composite key is only a total key if the owner part is `NOT NULL` — [Microsoft Learn, Create unique indexes](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-unique-indexes)

### Inferences
- `unique_within(parent, key)` ≡ FD `parent, key → *` over the child relation ≡ `{parent} ∪ key` is a candidate key. Two immediate consequences a DSL should encode rather than rediscover: (1) the constraint is a *declaration of a candidate key*, so the same rule must also answer "can I look up a child by (parent, key)?"; (2) the parent column must be non-null for the key to be total — otherwise you have a *partial* key, which is the weak-entity case done wrongly.
- "Cardinality vs uniqueness" is the cleanest mental split and every surveyed system separates them:
  - per-subject at-most-one = OWL `FunctionalProperty`, SHACL `sh:maxCount 1`, UML upper bound 1;
  - per-population at-most-one for a value = OWL `InverseFunctionalObjectProperty`, DASH `uniqueValueForClass`, SQL `UNIQUE(value)`;
  - per-parent at-most-one = SQL `UNIQUE(parent, value)`, LinkML container-scoped `unique_keys`, `xs:unique` under a parent element, ER partial key.
  These are three different constraints, and `unique_within` is the third. A DSL that offers only the first two will be unable to express the third, and a DSL that offers only the third cannot express global identifiers.
- The ER construct also supplies the lifecycle answer the SQL layer leaves implicit: a weak entity's existence depends on its owner, so deleting the owner deletes the part (this is why `ON DELETE CASCADE` is the natural lowering). Uniqueness then repairs itself because the scope disappears with the rows.
- Because the composite key is a *candidate key*, reparenting is a key update, not a move: `UPDATE child SET parent_id = ?` must be checked exactly like `UPDATE child SET name = ?`. Nothing in the relational model gives reparenting special semantics — which is a point in favour of saying so explicitly in a DSL.

### Gaps
- No primary source fetched for the formal definition of a functional dependency (`X → Y`) or for Armstrong's axioms; the FD framing above is my own reduction of the Elmasri mapping rule, not a quotation. The report writer should treat "≡ FD" as inference, not citation.
- No source fetched on weak entities in the SQL:2016 standard or on how ORMs (Hibernate `@EmbeddedId`, EF composite keys) model reparenting; that comparison would strengthen the "reparenting is a key mutation" claim.
- No source fetched on whether any graph database (Neo4j, TypeDB) has a native scoped-uniqueness constraint; TypeDB's `@key` and `@unique` were mentioned in LinkML's generator list but not verified.

## Boundary semantics: at-most-one vs exactly-one, nulls, case, key ordering, mutation/reparenting, delete/unlink

### Takeaway
Across every surveyed system the same six decisions recur, and each system gets at least one of them wrong or implicit. The consensus that is safe to copy: **separate "the key is present" from "the key is unique"** (xs:key vs xs:unique; PK vs UNIQUE; LinkML singular vs compound key); **make the comparison explicit** (collation/equality is part of the constraint, not the storage); **treat key mutation as ordinary mutation** but allow batch/deferred checking; **make the delete action explicit** because deleting the scope destroys the constraint's domain.

### Cited Findings
- At-most-one vs exactly-one, XML phrasing: `xs:unique` fields "may be undefined in any of the elements in the selection list, while `xs:key` identifiers must be defined for all"; "A key is a unique constraint with the additional restriction that all the nodes corresponding to all the fields are required" — [O'Reilly](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html), [O'Reilly §9.2.3](https://docstore.mik.ua/orelly/xml/schema/ch09_02.htm)
- Nullability is the SQL spelling of the same distinction: a primary key "requires that the values be both unique and not null", and PostgreSQL "will force the column(s) to be marked `NOT NULL`" — [PostgreSQL 5.5.4](https://www.postgresql.org/docs/current/ddl-constraints.html)
- LinkML: a singular key (`key: true`) is "automatically *required*"; declaring it `required: false` "would be ignored" — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Nulls, three incompatible vendor defaults in one place: PG ("two null values are not considered equal"), MySQL ("permits multiple `NULL` values"), SQL Server ("at most one row with a `NULL` is allowed") — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html), [MySQL CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html), [Microsoft Learn CREATE INDEX](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql)
- Standard-level: PG states the default NULL treatment "is implementation-defined according to the SQL standard, and other implementations have a different behavior" — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Explicit nulls-equal opt-in exists (PG `NULLS NOT DISTINCT`) — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html)
- Case sensitivity is a property of the comparison, not the constraint: PG's nondeterministic collations make case/accent/normalization-equivalent strings *equal*; `ON UPDATE RESTRICT` explicitly guards against "a character string with a different case variant, if a character string type with a case-insensitive collation is used" — [PostgreSQL 23.2.2.4](https://www.postgresql.org/docs/current/collation.html), [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- MySQL's default `utf8mb4_0900_ai_ci` demonstrates case- and accent-insensitive equality in its own index examples — [MySQL CREATE INDEX, Functional Key Parts](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
- Composite key ordering: SQL column order does not change uniqueness (the compared tuple is a set of values), only index/plan behaviour — "Put the category column first, for the reasons described in Section 11.3" — [PostgreSQL 11.8](https://www.postgresql.org/docs/current/indexes-partial.html)
- XML field order is positional but equality is componentwise, so reordering `xs:field` elements cannot change which instances collide — derived from the requirement that "the combination of the field elements must be unique" with one `field` per component — [Microsoft Learn, xsd:unique](https://learn.microsoft.com/en-us/previous-versions/dotnet/netframework-4.0/ms256146(v=vs.100))
- Key mutation is checked per-row by default; the canonical failing case is `UPDATE numbers SET number = number + 1` (end state valid, intermediate invalid) — [Emmer](https://emmer.dev/blog/deferrable-constraints-in-postgresql/), [Curiosum](https://curiosum.com/blog/using-postgresql-deferred-uniqueness-constraints)
- The escape hatch on engines without deferrable constraints (SQL Server, MySQL) is staging values then updating, or a temporary discriminator column + partial unique index — [Stack Overflow "Swap unique indexed column values"](https://stackoverflow.com/questions/644/swap-unique-indexed-column-values-in-database), [Stack Overflow "Incrementing with one query a set of values in a field with UNIQUE constraint, Postgres"](https://stackoverflow.com/questions/5363385/)
- Delete/unlink is a policy, not a default: `NO ACTION` / `RESTRICT` / `CASCADE` / `SET NULL` / `SET DEFAULT`, with the explicit guidance that "When the referencing table represents something that is a component of what is represented by the referenced table and cannot exist independently, then `CASCADE` could be appropriate" — [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- A subtle trap with `SET NULL`: the docs warn that the actions "do not excuse you from observing any constraints", but also that a column list can be given so only some FK columns are nulled — "Without the specification of the column, the foreign key would also set the column `tenant_id` to null, but that column is still required as part of the primary key" — [PostgreSQL 5.5.5](https://www.postgresql.org/docs/current/ddl-constraints.html)
- OWL side: keys carry no existence or cardinality obligation at all — "It does not state that each registered patient has at least or at most one value of `:hasWaitingListN`." — [OWL 2 New Features, F9](https://www.w3.org/TR/owl2-new-features/)
- SHACL side: existence and cardinality are separate components (`sh:minCount`, `sh:maxCount`), and uniqueness is not a component at all — [SHACL §4.2, §4.4.5](https://www.w3.org/TR/shacl/)

### Inferences
- The six decisions collapse to a small orthogonal matrix a DSL should expose:
  1. **presence**: key slots total or optional (⇒ exactly-one vs at-most-one population),
  2. **comparison**: exact / case-folded / collation-driven / normalized (⇒ what counts as a duplicate),
  3. **arity**: which slots are in the key, and whether scope is one of them,
  4. **timing**: immediate vs end-of-transaction (⇒ whether key swaps and bulk renames are expressible),
  5. **mutability**: is the key immutable, reparentable, both?
  6. **lifecycle**: on parent delete — cascade, restrict, or detach.
- Copying SQL's "NULLs are distinct" default into a domain DSL is actively harmful: it turns a declared uniqueness rule into one that is silently vacuous for exactly the records a user most needs to name (unnamed children). Recommend either total keys (default) or an explicit "optional key, absent values exempt" flag — never the three-valued default.
- Case sensitivity should not be inherited from the platform's collation, because that makes the *model's* meaning depend on deployment. A `unique_within` should carry its comparison, defaulting to identity/ordinal, with case-folding as an explicit opt-in (this is the opposite of MySQL's `_ai_ci` default and of most collation-driven engines).
- Reparenting deserves to be *named* in the DSL even though its semantics are just a key update, because (a) it is the operation that reveals whether the scope is part of the key, and (b) it is the operation that must decide what happens to the *old* scope's constraint window (nothing — the row simply leaves it).
- `SET NULL` on the scope column should be rejected or warned on by a DSL that has scoped keys: it converts a scoped unique constraint into an unscoped-and-exempt one, which is almost certainly a modelling error.

### Gaps
- No source fetched on how "absent key" interacts with duplicate detection in LinkML (does an absent compound key slot exempt the instance?) — the docs describe the container scope but not the missing-slot case.
- No source fetched on `xs:unique` behaviour with `xsi:nil` values, despite the `key` vs `unique` distinction turning on "the author's name can have a 'nil' value" — [O'Reilly §9.2.3](https://docstore.mik.ua/orelly/xml/schema/ch09_02.htm) raises it without resolving it.
- No source fetched on Unicode normalization as a uniqueness concern beyond PostgreSQL's collation docs; whether a DSL should normalize NFC before comparing keys was not established.

## What a domain DSL should copy, and what it should deliberately reject

### Takeaway
Copy LinkML's tri-partition (global identifier / container-scoped singular key / container-scoped compound key) and XML Schema's present-vs-unique split, but reject every system's *implicit* scope (SQL's composite tuple, XML's element nesting, OWL's class membership) in favour of an explicit scope reference. Above all, reject OWL's reading of a key as identity entailment: `unique_within(parent)` is an integrity constraint (duplicates are an error), not a merge rule.

### Cited Findings
- The four scope mechanisms actually on offer, side by side: SQL — scope is a column in the tuple ("the combination of values in the indicated columns is unique across the whole table") — [PostgreSQL 5.5.3](https://www.postgresql.org/docs/current/ddl-constraints.html); LinkML — scope is the containing multi-valued slot ("the uniqueness scope is that of the container") — [LinkML](https://linkml.io/linkml/schemas/constraints.html); XML Schema — scope is the element the declaration is attached to ("The root element for the constraint is the element in which the constraint is defined") — [O'Reilly](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html); OWL — scope is the class expression (`HasKey(CE …)`) — [OWL 2 Syntax §9.5](https://kgdev.net/specifications/owl2-syntax/Axioms/)
- Only LinkML distinguishes *scoped* from *global* uniqueness as a first-class, orthogonal choice (`unique_keys` vs `identifier: true`) — [LinkML](https://linkml.io/linkml/schemas/constraints.html)
- Only XML Schema distinguishes *optional key* from *required key* as a first-class, orthogonal choice (`xs:unique` vs `xs:key`) — [O'Reilly](https://www.oreilly.com/library/view/xml-schema/0596002521/re54.html)
- The two systems with no answer at all (JSON Schema, SHACL Core) both fail for the same architectural reason: they validate one instance location at a time and have no population-level pass — [JSON Schema Validation §1](https://json-schema.org/draft/2019-09/json-schema-validation), [Validating RDF Data ch.7](https://book.validatingrdf.com/bookHtml013.html)
- OWL's semantics is identity-formation, not validation: agreeing keys imply `x = y` — [OWL 2 Direct Semantics Table 9](https://www.w3.org/TR/owl2-direct-semantics/); "if the values… were the same for two named instances… these two individuals would be equal" — [OWL 2 New Features, F9](https://www.w3.org/TR/owl2-new-features/)
- UML `{unique}` is collection deduplication with no population semantics — "no two values in the collection may be equal… equality of objects… is based on object identity" — [UML spec via Stack Overflow](https://stackoverflow.com/questions/44671936/what-does-is-unique-eclipse-uml-stand-for)
- Weak-entity theory supplies the correct target semantics: key = owner PK ∪ partial key, with total participation in the identifying relationship — [Elmasri/Navathe Ch.7](https://www.cs.purdue.edu/homes/bb/cs448_Fall2016/lecture-files/pdf/ch07-Relational%20Database%20Design%20by%20ER-%20and%20EERR-to-Relational%20Mapping.pdf), [Elmasri 6e Ch.7](https://cis.csuohio.edu/~sschung/cis430/Elmasri_6e_Ch07.pdf)
- Deferrable checking is a real requirement, not a nicety: without it, reordering/swapping keys is inexpressible in one transaction on PG, and requires staging hacks on SQL Server/MySQL — [Emmer](https://emmer.dev/blog/deferrable-constraints-in-postgresql/), [Stack Overflow](https://stackoverflow.com/questions/644/swap-unique-indexed-column-values-in-database)
- Partial/conditional uniqueness is a genuine need (one "successful" row per subject+target) but is expressed as an index predicate, not as constraint semantics — [PostgreSQL 11.8 Example 11.3](https://www.postgresql.org/docs/current/indexes-partial.html)

### Inferences — copy / reject table

| Decision | Copy from | Reject from | Why |
|---|---|---|---|
| Scope is explicit and named (`within: parent`) | LinkML (container scope), ER identifying relationship | SQL composite tuple, XML element nesting, OWL class expression | Scope-as-data cannot be validated, renamed, or reported on; scope-as-placement is unexpressible for flat records; scope-as-class is the wrong axis |
| Three-tier taxonomy: global id / scoped key / scoped compound key | LinkML (`identifier` / `key` / `unique_keys`) | SQL (only one PK, everything else is a bare UNIQUE) | These are three different rules with different error messages and different lowering |
| Presence separate from uniqueness | XML Schema (`xs:key` vs `xs:unique`), SQL (PK vs UNIQUE), LinkML (singular vs compound) | OWL `hasKey` (neither total nor functional) | "Every child has a name" and "no two children share a name" are independent facts; conflating them forces a wrong default |
| Key equality is declared, not inherited | PostgreSQL explicit `NULLS [NOT] DISTINCT`, explicit `COLLATE` | MySQL `_ai_ci` default, SQL Server's implicit NULL-as-value, SQL's implementation-defined default | Otherwise "duplicate" changes meaning per deployment |
| At-most-one default, exactly-one on request | XML `unique` (ignores keyless nodes) with `key` as the strict variant | SQL's NULL-distinct default | At-most-one with *no* exemption for absent keys is the useful default; silent exemption is the failure mode |
| Batch/deferred checking | PostgreSQL `DEFERRABLE INITIALLY DEFERRED` | SQL Server / MySQL (no deferrable constraints) | Key swaps and reorders are ordinary domain operations |
| Key mutation is ordinary mutation; reparenting is a key update | Relational model (candidate key) | Any notion of reparenting as a special un-checked move | If `parent` is part of the key, moving *is* a key change and must be checked |
| Explicit delete/unlink policy | SQL `ON DELETE CASCADE/RESTRICT/SET NULL`, ER "existence dependency" | RDF/OWL (deleting a parent triple silently orphans children) | Destroying the scope destroys the constraint's domain; the policy must be declared, not emergent |
| Duplicate ⇒ error | SQL, XML Schema, LinkML | OWL `hasKey` (duplicate ⇒ same individual) | A domain author writing `unique_within` means "reject this data", never "merge these records" |
| Population-level evaluation | SQL unique index, LinkML container validation | JSON Schema / SHACL Core per-node model | The check is inherently a self-join over the relation; per-node validators cannot express it |
| Conditional uniqueness as a first-class concept (if offered at all) | PostgreSQL partial unique index (as a *lowering target*) | Presenting a predicate-on-index as the *model* | The predicate belongs in the domain model; the index is an implementation detail |
| `{unique}` as key | — | UML `isUnique` | It is set-vs-bag semantics on a collection; it constrains values, not populations |

### Gaps
- No source fetched on how a DSL should *report* a scoped-uniqueness violation (which pair, which field, which scope). SQL gives a constraint name and key value; LinkML's validator error shape was not examined; this is a design gap the report should flag rather than fill.
- No source fetched comparing this feature to TypeDB `@key` / `@unique`, Neo4j uniqueness constraints, or Datalog-style integrity constraints — all plausible prior art for a multi-impl `uses` seam.
- No source fetched on the "at most one per relationship instance" case (a join entity, not an owner), which is the one shape LinkML's container scope cannot express.
